Milestone M6 Relations

CSCI 305: Concepts of Programming Languages

In this milestone you build the logic language inside Bridger. A program declares relations, adds facts to them, states rules about them, and asks queries. A query's answer is the least fixpoint of the rules over the facts. You write the matcher that unifies one atom with one fact, the engine that computes the fixpoint and answers queries, the evaluator and checker arms for the query forms, and the static checks that every rule must pass before the program runs. From now on the rule checks run beside the type checker, and a program that fails either one prints nothing.

What to build the specification

Read the Milestone M6 chapter before you start. It is the authoritative specification. Its two tables, one for the query forms and one for the rule checks, are the checklist your code is measured against. The rules themselves are in the language reference appendix (under evaluation, typing, and purity and effects). The “Building it” sections of the Part VII chapters, from Unification through Querying relations, describe the algorithms. The work is spread over more files than before:

Two changes have no todo_m6! marker. In the Call arm of both the evaluator and the checker, a call whose callee is a relation is a hole-free query. In the checker's Var arm, a relation's name used as a value is RelationNotAValue. The chapter spells out the contracts the tests hold each file to. These are the ones that most often cause trouble:

  • Solutions are distinct and in canonical order. Each match is cut down to the query's named holes, duplicates are removed, and the rest are sorted with the provided compare, first hole first. The answer depends on the facts and rules alone, never on the order the facts were added or the order the engine derived them.
  • Anonymous holes are distinct variables. Each ? becomes a fresh variable no identifier can spell. Give them all one name and needs(?, ?) silently requires both columns to be equal.
  • The database is untouchable during a fixpoint. A query, add, or clear reached from a filter is stuck with QueryInFilter. Set materializing before the rounds and clear it before any error from them is returned. This is the same trap as M4's call depth and M5's nesting bound: a ? before the reset leaves every later query stuck.
  • Arguments run once, left to right, after the relation's name is resolved and before the argument count is judged, so an argument's effect happens even when the form then has the wrong arity.
  • The checks stop at the first failure, in source order. The head is checked before the body and the conjuncts left to right. For each filter, purity checks HigherOrder, then Impure, then Recursive. An Impure error carries a witness, the path of names from the filter to the first effect, and the tests check that path.

Everything outside the holes is provided. That includes the relation database (add, clear, facts), Subst, the driver that binds each declared relation in the root environment and runs the rule checks and the type checker before main, and the RelationColumn check on column types. The chapter lists the provided runtime the M6 files use.

First: paste in the helper module

The starter leaves out a module of helpers that the rule checks use: subexprs, query_exprs, free_vars, and bound_names. The chapter's helper module section prints it in full. Copy it, unchanged, to the end of src/relations/check.rs, and import what you use, as in use helpers::{free_vars, subexprs};.

  • It must live in src/relations/check.rs. Only the submitted files are collected, so a helper you put in a new file of your own is not part of what is graded, and your submission will not compile on Gradescope.
  • It is a pub mod helpers with its own use lines, so it cannot clash with your imports, and a helper you have not called yet raises no clippy warning.
  • You may read and use it freely, but you do not need to change it. The rest of check.rs is your work: the impure set, the witness, the recursion and higher-order checks, and the classification of conjuncts into generators and filters.

Getting the code and running the tests

M6 builds directly on your M1–M5 code. Because the milestones are cumulative, cargo m6 runs every M5, M4, M3, M2, and M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M5 first, and keep working in the same clone with your completed evaluator and checker in place. Every program that uses a relation goes through your M5 checker before it runs, and the bodies of filters are ordinary expressions your M1–M4 evaluator runs.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1. That setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1 through M5. Then pick up the same loop, with the milestone number advanced: 

cargo m6                                    # run the Milestone-6 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m6 is short for cargo test --features m6, and runs the M6 tests and every earlier milestone's. To list the milestone-tagged holes at any time: 

grep -rn 'todo_m6!' src

The holes for constructors, match, ?, structs, and methods, along with check_guards in src/relations/check.rs, stay todo!s until their own milestones.

A suggested order: write Subst::unify first, since the engine calls it for every pairing of an atom and a fact. Then write the engine and the evaluator's arms. Many provided tests run whole programs without the static checks, so you can get the engine right before the checker knows anything about relations. The checker's arms and the rule checks can follow in either order.

Running a program

With --features m6, cargo run runs the rule checks and the type checker before main. deps.brg builds a dependency graph with an ordinary loop and asks the relation what it implies: 

$ cat deps.brg
relation needs : (String, String);
relation uses : (String, String);

rule uses(a, b) :- needs(a, b);
rule uses(a, c) :- needs(a, b) and uses(b, c);

fn main() {
    let edges = [("app", "ui"), ("ui", "gfx"), ("app", "net"), ("net", "io")];
    for e in edges { add needs(e.0, e.1); }
    println(solutions uses("app", ?m));
    println(uses("io", "app"));
    for uses(?m, "io") { println(m); }
}

$ cargo run -q --features m6 -- deps.brg
["gfx", "io", "net", "ui"]
false
app
net

In hops.brg a filter calls a function that recurses. The function always returns, but the purity check reads the call graph, never the arguments, so the program never starts. Not even start is printed, and the exit status is 1: 

$ cat hops.brg
relation link : (String, String);
relation near : (String, String);

fn hops(n: Int) -> Bool = if n <= 0 { true } else { hops(n - 1) };

rule near(a, b) :- link(a, b) and hops(2);

fn main() {
    println("start");
    add link("a", "b");
    println(solutions near(?a, ?b));
}

$ cargo run -q --features m6 -- hops.brg

A few examples

After deps.brg's four adds, these queries have these values:

solutions uses("app", ?m)                    ["gfx", "io", "net", "ui"]
solutions uses(?a, "gfx")                    ["app", "ui"]
solutions needs(?a, ?)                       ["app", "net", "ui"]
solutions uses("app", "io")                  [()]
uses(?m, "app")                              false
solutions uses(?m, ?m)                       []
{ clear needs; solutions uses(?a, ?b) }      []

Forms and rules that are rejected before the program runs, with the error and where it is reported (see the chapter for the declarations these assume):

add uses("app", ?m)                          HoleInAdd, at the whole form
solutions uses(1, ?m)                        Mismatch (expected String, found Int), at 1
{ let f = uses; f("a", "b") }                RelationNotAValue (uses), at uses
rule uses(a, c) :- needs(a, b);              Unbound (c), at the head
rule leaf(a) :- size(a, n + 1);              ArgumentNotATerm, at n + 1
rule leaf(a) :- size(a, n) and m > cap;      Unbound (m), at the filter
rule leaf(a) :- size(a, n) and note(a);      Impure, witness [note, println]
rule leaf(a) :- size(a, n) and n;            Mismatch (expected Bool, found Int)

The provided tests come in four kinds. Some call Subst::unify directly on terms and values. Some run a whole program with run_program, which skips the static checks, so the engine meets filters the checks would have refused. Some run check_rules alone on a loaded program, and some run the type checker on one. A rejection is tested by its RuleError or TyError variant and, where it matters, by its payload (the name in Unbound, the path in Impure), never by the text of its message. When cargo m6 is all green, your implementation is very likely correct.

How M6 is graded

M6 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M6 behavior (eight properties, 5 points each) and 40 on carried-over regression tests for the past milestones (M1 through M5), since M6 is cumulative. The carried-over 40 is divided evenly among M1, M2, M3, M4, and M5 (8 points each), then across each milestone's properties, so a regression in any one of them is weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface, separate from the provided tests you run locally with cargo m6.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting. The starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. The autograder builds your files against its own copies of the frozen files, so make sure your code builds with those files unmodified.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: you must pass all of them, the M6 tests and the carried-over M5–M1 tests, before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative, roughly −20 and up to −40, at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first. Code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M6 is cumulative, a change that breaks an earlier milestone's test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property, a single rule your implementation must obey. Eight properties cover the new M6 behavior:

  • Unification: Subst::unify matches a pattern against a fact. A variable's first sighting binds it, a repeat must agree, a constant must equal the fact's value, and the lengths must match. A success extends the substitution, and neither a success nor a failure changes the original.
  • Queries: a query computes the least fixpoint of the rules over the facts, including recursive and mutually recursive rules and cyclic data. A hole-free query tests membership, solutions collects the named holes' values, and a query with holes in boolean position tests existence.
  • Relational for: a for over a query walks every solution in canonical order, binding its holes, so the body's effects accumulate across the matches.
  • Add and clear: add inserts a ground fact and clear removes one relation's facts, and later queries see the change, derived facts included. A fact with a hole is HoleInAdd.
  • Filters: a rule's filters narrow what it derives, in any position in the body, and a filter may read a top-level constant or call a pure function.
  • Rule structure: the static checks accept a well-formed rule, and reject a head that names no declared relation (NotARelation), a generator of the wrong arity (Arity), an argument that is not a term (ArgumentNotATerm), and a variable no generator binds (Unbound).
  • Rule purity: a filter that reaches an effect, directly or several calls away, is Impure with the right witness path. One that reaches a recursive function is Recursive, even when the recursion would stop, and one that reaches a function with a function-typed parameter is HigherOrder. Reading a relation from a filter is an effect.
  • Rule typing and the stuck state: a rule's terms are typed by their columns and a filter must be Bool. In a program run without the checks, a query, add, or clear reached during a fixpoint is a clean QueryInFilter, not a loop.

A property is all-or-nothing. It is checked by several cases, some visible and some hidden, and you earn its points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it. If it is a hidden one, you see a hint about what kind of case it is, but not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M6 on its own. That is fine. What I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote. Point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. solutions uses("app", ?m) in deps.brg (from above) is ["gfx", "io", "net", "ui"]. Using your engine, explain how uses("app", "io") gets derived: which round of your fixpoint first produces it, which rule fires, and what substitution your unify builds for each generator. How does your loop decide that it has reached the fixpoint? Why does the same loop terminate on a graph with a cycle, such as an extra fact needs("io", "app")?
  2. solutions needs(?a, ?) is ["app", "net", "ui"], three values from four facts. Point at where your engine cuts each match down to the named holes, removes duplicates, and sorts. Why must the anonymous hole be cut away before duplicates are removed? Why does each ? need a fresh variable name, and what would solutions needs(?, ?) return if your engine gave every anonymous hole the same name?
  3. rule leaf(a) :- size(a, n) and m > cap; is Unbound (m), but n > cap is accepted, and so is { let m = n * 2; m > cap }. Walk through your check_range_restriction on all three: which names free_vars gives for each filter, and which test lets each name through or rejects it. Why does the language insist that every head variable be bound by a generator? What would a rule like rule uses(a, c) :- needs(a, b); have to mean if it were allowed?
  4. hops.brg (above) is rejected as Recursive, although hops(2) always returns. Show where your check_pure finds the cycle and why it reports Recursive rather than Impure. Then, for the filter note(a), where note calls println, explain how your code builds the witness [note, println], and how it computes the impure set I as a least fixpoint over the program's functions.
  5. The purity check already rejects every filter that queries, yet your engine also keeps a materializing flag. Point at where you set and clear it in solutions, and explain why it must be cleared before an error from the rounds is returned. Using the textbook's p/q/r program from the chapter's design problems, describe what your engine would do, run without the checks, if the flag were not there.

How you implemented it

  • Walk through your solutions from start to finish: how you turn the query's arguments into terms, how you compute the fixpoint (the starting facts, one round, and firing one rule through its generators and filters), and how you build the answer. Say how your Subst::unify handles a variable already bound, and how it leaves the original substitution unchanged on failure. Naming the provided tools you used (RelationDb, Subst, compare, type_of, env.root(), Control) is encouraged.
  • Describe how your check_pure decides what a call reaches: how you tell a local from a top-level function or a native, how you treat map, filter, and fold callbacks, and which of the provided helpers (subexprs, free_vars, bound_names) you used and where.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made. If you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative. If your description does not match the code you submitted (it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission), you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester. M6 spans more files than any milestone so far, so make sure you can explain each of them.
