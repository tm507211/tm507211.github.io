Milestone M4 Functions, Closures, and Static Scope

CSCI 305: Concepts of Programming Languages

In this milestone functions become values, and your interpreter runs its first whole Bridger program. You put two forms into the evaluator: a lambda, which evaluates to a closure holding its parameters, its body, and the environment it was written in, and a call, which runs that body in the captured environment extended with the arguments. Every program starts by calling main, so once your Call arm works, cargo run can run a .brg file from start to finish.

What to build the specification

Full specification: Textbook — Milestone M4: functions, closures, and static scope  |  Previous milestone: Milestone M3: control flow and mutation

Read the Milestone M4 chapter before you start — it is the authoritative specification, and it points to the “Building it” sections of First-class functions and Evaluating function calls, which walk through each arm premise by premise. In short, you implement the two milestone-tagged holes in eval_expr: 

// src/interp/eval.rs — the two M4 arms
Expr::Lambda(..) => todo_m4!("E-Lam"),
Expr::Call(..)   => todo_m4!("E-App (dispatch Bridger vs. Native closure)"),

Two arms is a smaller count than M3's seven, but Call carries a lot: it is where a closure meets its arguments, where the call depth is counted, where the return channel you built at M3 is finally caught, and where the prelude's native functions are dispatched. Lambda is short:

  • Lambda builds a Closure::Bridger from the parameter names, a copy of the body, and the env the arm was given, and returns it wrapped as a Value::Closure. It evaluates nothing — the body runs only when the closure is called, so a lambda whose body would be stuck is still a value. A parameter's type annotation is for the type checker at M5 and is dropped here.
  • Call evaluates the operator first. If it is not a Value::Closure, the call is stuck with NotAFunction (its found filled in by type_of) before any argument is evaluated. Otherwise it evaluates the arguments from left to right and dispatches on the closure:
    • a Closure::Native hands the argument values to the provided eval_prelude;
    • a Closure::Bridger checks the argument count against the parameter count (ArityMismatch, with expected the parameter count and found the argument count), extends the closure's environment — not the caller's — with one binding per parameter, and evaluates the body there, between enter_call and leave_call.
    Both errors carry the span of the whole call.

Two details decide whether the Bridger case is right. First, a return stops at its call: a body that ends in Err(Control::Return(v)) makes v the call's value, while a Control::Raise passes through the call unchanged. Second, the frame count must balance: leave_call runs after the body whatever the body's outcome. Putting ? on the body's result before leave_call would leave on exactly the Return and Raise paths without decrementing the count — and, for Return, without catching it. Take the body's result as a value, call leave_call, and only then decide what the result means.

Everything around those two arms is provided. Env::extend, enter_call (which refuses past 100 000 nested calls with StackOverflow), leave_call, eval_prelude, type_of, and the two new RuntimeError variants are ready to use. So is the driver, eval_program: it binds every prelude function and every top-level fn into the program's root environment, initializes the global lets in dependency order (reporting a cycle as InitializationCycle), and then evaluates a call main() — through your Call arm. The higher-order natives map, filter, and fold also call the function they are handed by evaluating an ordinary call expression through your arm, so map(xs, |x| x * 10) runs your Call once per element, with the same arity check and the same return handling as a call written in the program.

Your earlier arms are graded again here

Functions are the first values that cannot be compared, and whole programs are the first place where the order of side effects is easy to observe. One of the M4 properties, evaluation order (below), checks behavior that lives in arms you wrote at M1 and M3, so look back at them before you submit:

  • Left to right, everywhere. Binary operators (arithmetic, comparisons, ==), tuples, lists, and calls evaluate their operands left to right, so a program that prints inside each operand prints in source order.
  • Assignment evaluates its target first. In e1 := e2, the target e1 runs before e2, and a target that is not a reference is stuck before e2 runs.
  • == on a function is stuck. At M1 there were no functions, so your equality arm may simply compare the two values. Now f == g — or == on a tuple or list that contains a function anywhere inside — must be stuck with RuntimeError::NotComparable. The provided uncomparable(v) in src/interp/value.rs returns the type of the first function it finds inside v, or None; it is what you need for found. References, by contrast, compare by identity: an alias of a reference is == to it.

Getting the code and running the tests

M4 builds directly on your M3, M2, and M1 code. Because the milestones are cumulative, cargo m4 runs every M3, M2, and M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M3 first — keep working in the same clone with your completed M1–M3 arms in place. Every program begins with a call, and calls run the bodies your earlier arms evaluate, so without them the whole-program tests cannot pass no matter what you write here.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1 — that setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1 through M3. Then pick up the same loop, with the milestone number advanced: 

cargo m4                                    # run the Milestone-4 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m4 is short for cargo test --features m4, and runs the M4 tests and every M3, M2, and M1 test. To list the two milestone-tagged holes at any time: 

grep -rn 'todo_m4!' src

Running a program

New at M4: the interpreter runs programs from a file. cargo run builds the bridger binary and passes it the arguments after --. Standard input is the program's input, so a program that calls read_int or read_line can be fed with a pipe: 

$ cat fact.brg
fn fact(n: Int) -> Int = if n == 0 { 1 } else { n * fact(n - 1) };
fn main() { println(fact(5)); }

$ cargo run -q --features m4 -- fact.brg
120

$ echo "3 4" | cargo run -q --features m4 -- sum.brg
7

A program that gets stuck stops with the error's message and the source underlined at the span your arm attached, and exits with status 1. A wrong span underlines the wrong code, which is why the tests check the span of every error along with its variant. Writing a few small programs of your own and running them is the fastest way to see what your closures are doing.

A few examples

Expressions and the values your evaluator should produce:

(|x| x + 1)(4)                                 ⇒ 5
(|| 7)()                                       ⇒ 7    (zero parameters)
(|f| f(3))(|x| x * 2)                          ⇒ 6    (a function as an argument)
(|x| |y| x * 10 + y)(4)(2)                     ⇒ 42   (a function returned, then called)

{ let y = 1; let f = |x| x + y; let y = 100; f(0) }
                                               ⇒ 1    (f keeps the y it captured)

(|| { return 7; 9 })()                         ⇒ 7    (the call catches the return)
map([1, 2, 3], |x| x * 10)                     ⇒ [10, 20, 30]
fold([1, 2, 3], 0, |a, x| a * 10 + x)          ⇒ 123  (fold goes from the left)

Expressions and programs that are stuck — no value, and the run reports a runtime error:

5()                        ⇒ stuck   (NotAFunction: found Int)
(|x, y| 0)(1)              ⇒ stuck   (ArityMismatch: expected 2, found 1)
(|x| x) == (|x| x)         ⇒ stuck   (NotComparable: functions have no equality)

let a = a + 1;             ⇒ stuck   (InitializationCycle: a global that reads itself)

fn sum_to(n: Int) -> Int = if n == 0 { 0 } else { n + sum_to(n - 1) };
fn main() { println(sum_to(1000000)); }
                           ⇒ stuck   (StackOverflow at the call sum_to(n - 1))

The provided tests come in two kinds. The first builds an Expr by hand, as the earlier milestones' tests do, with the new builders lambda and call. The second loads a whole program from source and runs it through eval_program: run_program returns the value main produced and the text it printed, run_stuck returns the error it got stuck on, and run_with_input / run_stuck_with_input do the same with text on standard input. When cargo m4 is all green, your evaluator is very likely correct.

How M4 is graded

M4 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M4 behavior — seven properties, about 5.7 points each — and 40 on carried-over regression tests for the past milestones (M1, M2, and M3), since M4 is cumulative and your evaluator must keep the expression, binding, and state fragments working. The carried-over 40 is divided evenly among M1, M2, and M3 (about 13.3 points each), then across each milestone's properties — so a regression in any one of them is weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface — separate from the provided tests you run locally with cargo m4.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting; the starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. The autograder builds your files against its own copies of the frozen files, so make sure your code builds with those files unmodified.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: passing all of them — the M4 tests and the carried-over M3, M2, and M1 tests — is required before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative — roughly −20, and up to −40 — at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first: code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M4 is cumulative, a change that breaks an M3, M2, or M1 test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property — a single rule your evaluator must obey. Seven properties cover the new M4 behavior:

  • Lambdas and application — a lambda closes over its definition environment (static scope); functions are first-class values that can be passed and returned; the wrong number of arguments is ArityMismatch, calling a non-function is NotAFunction, and a return ends only the innermost call.
  • Programs — a whole program runs main and yields its value; print/println reach the output; top-level functions may be declared in any order, call one another, recurse, and be passed as values.
  • Globals — global lets are visible to main and to each other, each initialized once, in dependency order (through function bodies too); a cycle among them is InitializationCycle.
  • Prelude natives — native functions run through the same call path, including map, filter, and fold, which iterate rather than recurse, so a long list costs no call depth.
  • Readers — the read_* family consumes whitespace-separated tokens and whole lines from the input; the _opt readers return None on a bad token or at end of input, while a plain reader is stuck with an InputError.
  • Runtime limits — runaway recursion is a clean StackOverflow (keeping whatever was already printed), an over-large range is RangeTooLarge, and an expression nested too deeply is TooDeep — each a stuck state, never a crash of the interpreter itself.
  • Evaluation order — operands are evaluated left to right, threading their effects; references compare by identity; an assignment target that is not a reference is stuck before its right-hand side runs; == on (or printing of) a function is stuck. See the box above: much of this lives in your earlier arms.

Several of these properties exercise provided code — the driver, the readers, the range bound — but none of them can pass until your Call arm works, since every program starts with a call, and a Call arm that does not balance enter_call and leave_call will fail the runtime-limits property in ways that are hard to see in a small test. The carried-over 40 re-checks the expression rules from M1, the binding rules from M2, and the state and control rules from M3, so a regression in any of them costs points here.

A property is all-or-nothing: it is checked by several cases — some visible, some hidden — and you earn its points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it; if it is a hidden one, you see a hint about what kind of case it is, but not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M4 on its own. That is fine — what I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote — point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. In { let y = 1; let f = |x| x + y; let y = 100; f(0) } the result is 1, not 101. Walk through what your Expr::Lambda arm stores in the closure, which environment your Expr::Call arm extends with the parameter x, and why that gives 1. What would the result be if your Call arm extended the caller's environment instead, and what is the name for the scoping discipline your interpreter implements?
  2. Your Call arm evaluates the operator, the arguments, and checks the arity, in some order. Say the order your code uses, and use it to explain why 5(print(1)) is stuck with NotAFunction without printing anything, while (|x, y| 0)(print(1)) prints 1 and then is stuck with ArityMismatch. Which span do both errors carry?
  3. At M3, nothing you wrote caught Control::Return. Now your Call arm does. Show how your arm turns Err(Control::Return(v)) into the call's value while letting a Control::Raise through, and explain why you must not apply ? to the body's result before calling leave_call. What two things would go wrong if you did?
  4. fold(range(0, 1000000), 0, |a, x| a + x) runs to completion, while the recursive sum_to(1000000) is a StackOverflow, even though both call a Bridger function a million times. Explain the difference in terms of how many calls are in progress at once and what your enter_call/leave_call pair counts. How does fold's callback reach your Call arm at all, given that fold is a native?
  5. A top-level fn fact can call itself, but let fact = |n| if n == 0 { 1 } else { n * fact(n - 1) }; inside main is stuck with an unbound variable. Using what your Lambda arm captures and what the provided driver does for top-level functions, explain why the two behave differently.

How you implemented it

  • Walk through your Expr::Call arm from start to finish: how you destructure it, how you evaluate the operator and arguments, how you dispatch on Closure::Bridger versus Closure::Native, how you build the body's environment, and how you handle the body's result. Then describe your Expr::Lambda arm in a sentence or two. Naming the provided tools you used (self.eval_expr, env.extend, enter_call, leave_call, eval_prelude, type_of, RuntimeError, .into()/?) is encouraged.
  • Say what, if anything, you changed in your M1–M3 arms for this milestone — for example, to make == on a function stuck, or to fix an evaluation-order problem a whole-program test exposed — and why.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made — and if you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative: if your description does not actually match the code you submitted — it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission — you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester, so keep building the habit while the milestones are still small.

Submitting

First write your Description.md at the root of the repository. Then, from inside the project folder, check the code: 

cd bridger-interpreter                       # the project root

cargo m4                                     # all Milestone-4 tests pass (M3, M2, and M1 too)?
cargo fmt                                    # format your code
cargo clippy --all-targets -- -D warnings    # lint — fix any warnings

Then package src/ and the root .md files into a .zip. Run the command for your system from the project root.

macOS / Linux (Terminal):

zip -r ../m4-submission.zip src *.md

Windows (PowerShell):

Compress-Archive -Path src, *.md -DestinationPath ..\m4-submission.zip -Force

Either one writes m4-submission.zip in the folder just above the project, with src/ and Description.md at the top of the archive. The autograder replaces Cargo.toml, tests/, and the frozen src/ files with its own copies, so any changes you make to them are discarded. Only src/interp/eval.rs is graded as your code, so any helper functions you write must live in that file.

Upload m4-submission.zip to the Milestone M4 assignment on Gradescope (linked from Canvas). Some tests are visible, so you will get results back shortly and can resubmit before the deadline; other tests are hidden, so passing every visible test does not guarantee full credit.

No zip command on Linux? Install it (on Debian/Ubuntu, sudo apt install zip). Alternatively, in Finder (macOS) or File Explorer (Windows), select the src folder and the .md files inside the project folder (not the project folder itself) and choose Compress / Send to → Compressed (zipped) folder.
