Milestone M3 Control Flow and Mutation

CSCI 305: Concepts of Programming Languages

In this milestone your evaluator stops merely computing a value and starts doing things: it chooses a branch, repeats an action, changes state in a store, and carries a value out past the code around it. You put seven forms into the interpreter — if, while, for, return, assignment :=, and the two reference operators ref and deref — so that each either evaluates to a value, changes the store and yields (), leaves on the return channel, or reports a well-formed runtime error.

What to build the specification

Full specification: Textbook — Milestone M3: control flow and mutation  |  Previous milestone: Milestone M2: environments and binding

Read the Milestone M3 chapter before you start — it is the authoritative specification, with the exact rule for each form, the case that leaves each one stuck, and the full description of the store. In short, you implement the five milestone-tagged holes in eval_expr: 

// src/interp/eval.rs — the five M3 arms
Expr::If(..)     => todo_m3!("E-If"),
Expr::While(..)  => todo_m3!("E-While"),
Expr::For(..)    => todo_m3!("E-For"),
Expr::Assign(..) => todo_m3!("E-Assign"),
Expr::Return(..) => todo_m3!("E-Return"),

Two more forms are not on that list. ref and deref are UnOp variants, so they are two new cases of the match inside the Expr::Unary arm you already wrote at M1 for -e and not e — the stub that was labelled “ref & deref join at M3”. grep -rn 'todo_m3!' src lists only the five above, so it under-counts M3 by exactly those two: seven forms in all, five their own Expr variant and two cases of an existing one.

What is new on the provided side is the store. A Store now lives on the interpreter as self.store, with three operations — alloc(v) makes a fresh cell and returns its Loc, read(loc) returns the value in a cell, and write(loc, v) overwrites one — and a value Value::Ref(loc) carries a cell's location. It is provided and frozen; the mutation forms are exactly its three operations:

  • ref e evaluates e to v, calls self.store.alloc(v), and returns Value::Ref(loc).
  • deref e evaluates e to a Value::Ref(loc) and returns self.store.read(loc).
  • e1 := e2 evaluates e1 to a Value::Ref(loc), then e2 to a value, calls self.store.write(loc, v), and returns Value::Unit.

The control forms match the value they branch on. if evaluates only the branch its condition selects, and an else-less if whose condition is false yields (). while is a host loop that re-tests its condition and runs the body — whose value is taken with ? and dropped — while the condition is true, yielding (). for x in e { … } evaluates e to a list and runs the body once per element in a fresh env.extend(x, item), discarding each turn's value and yielding (). And return e leaves on a channel of its own, Err(Control::Return(v)) — the second variant of Control, beside the Control::Raise an error rides — travelling straight out through the loops and blocks in its way. A non-Bool condition (if, while), a non-list iterable (for), and a deref or := of a non-reference are the new stuck cases; the last two are a RuntimeError::TypeError built with Ty::reference(..).

Getting the code and running the tests

M3 builds directly on your M2 and M1 code. Because the milestones are cumulative, cargo m3 runs every M2 and M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M2 first — keep working in the same clone with your completed M1 and M2 arms in place. If you have not done them yet, do them before starting M3; without the earlier arms, the carried-over tests cannot pass no matter what you write here.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1 — that setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1 and M2. Then pick up the same loop, with the milestone number advanced: 

cargo m3                                    # run the Milestone-3 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m3 is short for cargo test --features m3. Milestones are cumulative, so cargo m3 runs the M3 tests and every M2 and M1 test — the earlier fragments keep passing as you grow the evaluator. To list the five milestone-tagged holes at any time: 

grep -rn 'todo_m3!' src

The five holes turn up in src/interp/eval.rs. Remember that this grep under-counts: ref and deref are the two new cases you add inside the Expr::Unary arm, not todo_m3! holes of their own. Every other Expr variant is a hole tagged for a later milestone, so the crate still compiles with these unwritten.

A few examples

Programs and the values your evaluator should produce:

if true { 1 } else { 2 }                       ⇒ 1
if false { 9 }                                 ⇒ ()   (else-less, condition false)
deref (ref 5)                                  ⇒ 5

let r = ref 0; r := 7; deref r                 ⇒ 7    (write, then read it back)
let a = ref 1; let b = a; b := 9; deref a       ⇒ 9    (b and a share the cell)

let i = ref 0;
while deref i < 3 { i := deref i + 1 }; deref i  ⇒ 3

let acc = ref 0;
for x in [1, 2, 3] { acc := deref acc + x }; deref acc  ⇒ 6

Programs that leave through the return channel rather than with a value:

return 5                                        → returns 5
while true { return 7 }                         → returns 7   (the loop is abandoned)

Expressions that are stuck — no value, and the run reports a runtime error:

if 3 { 1 } else { 2 }     ⇒ stuck   (condition is not a Bool)
while 1 { }               ⇒ stuck   (condition is not a Bool)
for x in 5 { }            ⇒ stuck   (iterable is not a list)
deref 5                   ⇒ stuck   (deref of a non-reference — TypeError)
5 := 6                    ⇒ stuck   (assign to a non-reference — TypeError)

The provided tests build an Expr by hand and check the resulting Value, the error a stuck test blames (its variant and span), or — for a return — the value it carries out. The builders if_, if_else, while_, for_, assign, and return_ join the earlier ones; ref and deref are written as unary(UnOp::Ref, …) and unary(UnOp::Deref, …); and the assertion returned unwraps the return channel where value_of and stuck unwrap a value or an error. When cargo m3 is all green, your evaluator is very likely correct.

How M3 is graded

M3 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M3 behavior — five properties, 8 points each — and 40 on carried-over regression tests for the past milestones (M1 and M2), since M3 is cumulative and your evaluator must keep the expression and binding fragments working. The carried-over 40 is divided evenly between M1 and M2 (20 points each), then across each milestone's properties — so an M1 regression and an M2 regression are each weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface — separate from the provided tests you run locally with cargo m3.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting; the starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. Make sure a fresh clone of exactly what you submit runs cargo build.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: passing all of them — the M3 tests and the carried-over M2 and M1 tests — is required before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative — roughly −20, and up to −40 — at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first: code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M3 is cumulative, a change that breaks an M2 or M1 test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property — a single rule your evaluator must obey. Five properties cover the new M3 behavior, one for each area of the milestone: conditionals (an if evaluates only the branch its condition selects, and an else-less if with a false condition yields ()), references (ref, deref, and := act on the store, and a deref or := of a non-reference is stuck with a TypeError), while (the host loop discards its body's value and stops with (); a non-Bool condition is stuck), for (a fresh binding of the loop variable per list element, yielding (); a non-list iterable is stuck), and return (a value leaves on its own channel, abandoning the loop or block around it). The carried-over 40 re-checks the expression rules from M1 and the binding rules from M2, so a regression in either costs points here. A property is all-or-nothing: it is checked by several cases — some visible, some hidden — and you earn its 8 points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it; if it is a hidden one, you see only the property's rule, not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M3 on its own. That is fine — what I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote — point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. Your eval_expr returns Result<Value, Control>, and a return travels as Err(Control::Return(v)) — the same Err side an error uses. In your Expr::Return arm, how do you build that value, and why carry a return as an Err rather than an ordinary Value? How do the two channels — Control::Return and Control::Raise — stay distinct, and what catches Control::Return at this milestone?
  2. Walk through your assignment arm e1 := e2: in what order do you evaluate the two sides, which one must be a Value::Ref(loc), which self.store operation you call, and what value the form returns. For the stuck case — assigning to something that is not a reference — name the RuntimeError variant you build and how you form the expected type.
  3. The Mutation chapter's rules thread a store in and a store out, yet your interpreter keeps one self.store and mutates it in place. Explain, using let a = ref 1; let b = a; b := 9; deref a ⇒ 9, why aliasing works: what ref allocated, what b = a copied, and why writing through b is visible through a.
  4. Your while arm is a host loop and your for arm walks a list. For each, say what value the body produces and what you do with it, what the loop as a whole evaluates to, and — for for — how env.extend(x, item) gives the loop variable a fresh binding each turn. Then explain how a return inside either body escapes the loop, referring to the ? in your arm.
  5. In if 3 { 1 } else { 2 } the condition is not a Bool, and the program is stuck. Walk through how your Expr::If arm produces that, and contrast it with if false { 9 }, which is not stuck. Which branches does your arm evaluate in each case, and what does an else-less if return when its condition is false?

How you implemented it

  • Walk through one of your loop arms (Expr::While or Expr::For): how you destructure it, how you re-evaluate the condition or iterate the list, where you take the body's value with ? and drop it, and how you produce Value::Unit. Then describe the two new cases you added inside Expr::Unary for UnOp::Ref and UnOp::Deref. Naming the provided tools you used (self.eval_expr, self.store.alloc/read/write, env.extend, RuntimeError, Ty::reference, .into()/?) is encouraged.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made — and if you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative: if your description does not actually match the code you submitted — it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission — you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester, so keep building the habit while the milestones are still small.

Submitting

First write your Description.md at the root of the repository. Then, from inside the project folder, check the code and package the entire project into a .zip: 

cd bridger-interpreter                       # the project root

cargo m3                                     # all Milestone-3 tests pass (M2 and M1 too)?
cargo fmt                                     # format your code
cargo clippy --all-targets -- -D warnings    # lint — fix any warnings

zip -r ../m3-submission.zip . -x '.git/*' 'target/*'

That writes m3-submission.zip in the folder just above the project. The -x flags leave out the .git/ history and the target/ build directory, which you do not need to submit. Submit the whole project, not just eval.rs.

Then upload m3-submission.zip to the Milestone M3 assignment on Gradescope (linked from Canvas). Some tests are visible, so you will get results back shortly and can resubmit before the deadline; other tests are hidden, so passing every visible test does not guarantee full credit.

No zip command? The simplest route on any system is the GUI: select the project folder in Finder (macOS) or File Explorer (Windows) and choose Compress / Send to → Compressed (zipped) folder. Just make sure the files sit at the top of the archive (with src/ and Cargo.toml at its root), not nested inside an extra folder. If you would rather have the command line: macOS and most Linux systems already include zip (on Debian/Ubuntu, install it with sudo apt install zip); on Windows, install a zip tool such as 7-Zip, or use the built-in PowerShell command Compress-Archive.
