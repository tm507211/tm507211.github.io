Milestone M1 The Expression Evaluator

CSCI 305: Concepts of Programming Languages

In this milestone you complete the evaluator for the language's expression fragment: literals, arithmetic and boolean operators, comparisons, string and list operations, tuples, and projection. You fill in six match arms of one method, eval_expr, so that every expression either evaluates to a value or reports a well-formed runtime error.

What to build the specification

Full specification: Textbook — Milestone M1: the expression evaluator  |  Warm-up: Milestone M0: Rust warm-up

Read the Milestone M1 chapter before you start — it is the authoritative specification, including the exact rule for each expression form and the case in which it is stuck. In short, you implement the six milestone-tagged holes in eval_expr: 

// src/interp/eval.rs — the six M1 arms
Expr::Lit(..)    => todo_m1!("E-Lit"),
Expr::Unary(..)  => todo_m1!("E-Neg / E-Not"),
Expr::Binary(..) => todo_m1!("E-Arith/Ord/Eq, E-And/Or, E-Concat, E-Cons"),
Expr::Tuple(..)  => todo_m1!("E-Tuple"),
Expr::List(..)   => todo_m1!("E-List"),
Expr::Proj(..)   => todo_m1!("E-Proj"),

Everything else in the interpreter — the parser, the value and error types, the environment — is provided and frozen. Your work is the meaning of these six forms. Keep three contracts in mind: an arm returns Ok(v) on success and Err(Control::Raise(..)) when stuck (carrying the RuntimeError and the span it blames); and/or short-circuit; and integer arithmetic wraps modulo 264.

Getting the code and running the tests

Install the Rust toolchain from rustup (it brings cargo, the formatter, and the linter), then confirm it runs: 

cargo --version

Get the starter repository, bridger-interpreter. If you have Git installed, clone it and build it once — a fresh clone builds green, because every unfilled hole still compiles: 

git clone https://github.com/chaluli/bridger-interpreter.git
cd bridger-interpreter
cargo build

Never used Git? You can instead download the code as a .zip: on the repository page, click the green Code button, choose Download ZIP, and unzip it. Then cd into the unzipped bridger-interpreter folder and run cargo build. (Cloning with Git is worth learning — it makes it easy to save your progress and pull any updates — but either way works.)

The loop you repeat as you work:

cargo m1                                    # run the Milestone-1 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint
cargo doc --no-deps --open                  # browse the provided types

cargo m1 is short for cargo test --features m1. Milestones are cumulative, so cargo m2 later runs both M2 and M1 tests. To list exactly what M1 asks of you at any time: 

grep -rn 'todo_m1!' src

A few examples

Expressions and the values your evaluator should produce:

1 + 2 * 3          ⇒ 7
-(3 - 5)           ⇒ 2
7 / 2              ⇒ 3          (integer division)
2 < 3              ⇒ true
(1, 2) == (1, 2)   ⇒ true       (structural)
"ab" ++ "cd"       ⇒ "abcd"
[1, 2] ++ [3]      ⇒ [1, 2, 3]
0 :: [1, 2]        ⇒ [0, 1, 2]
(10, 20).1         ⇒ 20
false and (1 / 0)  ⇒ false      (right operand never evaluated)

Expressions that are stuck — no value, and the run reports a runtime error:

1 + true      ⇒ stuck   (an Int operator met a Bool)
5 / 0         ⇒ stuck   (division by zero)
"a" ++ [1]    ⇒ stuck   (++ needs both strings or both lists)
(1, 2).5      ⇒ stuck   (projection past the end of a 2-tuple)

The provided tests build an Expr by hand and check either the resulting Value or, for a stuck expression, the error's variant, its expected/found types, and the span it blames. When cargo m1 is all green, your evaluator is very likely correct.

How M1 is graded

M1 is worth 100 points:

ItemPoints
Auto-graded tests 80, split evenly across 10 properties (8 points each). These are held-back tests, run on Gradescope against the public interface — separate from the provided tests you run locally with cargo m1.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting; the starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. Make sure a fresh clone of exactly what you submit runs cargo build.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: passing all of them is required before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative — roughly −20, and up to −40 — at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first: code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property — a single rule your evaluator must obey, such as “and and or short-circuit” or “division by zero is stuck with a DivByZero error at the operator.” A property is all-or-nothing: it is checked by several cases — some visible, some hidden — and you earn its 8 points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it; if it is a hidden one, you see only the property’s rule, not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M1 on its own. That is fine — what I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote — point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. What does it mean for an expression to be stuck, as opposed to evaluating to a value? Explain in terms of your method's return type: what does eval_expr return in each case (the Ok/Err shape), and for a stuck expression, which RuntimeError variant and expected/found types does it carry?
  2. Walk through how the ? operator behaves in one of your arms: when you write self.eval_expr(sub, env)?, what happens if that subexpression is stuck, and what does it save you from writing by hand? What would the same arm look like without ??
  3. In your and/or implementation, how do you avoid evaluating the right operand once the left operand has already decided the answer? Point to the lines that do it, name the Rust control flow you used, and say why you could not evaluate both operands first and then combine them.
  4. Why does your integer arithmetic wrap rather than overflow-panic, and which specific operations (or method calls) in your code produce that behavior?
  5. When your code reports a stuck expression, which node's span does the error carry, and how does your code get that span? Why is blaming that node more useful to a user than blaming, say, the whole expression?

How you implemented it

  • Walk through your Expr::Binary arm: how do you evaluate the operands, dispatch on the BinOp, build the result value, and report a type error? Naming the provided tools you used (self.eval_expr, type_of, the wrapping operations, RuntimeError, .into()/?) is encouraged.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made — and if you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative: if your description does not actually match the code you submitted — it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission — you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester, so build the habit now, while M1 is small.

Submitting

First write your Description.md at the root of the repository. Then, from inside the project folder, check the code and package the entire project into a .zip: 

cd bridger-interpreter                       # the project root

cargo m1                                     # all Milestone-1 tests pass?
cargo fmt                                    # format your code
cargo clippy --all-targets -- -D warnings    # lint — fix any warnings

zip -r ../m1-submission.zip . -x '.git/*' 'target/*'

That writes m1-submission.zip in the folder just above the project. The -x flags leave out the .git/ history and the target/ build directory, which you do not need to submit. Submitting the whole project (rather than just eval.rs) keeps things uniform with later milestones, which touch several source files.

Then upload m1-submission.zip to the Milestone M1 assignment on Gradescope (linked from Canvas). Some tests are visible, so you will get results back shortly and can resubmit before the deadline; other tests are hidden, so passing every visible test does not guarantee full credit.

No zip command? The simplest route on any system is the GUI: select the project folder in Finder (macOS) or File Explorer (Windows) and choose Compress / Send to → Compressed (zipped) folder. Just make sure the files sit at the top of the archive (with src/ and Cargo.toml at its root), not nested inside an extra folder. If you would rather have the command line: macOS and most Linux systems already include zip (on Debian/Ubuntu, install it with sudo apt install zip); on Windows, install a zip tool such as 7-Zip, or use the built-in PowerShell command Compress-Archive.
