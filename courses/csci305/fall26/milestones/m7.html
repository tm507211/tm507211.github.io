Milestone M7 Algebraic Data Types

CSCI 305: Concepts of Programming Languages

In this milestone Bridger gets its own data. You build constructor applications, match with its patterns and guards, and the ? operator, in both the evaluator and the type checker. The checker also proves that every match covers its scrutinee's type, and the rule checks extend to guards, which must be pure. With this milestone the prelude's Option, Result, and Ordering constructors come to life.

What to build the specification

Full specification: Textbook — Milestone M7: algebraic data types and pattern matching  |  Previous milestone: Milestone M6: relations

Read the Milestone M7 chapter before you start. It is the authoritative specification. Its two tables, one for the forms and one for the patterns, are the checklist your code is measured against. The rules themselves are in the language reference appendix (under constructors and pattern matching, control flow, and purity and effects). The algorithms are in the Part VIII chapters: Sum and product types, Pattern matching, and Exhaustiveness checking. The work is in three files you have already edited: 

// src/interp/eval.rs
Expr::Ctor(..) => todo_m7!("E-Ctor"),
Expr::Match(..) => todo_m7!("E-Match"),
Expr::Try(..) => todo_m7!("E-Try (`?`: match + return)"),

// src/types/check.rs
Expr::Ctor(..) => todo_m7!("T-Con"),
Expr::Match(..) => todo_m7!("T-Match (patterns, then exhaustiveness)"),
Expr::Try(..) => todo_m7!("T-Try"),
fn is_exhaustive(&self, arms: &[Arm], scrut_ty: &Ty) -> bool   // pasted in, see below
fn normalize(&self, p: &Pattern) -> Pat
fn signature(&self, ty: &Ty) -> Option<Signature>

// src/relations/check.rs
pub fn check_guards(program: &Program) -> Result<(), RuleError>

Two changes have no todo_m7! marker. The checker's Lambda arm reports a ? that a lambda's body cannot carry as TryInLambda. And your M6 purity judgment must now handle constructor applications, match, and ?, which no M6 program could reach. The chapter spells out the contracts the tests hold each file to. These are the ones that most often cause trouble:

  • A pattern that does not fit is not an error. The matcher's failure sends the evaluator to the next arm. Only after the last arm fails is the result NonExhaustiveMatch, at the match. A guard that is not a Bool is a TypeError at the guard.
  • Keep list tails shared. A :: or ...rest pattern binds the tail it was given. Rebuilding the tail makes every recursion over a list quadratic.
  • Ctor resolves its name first, and counts its arguments last. The evaluator decides what the name means before it runs the arguments, and reports ArityMismatch only after running them. The checker makes its arity report before it checks any argument.
  • Disagreement before gaps. The checker types every arm before it asks whether the arms are exhaustive, so a body of the wrong type is a Mismatch even when the match also has a gap. A guarded arm contributes nothing to coverage, since its guard may fail.
  • ? is a match and a return. On a None or an Err, raise the same Control::Return your return arm uses. In the checker, the operand's carrier must match the enclosing function's return type, and a Result's two error types must agree.
  • Guards allow recursion. check_guards reuses your M6 purity judgment, except that a guard may reach a recursive function. It reports the first offender in source order, and the order of decls is not the order of the file.

Everything outside the holes is provided, including Value::Ctor, Value::List and its uncons, Pattern::binders, and the driver that runs the guard checks, the rule checks, and the type checker before main. Struct values do not exist until M8, but struct patterns are part of the matcher, the checker, and exhaustiveness now. The chapter lists the provided runtime the M7 arms use.

First: paste in the exhaustiveness module

The starter leaves out the usefulness test behind exhaustiveness checking. The chapter's exhaustiveness section prints it in two parts. Copy both, unchanged:

  • The pub mod exhaustive module goes at the end of src/types/check.rs. Add use exhaustive::{Con, Pat, Signature}; to the file's imports.
  • The three declarations, is_exhaustive, normalize, and signature, go inside the impl Checker block, beside your other methods. Pasting them adds their todo_m7! holes, which are yours to fill.
  • Both must live in src/types/check.rs. Only the submitted files are collected, so code you put in a new file of your own is not part of what is graded, and your submission will not compile on Gradescope.
  • The module provides covers, and inside it useful (U), specialize (S), and default_rows (D). It allows dead_code, so it raises no clippy warning before your code calls it. You may read it freely, but you do not need to change it.
  • You write the reduction of a pattern to a Pat (normalize), a type's constructors (signature), and the method that joins them (is_exhaustive).

Getting the code and running the tests

M7 builds directly on your M1–M6 code. Because the milestones are cumulative, cargo m7 runs every M6, M5, M4, M3, M2, and M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M6 first, and keep working in the same clone with your completed evaluator, checker, and rule checks in place. check_guards is built on your M6 purity judgment, and every program goes through your M5 checker before it runs.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1. That setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1 through M6. Then pick up the same loop, with the milestone number advanced: 

cargo m7                                    # run the Milestone-7 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m7 is short for cargo test --features m7, and runs the M7 tests and every earlier milestone's. To list the milestone-tagged holes at any time: 

grep -rn 'todo_m7!' src

The holes for struct literals, field access, and method calls stay todo_m8!s until the next milestone.

A suggested order: write the matcher and the evaluator's arms first, since many provided tests run whole programs without the checker. Then write check_pattern and the checker's arms with an is_exhaustive that just returns true, and fill in the real check once the rest passes. check_guards can come at any point after that.

Running a program

With --features m7, cargo run runs the static checks and then main. calc.brg uses constructors, match, and ? together: 

$ cat calc.brg
type Calc = Num(Int) | Add(Calc, Calc) | Div(Calc, Calc);

fn result(e: Calc) -> Result<Int, String> = match e {
    Num(n) => Ok(n),
    Add(l, r) => Ok(result(l)? + result(r)?),
    Div(l, r) => {
        let d = result(r)?;
        if d == 0 { Err("divide by zero") } else { Ok(result(l)? / d) }
    },
};

fn main() {
    println(result(Add(Num(1), Div(Num(8), Num(2)))));
    println(result(Div(Num(1), Add(Num(0), Num(0)))));
}

$ cargo run -q --features m7 -- calc.brg
Ok(5)
Err("divide by zero")

In gap.brg a function over Calc forgets Div. main never builds a Div, but the checker rejects the program before it starts. Not even start is printed, and the exit status is 1: 

$ cat gap.brg
type Calc = Num(Int) | Add(Calc, Calc) | Div(Calc, Calc);

fn size(e: Calc) -> Int = match e {
    Num(_) => 1,
    Add(l, r) => 1 + size(l) + size(r),
};

fn main() {
    println("start");
    println(size(Num(1)));
}

$ cargo run -q --features m7 -- gap.brg
  × match is not exhaustive
   ╭─[gap.brg:3:27]
 2 │
 3 │ fn size(e: Calc) -> Int = match e {
   ·                           ────┬────
   ·                               ╰── here
 4 │     Num(_) => 1,
   ╰────

Because the checker runs first, no program containing a match runs under --features m7 until the checker's arms are written. The first todo_m7! it meets stops the run.

A few examples

Each expression has the value at its right:

match [4, 5, 6] { [a, b, ...t] => (b, t), _ => (0, []) }     (5, [6])
match [1, 2] { x :: y :: [] => x + y, _ => 0 }               3
match false { true => 1, false => 2 }                        2
match Err("no") { Ok(n) if n > 0 => n, Ok(_) | Err(_) => 0 } 0

Matches that are rejected before the program runs, with the error and where it is reported (the chapter has more):

match (Some(1), true) { (None, _) => 0, (_, false) => 1 }
                                   NonExhaustiveMatch, at the match
match 1 { 0 => "z", n => n }       Mismatch (expected String, found Int), at n
match (1, 2) { (a, a) => a, _ => 0 }
                                   NonLinearPattern (a), at the second a
match Some(1) { Some(a) | None => 0 }
                                   OrPatternBindings (a), at the whole pattern
1?                                 TryOnNonCarrier (Int)
match 1 { k if { println(k); true } => 0, _ => 1 }
                                   ImpureGuard, witness [println]

The provided tests come in three kinds. Some run a whole program with run_program, which skips the static checks, so the evaluator meets programs the checker would have refused. Some call Checker::check_program on a loaded program, and some call check_guards alone. A rejection is tested by its error variant and, where it matters, by its payload (the name in NonLinearPattern, the path in ImpureGuard), never by the text of its message. When cargo m7 is all green, your implementation is very likely correct.

How M7 is graded

M7 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M7 behavior (five properties, 8 points each) and 40 on carried-over regression tests for the past milestones (M1 through M6), since M7 is cumulative. The carried-over 40 is divided evenly among M1 through M6 (about 6.7 points each), then across each milestone's properties, so a regression in any one of them is weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface, separate from the provided tests you run locally with cargo m7.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting. The starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. The autograder builds your files against its own copies of the frozen files, so make sure your code builds with those files unmodified.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: you must pass all of them, the M7 tests and the carried-over M6–M1 tests, before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative, roughly −20 and up to −40, at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first. Code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M7 is cumulative, a change that breaks an earlier milestone's test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property, a single rule your implementation must obey. Five properties cover the new M7 behavior:

  • Constructors: a constructor application builds a tagged value, a generic constructor is typed at its use, and the wrong number of arguments is an ArityMismatch.
  • Match basics: match takes the first arm whose pattern matches, binding its variables. It handles constructor, cons-list, literal, guard, wildcard, or-, and list-rest patterns, and an arm's variables are in scope for that arm only.
  • Exhaustiveness: a match's arms must all produce one type, and its patterns must cover the scrutinee's type, looking inside constructors, tuples, and lists, and requiring a catch-all for Int and String. Otherwise the checker reports NonExhaustiveMatch.
  • Match at run time: in a program run without the checks, a match that no arm covers is a clean NonExhaustiveMatch stuck state, not a crash.
  • Try: e? unwraps an Ok or Some and returns an Err or None from the enclosing function, and it is checked against that function's return type.

The guard checks are not a separate property. The provided tests cover them, so they count through the provided-test gate.

A property is all-or-nothing. It is checked by several cases, some visible and some hidden, and you earn its points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it. If it is a hidden one, you see a hint about what kind of case it is, but not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M7 on its own. That is fine. What I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote. Point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. calc.brg (above) prints Err("divide by zero") for Div(Num(1), Add(Num(0), Num(0))). Trace that call through your code: which arm of the match runs at each level, what your matcher binds, and what your Try arm does when result(r)? sees an Ok. Then explain how a failing ? leaves the enclosing function: what your evaluator raises, and which part of your earlier code turns it into the function's result.
  2. gap.brg (above) is rejected before it runs, although main never builds a Div. Show what your normalize produces for each arm of size, what your signature returns for Calc, and how covers concludes that a value escapes every row. Why must signature return None for Int, and what would go wrong if it returned the literals that appear in the arms?
  3. match (Some(1), true) { (None, _) => 0, (_, false) => 1 } is not exhaustive, but neither column alone has a missing constructor. Name a value that escapes both arms, and explain how the usefulness test finds the gap by looking at the two columns together. Then explain why your is_exhaustive leaves out a guarded arm, using match Err("no") { Ok(n) if n > 0 => n, Ok(_) | Err(_) => 0 }.
  4. match (1, 2) { (a, a) => a, _ => 0 } is NonLinearPattern and match Some(1) { Some(a) | None => 0 } is OrPatternBindings. Point at where your check_pattern catches each one. Why does Bridger reject a repeated variable instead of reading it as an equality test, and why must both sides of an | bind the same names at the same types?
  5. A rule filter that reaches a recursive function is Recursive, yet a guard may reach one: match 1 { k if false and up(k) => 0, _ => 1 } is accepted, where up calls itself. Explain why the two places are treated differently, and how your check_guards reuses your M6 purity judgment while allowing recursion. How does your code build the witness [ping, println] for a guard that calls ping, which prints?

How you implemented it

  • Walk through your matcher from start to finish: one sentence per kind of pattern, saying how it decides whether the value fits and what it binds. Say how your :: and ...rest arms keep the tail shared, and how your | arm tries its sides. Naming the provided tools you used (Value::Ctor, List::uncons, Pattern::binders, type_of, Control) is encouraged.
  • Describe your checker's Match and Try arms: how you check each arm on its own copy of the context, when you call is_exhaustive, and how ? decides between TryInNonCarrierFunction, TryInLambda, and a Mismatch of error types.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made. If you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative. If your description does not match the code you submitted (it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission), you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester. M7 touches the evaluator, the checker, and the rule checks, so make sure you can explain your changes to each of them.
