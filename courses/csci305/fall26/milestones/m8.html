Milestone M8 Structs, Methods, and Traits

CSCI 305: Concepts of Programming Languages

In this milestone Bridger gets objects. You build struct literals, field access, and method calls, in both the evaluator and the type checker. A method call dispatches on the head of its receiver, a bounded type parameter reaches its trait's methods, and ? converts an error through an impl From. Your M6 purity judgment learns to follow method calls. This is the last milestone: with it, your interpreter runs the whole language.

What to build the specification

Read the Milestone M8 chapter before you start. It is the authoritative specification. Its table of forms is the checklist your code is measured against. The rules themselves are in the language reference appendix (under structs, fields, and methods), and the static errors are catalogued by name. The ideas are in the Part IX chapters: Structs with methods, Dispatch and encapsulation, and Traits vs. inheritance. The work is in three files you have already edited:

Expr::Field(..) => todo_m8!("E-Field (struct field access)"),
Expr::Method(..) => todo_m8!("E-Method (head-type dispatch)"),

// src/types/check.rs
Expr::Struct(..) => todo_m8!("T-Struct"),
Expr::Field(..) => todo_m8!("T-Field"),
Expr::Method(..) => todo_m8!("T-Method (dispatch on the receiver's type; bounds)"),

// src/relations/check.rs
// no marker: your purity walk meets struct literals, fields, method calls, and a converting ?

Three changes have no todo_m8! marker. The checker's Try arm accepts a ? whose error type differs from the function's when an impl From converts it. The evaluator's Try arm runs that conversion. And your purity judgment from M6 and M7 must handle the new forms, which no earlier program could reach. The chapter spells out the contracts the tests hold each file to. These are the ones that most often cause trouble:

  • A struct value keeps declaration order. The evaluator runs the field expressions in the order the literal writes them, then stores the fields in the order the declaration lists them, so Pos { y: 2, x: 1 } == Pos { x: 1, y: 2 }.
  • The two sides report struct errors at different places. The evaluator reports DuplicateField, NotAStruct, MissingField, and NoSuchField, in that order, all at the literal. The checker reports a repeated or undeclared field at that field's value and a missing one at the literal.
  • The recorded choice comes first. The evaluator's Method arm runs the method conversions holds at the call's span if there is one, then the one methods holds under the receiver's head key, then a built-in conformance. Only then is it NoSuchMethod.
  • A method body runs in the root scope. Build its scope from env.root(), not the caller's environment, with self bound when the method takes one and then each parameter. A Return from it is the call's value, as in your Call arm.
  • Pairings are the method's, not the syntax's. A method with self called on a type name is NoReceiver, and one without called on a value is NotAMethod. A bare type parameter as a receiver is TypeParamCall, since it has no head at run time.
  • Convert only when the types differ. The Try arm calls find_from just before it would report Mismatch. When the error types already agree nothing is recorded, so an M7 program checks and runs as it did.
  • A method call is a callee. In your purity walk a method call or a ? names a callee key, as a function call names a function, and your check_guards also walks every method body in program.impls.

Everything outside the holes is provided, including Value::Struct and Value::Type, the methods and conversions tables built when a program loads, prelude::builtin_method, and every declaration check (conformance, coherence, and the discharge of the bounds your arms register). The chapter lists the provided runtime the M8 arms use.

First: paste in the three helper modules

The starter leaves out the bookkeeping that connects objects to the rest of the interpreter. The chapter's helper modules section prints it as three modules, one for each file you edit. Copy each, unchanged, to the end of its file, after everything else:

  • mod head goes at the end of src/interp/eval.rs. It gives head_key, the key a value's head has in the method table.
  • mod objects goes at the end of src/types/check.rs, after the M5 helpers and the M7 exhaustive module. It gives struct_decl, type_receiver, instantiate_struct, find_method, method_sig, and find_from.
  • pub mod calls goes at the end of src/relations/check.rs. It gives the call graph's method nodes: method_callee, method_bodies, method_params, method_keys, and is_prelude_fn.
  • Each must live in the file named above. Only the submitted files are collected, so code you put in a new file of your own is not part of what is graded, and your submission will not compile on Gradescope.
  • Each module brings its own use lines, so it cannot clash with the imports your arms add, and an item you have not called yet raises no warning. None of them contains a typing or evaluation rule. You may read them freely, but you do not need to change them.

Running a program

With --features m8, cargo run runs the static checks and then main. media.brg has two structs that implement one trait, and one function written over the trait: 

$ cat media.brg
struct Book { title: String, pages: Int }
struct Song { title: String, secs: Int }

trait Describe { fn describe(self) -> String; }

impl Book {
    fn new(title: String, pages: Int) -> Self =
        Book { title: title, pages: pages };
}
impl Describe for Book {
    fn describe(self) -> String =
        self.title ++ ", " ++ to_string(self.pages) ++ " pp.";
}
impl Describe for Song {
    fn describe(self) -> String =
        self.title ++ " (" ++ to_string(self.secs) ++ " s)";
}

fn catalogue<T: Describe>(xs: [T]) -> [String] =
    map(xs, |x: T| x.describe());

fn main() {
    println(catalogue([Book.new("Dune", 412), Book.new("Emma", 474)]));
    println(catalogue([Song { title: "Blue", secs: 191 }]));
}

$ cargo run -q --features m8 -- media.brg
["Dune, 412 pp.", "Emma, 474 pp."]
["Blue (191 s)"]

Writing impl Song in place of impl Describe for Song leaves the method in place but takes Song out of the trait. The program no longer starts, and the exit status is 1:

A few examples

After these declarations:

struct Pos { x: Int, y: Int }
type Light = Red | Amber | Green;

impl Pos {
    fn zero() -> Pos = Pos { x: 0, y: 0 };
    fn sum(self) -> Int = self.x + self.y;
    fn shift(self, d: Int) -> Self = Pos { x: self.x + d, y: self.y + d };
}
impl Light {
    fn advance(self) -> Light =
        match self { Red => Green, Green => Amber, Amber => Red };
}

each expression has the value at its right:

Pos { y: 2, x: 1 }                            Pos { x: 1, y: 2 }
Pos.zero().shift(3).sum()                     6
Green.advance()                               Amber
[3, 1, 2].length()                            3
"b".cmp("a")                                  Greater

These are rejected before the program runs, with the error and where it is reported (the chapter has more):

Pos { x: 1 }                       MissingField (y), at the literal
Pos { x: 1, y: 2, z: 3 }           NoSuchField (z), at 3
Light { x: 1 }                     NotAStruct (Light)
(1, 2).x                           FieldOfNonStruct (x, found (Int, Int))
Pos.sum()                          NoReceiver (sum)
Pos.zero().zero()                  NotAMethod (zero, on Pos)
Pos.zero().shift(1, 2)             ArityMismatch (shift: 1, given 2)

The provided tests come in three kinds. Some run a whole program with run_program, which skips the static checks, so the evaluator meets programs the checker would have refused and has no recorded choices to read. Some call Checker::check_program on a loaded program, and some call check_rules and check_guards. A rejection is tested by its error variant and, where it matters, by its payload, never by the text of its message. When cargo m8 is all green, your implementation is very likely correct.

How M8 is graded

M8 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M8 behavior (five properties, 8 points each) and 40 on carried-over regression tests for the past milestones (M1 through M7), since M8 is cumulative. The carried-over 40 is divided evenly among M1 through M7 (about 5.7 points each), then across each milestone's properties, so a regression in any one of them is weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface, separate from the provided tests you run locally with cargo m8.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting. The starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. The autograder builds your files against its own copies of the frozen files, so make sure your code builds with those files unmodified.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: you must pass all of them, the M8 tests and the carried-over M7–M1 tests, before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative, roughly −20 and up to −40, at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first. Code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M8 is cumulative, a change that breaks an earlier milestone's test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property, a single rule your implementation must obey. Five properties cover the new M8 behavior:

  • Structs: a struct literal builds a value of its declared type and field access reads a field. A literal missing a field is MissingField, one with an ill-typed field is a Mismatch, and access of an unknown field is NoSuchField. A struct prints in canonical form.
  • Methods: a method runs with self bound to the receiver and its arguments in scope, dispatched on the receiver's type. A call of a method the type does not have is rejected by the checker (NoSuchMethod) and, unchecked, is a clean NoSuchMethod stuck state.
  • Bounds: a generic bound such as T: Show resolves a method call on the type parameter through the trait, and requires the caller to supply a type that implements it, an UnsatisfiedBound otherwise.
  • Self: inside an impl, Self names the implemented type in signatures and bodies. Outside any impl, Self names no type.
  • Try conversion: when an e?'s error type differs from the enclosing function's, the checker finds the matching impl From's from and the evaluator runs it, so the error is converted on the way out.

The purity cases are not a separate property. The provided tests cover them, so they count through the provided-test gate.

A property is all-or-nothing. It is checked by several cases, some visible and some hidden, and you earn its points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it. If it is a hidden one, you see a hint about what kind of case it is, but not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M8 on its own. That is fine. What I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote. Point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. In media.brg (above), the one call x.describe() inside catalogue runs Book's method during the first call and Song's during the second. Trace how your evaluator's Method arm picks the body each time: what head key it computes, which table it looks in, and how it builds the body's scope. Then explain why Book.new("Dune", 412) is accepted while Pos.sum() is NoReceiver. Why does the body's scope start from env.root() and not from the caller's environment?
  2. When media.brg's checker meets x.describe(), x has type T, which has no impl. Explain how your Method arm still finds describe and its result type, and what changes when impl Describe for Song becomes impl Song. Why is a call such as T.describe(), with the type parameter itself as the receiver, rejected as TypeParamCall?
  3. The chapter's Log example implements Record<String> and Record<Int>, and Log { lines: [] }.record("start").record(7) prints ["start", "#7"] when checked but ["start", 7] when run unchecked. Both calls have the head Log and the name record. Explain what the checker records, where your evaluator's Method arm reads it, and why the unchecked run takes the other path. What does this say about whether dispatch by head alone determines the method?
  4. In the chapter's ? example, add("a", "z") prints Err(Missing("z")). Trace what your checker's Try arm does with lookup(k)?, whose error type is NotFound inside a function returning Result<Int, AppError>, and what your evaluator's Try arm does with the Err. Why does the same program run unchecked print Err(NotFound { key: "z" }), and why must nothing be recorded when the two error types already agree?
  5. A rule filter that calls same(b).describe(), where same returns its Book argument and b is a generator variable over a relation of books, is rejected as impure when Song's describe prints, although Book's has no effect. Writing b.describe() is accepted. Explain both results through the callee keys your purity walk gets from calls::method_callee, and say how your code builds the witness. Why is the purity judgment coarser here than the checker, which knows that same(b) has type Book?

How you implemented it

  • Walk through your evaluator's Struct, Field, and Method arms: the order in which each evaluates its parts and makes its checks, and how Struct arrives at declaration order. Naming the provided tools you used (Value::Struct, Value::Type, head_key, builtin_method, enter_call/leave_call) is encouraged.
  • Describe your checker's Struct, Field, and Method arms: how you use instantiate_struct and Ty::substitute to check a generic struct's fields, how the Method arm decides what its receiver is, and how it tells FieldNotMethod from NoSuchMethod.
  • Describe how you extended your purity walk and check_guards: which new forms only descend, how a method key joins your impurity fixpoint and recursion check, and where is_prelude_fn comes in.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made. If you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative. If your description does not match the code you submitted (it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission), you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester. M8 touches the evaluator, the checker, and the rule checks, so make sure you can explain your changes to each of them.
