Milestone M5 The Type Checker

CSCI 305: Concepts of Programming Languages

In this milestone your interpreter learns to reject a program before it runs. You fill in the type checker in src/types/check.rs: one arm of check_expr for each form of M1–M4, and the body of unify. The checker works bidirectionally — it checks an expression against a type when the context supplies one and synthesizes a type when it does not — and names what neither mode knows with an inference variable that unify solves. From now on the checker stands between the parser and the evaluator: a program with a type error prints nothing at all.

What to build the specification

Full specification: Textbook — Milestone M5: the type checker  |  Previous milestone: Milestone M4: functions, closures, and static scope

Read the Milestone M5 chapter before you start — it is the authoritative specification. Its table of forms is the checklist your checker is measured against; the rules themselves are collected in the typing rules appendix, and the “Building it” sections of A type checker and Function types and polymorphism turn them into the algorithm the arms follow. Every hole names the rules it implements: 

// src/types/check.rs — some of the M5 holes
Expr::Lit(..)    => todo_m5!("T-Int / T-Bool / T-Str / T-Unit"),
Expr::Var(..)    => todo_m5!("T-Var / T-Self"),
Expr::Block(..)  => todo_m5!("T-Block / T-Let / T-Seq"),
Expr::Return(..) => todo_m5!("T-Return (reads ctx.ret())"),
Expr::Call(..)   => todo_m5!("T-App (first-order matching of generics at the call)"),
// … and the rest of the M1–M4 forms

pub fn unify(&mut self, a: &Ty, b: &Ty, span: Span) -> Result<(), TyError> {
    todo_m5!("unify (structural agreement; solves TyKind::Meta with an occurs check)")
}

That is many more holes than M4's two, but most arms are short, and they share a shape. A few contracts hold across all of them, and the tests check each one:

  • Every arm ends the same way. When there is an expected type, the arm unifies the type it built with it (Chk-Sub), then resolves the type and records it at its own span. A type that is never recorded is never judged by the determination rule, so an arm that skips record lets an ambiguous type through.
  • unify(a, b, span) takes the type found first and the type required second. A failure is Mismatch { expected: b, found: a, span }, both resolved, and inside compound types the pair reported is the innermost one that disagrees: a [Int] passed where [String] is required is expected String, found Int. Swap the arguments and every mismatch message comes out backwards.
  • Premises are checked in the order the rule writes them — left operand before right, callee before arguments, condition before branches — and the first failure is the one reported.
  • A mismatch is reported where the type goes wrong. An arm that passes its expected type down to a part lets the mismatch surface at the smallest expression whose type disagrees, rather than at the whole.
  • The nesting bound. check_expr returns TooDeep once self.depth reaches MAX_NESTING, and otherwise increments depth, checks, and decrements it whatever the outcome — the same balance enter_call and leave_call kept at M4, with the same trap: a ? before the decrement leaves depth raised after every error.

Everything that belongs to a whole declaration is provided. The driver builds the top-level context from the signatures, checks each global in initialization order (reporting a cycle), checks every other declaration in source order, validates every written signature, and after each declaration judges the types your arms recorded and the bounds they asked for — NoEquality, NotPrintable, and UnsatisfiedBound come from there. The Ctx, the inference variables (fresh_meta, solve, resolve, record), decl, the bound and divergence bookkeeping, and Ty::substitute are ready to use. The chapter walks through what each arm must do, and prints skeletons of the Block and If arms showing where the divergence calls go.

First: paste in the helper module

The starter leaves out a module of helpers that several arms call: annotation, native_fn_type, global_type, check_callee / finish_call, and undetermined. The chapter's helper module section prints it in full. Copy it, unchanged, to the end of src/types/check.rs, after the closing brace of the impl Checker block.

  • It must live in check.rs. Only the submitted files are collected, so a helper placed in a new file of your own is not part of what is graded, and your submission will not compile on Gradescope.
  • It is a mod helpers with its own use lines, so it cannot clash with the imports your arms add, and its methods are pub, so a helper you have not called yet raises no clippy warning.
  • You may read and use it freely — and the write-up below asks you about check_callee and finish_call — but you do not need to change it.

Getting the code and running the tests

M5 builds directly on your M4, M3, M2, and M1 code. Because the milestones are cumulative, cargo m5 runs every M4, M3, M2, and M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M4 first — keep working in the same clone with your completed evaluator in place. Nothing in the evaluator changes at M5, but it must keep passing every earlier test, and whole-program tests run it after the checker accepts the program.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1 — that setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1 through M4. Then pick up the same loop, with the milestone number advanced: 

cargo m5                                    # run the Milestone-5 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m5 is short for cargo test --features m5, and runs the M5 tests and every M4, M3, M2, and M1 test. To list the milestone-tagged holes at any time: 

grep -rn 'todo_m5!' src

The holes for relations, constructors, match, ?, structs, and methods — and check_rule — stay todo!s until their own milestones.

Running a program

With --features m5, cargo run checks the program before it runs it. A program the checker rejects stops with the error before main is called, and exits with status 1. Compare the same program under M4 and M5: 

$ cat late.brg
fn main() {
    println("start");
    let total = 0;
    total := total + 1;
}

$ cargo run -q --features m4 -- late.brg
start
  × type error: expected ref<()>, found Int
   ╭─[late.brg:4:5]
 4 │     total := total + 1;
   ·     ─────────┬────────
   ·              ╰── here

$ cargo run -q --features m5 -- late.brg
  × type mismatch: expected ref<_>, found Int
   ╭─[late.brg:4:5]
 4 │     total := total + 1;
   ·     ──┬──
   ·       ╰── here

The evaluator gets as far as the assignment and reports the whole expression that got stuck; the checker reports total, the expression whose type disagrees, and the program never prints start. An unsolved inference variable prints as _. Because the checker runs first, no program runs under --features m5 until the arms it reaches are written — the first todo_m5! it meets stops the run. --features m4 still runs the evaluator with no checker in front of it. Once your checker is done, run the programs you wrote for M4 through it: a correct program that it rejects is either a bug in an arm or one of the conservative rejections the textbook describes, and the error's span tells you where to look.

A few examples

Expressions in an empty context, and the type your checker should give them:

(1, "a").1                                     : String
[] ++ [true]                                   : [Bool]
|x| x + 1                                      : fn(Int) -> Int
ref [1]                                        : ref<[Int]>
{ let r = ref 0; r := deref r + 1; deref r }   : Int
map([1, 2], to_string)                         : [String]
fold([1, 2, 3], 0, |acc, x| acc + x)           : Int

Expressions the checker rejects — the error variant, and where it is reported:

1 + "a"                          Mismatch (expected Int, found String), at "a"
(true, 1).4                      NoSuchComponent (index 4, arity 2)
{ let f = |x| x(x); () }         InfiniteType, at x(x)
{ let f = |x: Int| x; f == f }   NoEquality (fn(Int) -> Int)
len(42)                          UnsatisfiedBound (no impl Len for Int), at 42
{ let xs = []; xs := [1]; () }   Mismatch (expected ref<_>, found [_]), at xs
abs(1, 2)                        ArityMismatch (`abs` takes 1, given 2)

The provided tests come in two kinds. The first builds an Expr by hand with the builders from the earlier milestones and types it in an empty context with infer, or against a type with check. The second loads a whole program from source and checks it with check_program, on top of the prelude. A rejection is tested by its TyError variant and, where it matters, by its span and payload — never by the text of its message. When cargo m5 is all green, your checker is very likely correct.

How M5 is graded

M5 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M5 behavior — eight properties, 5 points each — and 40 on carried-over regression tests for the past milestones (M1 through M4), since M5 is cumulative and your evaluator must keep working behind the checker. The carried-over 40 is divided evenly among M1, M2, M3, and M4 (10 points each), then across each milestone's properties — so a regression in any one of them is weighted against that milestone's own share. These are held-back tests, run on Gradescope against the public interface — separate from the provided tests you run locally with cargo m5.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting; the starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. The autograder builds your files against its own copies of the frozen files, so make sure your code builds with those files unmodified.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: passing all of them — the M5 tests and the carried-over M4, M3, M2, and M1 tests — is required before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative — roughly −20, and up to −40 — at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first: code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M5 is cumulative, a change that breaks an M4, M3, M2, or M1 test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property — a single rule your checker must obey. Eight properties cover the new M5 behavior:

  • Operator types — arithmetic and negation over Int, comparison and the boolean connectives to Bool, concatenation over strings or lists, cons onto a list; an operand of the wrong type is a Mismatch.
  • Equality types — == and != yield Bool on a type that admits equality; operands of different types are a Mismatch, and comparing values with no equality (a function, anywhere inside) is NoEquality.
  • Compound types — tuples, lists, and projection are typed structurally; a list literal's elements share one type; an empty list takes its element type from context and is Ambiguous without one.
  • Control types — a block threads its let bindings, an if used as a value needs both branches to agree, loops and assignment have type (), and a return must match the enclosing function's result type.
  • Functions — a lambda infers a function type, its parameters solved by the body or an expected type; a call checks its arguments against the callee's parameters, and a wrong count is ArityMismatch.
  • Programs check — a well-typed program checks, recursion and use-before-definition included; generic and native prelude functions are instantiated afresh at each use; an unknown name is UnboundVariable.
  • Rejections — the checker rejects, before the program runs, a type mismatch, a bounded native call on a type that does not meet the bound (UnsatisfiedBound), and a global initialization cycle — including in a function main never calls and in a branch that is never taken.
  • Annotations and generics — a type annotation must name a declared type; a type parameter is a type only within its own declaration; and a self-application whose occurs check fails is InfiniteType.

Several of these exercise provided code — the driver, the bound and determination checks — but none of them can pass until your arms and unify feed that code what it needs: the types recorded at the right spans, the bounds required at the right places. The carried-over 40 re-checks every evaluator rule from M1–M4, so a regression in your evaluator costs points here even though M5 does not ask you to change it.

A property is all-or-nothing: it is checked by several cases — some visible, some hidden — and you earn its points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it; if it is a hidden one, you see a hint about what kind of case it is, but not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M5 on its own. That is fine — what I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote — point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. Under --features m4, late.brg (above) prints start and then stops at the whole assignment; under --features m5 it prints nothing and reports total, with expected ref<_>, found Int. Using your Assign arm and your unify, explain where the ref<_> comes from, why the error lands on total rather than on the whole assignment, and why expected and found come out in that order and not the reverse.
  2. [] ++ [true] has type [Bool], but [] ++ [] is Ambiguous. Trace both through your concatenation arm: what type the left operand synthesizes, how the right operand is checked, and what type remains afterward. For [] ++ [], is it your concatenation arm or the driver's determination rule that reports Ambiguous (and when does the other one fire)? Why does a type have to be recorded for the determination rule to judge it?
  3. In one body, id(1) and id("a") both check for a generic fn id<T>(x: T) -> T, but in |f| (f(1), f("a")) the second call is rejected. Point at the place in your Var arm where a type parameter becomes an inference variable, and explain why the first program checks. What would go wrong if that variable were made once per declaration instead of once per use? Why does the lambda's parameter f not get the same treatment?
  4. { let f = |x| x(x); () } is InfiniteType. Walk through what your Lambda and Call arms ask unify to do for x(x), and show where your occurs check fires. What would happen in your unify (and later, in resolve) if you left the occurs check out?
  5. fn f() -> Int { return 1; let y = []; println(y); 2 } checks, although nothing fixes the element type of y, while fn f() -> Int { return 1; 1 + true } is rejected. Using your Block arm, explain where you call dead_after, why that call has to come before the remaining statements are checked, and why the second program is still an error.

How you implemented it

  • Walk through your Expr::Call arm and your unify from start to finish. For Call: how you get the callee's type, the three cases it can be in (a function type, an unsolved variable, anything else), how you check the arguments, and what finish_call does with the callee's bounds. For unify: the order of your cases and how you report the innermost disagreement inside compound types. Naming the provided tools you used (check_callee, fresh_meta, resolve, record, Ty::func, TyError, ?) is encouraged.
  • Describe how your check_expr enforces the nesting bound and keeps self.depth balanced when an arm fails, and whether you factored the shared ending of every arm (Chk-Sub, resolve, record) into a method of your own.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made — and if you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative: if your description does not actually match the code you submitted — it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission — you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester, and the type checker is the largest milestone so far — it is worth understanding every arm.

Submitting

First write your Description.md at the root of the repository. Then, from inside the project folder, check the code: 

cd bridger-interpreter                       # the project root

cargo m5                                     # all Milestone-5 tests pass (M4–M1 too)?
cargo fmt                                    # format your code
cargo clippy --all-targets -- -D warnings    # lint — fix any warnings

Then package src/ and the root .md files into a .zip. Run the command for your system from the project root.

macOS / Linux (Terminal):

zip -r ../m5-submission.zip src *.md

Windows (PowerShell):

Compress-Archive -Path src, *.md -DestinationPath ..\m5-submission.zip -Force

Either one writes m5-submission.zip in the folder just above the project, with src/ and Description.md at the top of the archive. The autograder replaces Cargo.toml, tests/, and the frozen src/ files with its own copies, so any changes you make to them are discarded. New at M5: two files are graded as your code, src/interp/eval.rs and src/types/check.rs. Any helper functions you write — and the pasted-in helper module — must live in one of those two files.

Upload m5-submission.zip to the Milestone M5 assignment on Gradescope (linked from Canvas). Some tests are visible, so you will get results back shortly and can resubmit before the deadline; other tests are hidden, so passing every visible test does not guarantee full credit.

No zip command on Linux? Install it (on Debian/Ubuntu, sudo apt install zip). Alternatively, in Finder (macOS) or File Explorer (Windows), select the src folder and the .md files inside the project folder (not the project folder itself) and choose Compress / Send to → Compressed (zipped) folder.
