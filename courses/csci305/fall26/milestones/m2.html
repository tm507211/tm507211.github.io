Milestone M2 Environments and Binding

CSCI 305: Concepts of Programming Languages

In this milestone you make the evaluator's env parameter — carried unused since M1 — finally do work. You put a variable and a block into the interpreter: a variable reads its value from the environment, and a block threads an environment that each let extends over the rest of the block. You fill in two match arms of eval_expr, Expr::Var and Expr::Block, so that every one of these forms either evaluates to a value or reports a well-formed runtime error.

What to build the specification

Full specification: Textbook — Milestone M2: environments and binding  |  Previous milestone: Milestone M1: the expression evaluator

Read the Milestone M2 chapter before you start — it is the authoritative specification, including the exact rule for each form and the one case in which a variable is stuck. In short, you implement the two milestone-tagged holes in eval_expr: 

// src/interp/eval.rs — the two M2 arms
Expr::Var(..)   => todo_m2!("E-Var"),
Expr::Block(..) => todo_m2!("E-Block / E-Let / E-Seq"),

Everything else in the interpreter — the parser, the value and error types, and the Env itself — is provided and frozen. Your work is the meaning of a variable and a block. A variable is read against the environment: env.lookup(x) returns Some(v) for a name in scope and None for one that is not, and a None is the only new stuck case — RuntimeError::UnboundVariable { name, span }, blaming the variable's span. A block walks its items top to bottom, threading an environment that each let extends (producing a new child scope, never rewriting the parent), and its value is the trailing expression, or Value::Unit when there is none. Blocks and lets are never themselves stuck — only a stuck subexpression makes them so, and the ? operator sends it straight out, aborting the block at that item's span.

Getting the code and running the tests

M2 builds directly on your M1 code. Because the milestones are cumulative, cargo m2 runs every M1 test too, and the provided-test gate (below) will fail the whole milestone if any of them fail. Finish Milestone M1 first — keep working in the same clone with your completed M1 arms in place. If you have not done M1 yet, do it before starting M2; without the M1 expression arms, the carried-over tests cannot pass no matter what you write here.

The toolchain, the clone, and the layout of the codebase are the ones from Milestone M1 — that setup is done once, and this milestone does not change it. If you are starting fresh, follow the M1 page to install rustup, clone bridger-interpreter, and complete M1. Then pick up the same loop, with the milestone number advanced: 

cargo m2                                    # run the Milestone-2 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m2 is short for cargo test --features m2. Milestones are cumulative, so cargo m2 runs both the M2 tests and every M1 test — the expression fragment keeps passing as you grow the evaluator. To list exactly what M2 asks of you at any time: 

grep -rn 'todo_m2!' src

The two holes turn up in src/interp/eval.rs. Every other Expr variant is a hole tagged for a later milestone, so the crate still compiles with these two unwritten.

A few examples

Blocks and variables, and the values your evaluator should produce:

{ let x = 2; x + 3 }              ⇒ 5
{ let x = 1; let y = x + 1; y }  ⇒ 2      (a later let sees the earlier one)
{ let x = 1; let x = x + 1; x }  ⇒ 2      (the second binding shadows the first)
{ 1; 2; 3 }                      ⇒ 3      (the first two are discarded)
{ let x = 5; }                   ⇒ ()     (a trailing ; leaves no tail)
{ }                              ⇒ ()

Expressions that are stuck — no value, and the run reports a runtime error:

y                        ⇒ stuck   (UnboundVariable: y is not in scope)
{ { let x = 1; x }; x }  ⇒ stuck   (x's scope ended at the inner })
{ z; 1 }                 ⇒ stuck   (the unbound z aborts the block before the tail)

The provided tests build an Expr by hand and check either the resulting Value or, for a stuck expression, the error's variant, its name, and the span it blames. When cargo m2 is all green, your evaluator is very likely correct.

How M2 is graded

M2 is worth 100 points:

ItemPoints
Auto-graded tests 80, split 40 / 40: 40 on the new M2 behavior and 40 on the carried-over tests for past milestones (M1), since M2 is cumulative and your evaluator must keep the expression fragment working. Each half is split evenly across 5 properties (8 points each). These are held-back tests, run on Gradescope against the public interface — separate from the provided tests you run locally with cargo m2.
Formatting & linting 10: 5 for cargo fmt (checked on your submitted files) and 5 for cargo clippy (checked with -D warnings). Run both before submitting; the starter is clean on a fresh clone, so a warning means something you introduced.
Description.md 10, human-graded (see below).
Does not compile 0 for the entire milestone. Make sure a fresh clone of exactly what you submit runs cargo build.
Fails any provided test 0 for the entire milestone. The provided (visible) tests are a hard gate: passing all of them — the M2 tests and the carried-over M1 tests — is required before any of the 80 auto-graded points are counted.
Description does not match your code The Description.md can be scored negative — roughly −20, and up to −40 — at the discretion of the TA or instructor (see below). Passing every test does not by itself secure full credit.

The two 0 gates come first: code that does not compile, or that fails any of the tests shipped with the repository, earns no credit for the milestone regardless of anything else. Because M2 is cumulative, a change that breaks an M1 test trips this gate too. Only after both gates pass are the 80 auto-graded points, the 10 style points, and the 10 description points assessed.

Each of the 80 points is tied to one property — a single rule your evaluator must obey. Five properties cover the new M2 behavior, such as “an unbound variable is stuck with an UnboundVariable error at the variable’s span” or “a later let in a block sees the bindings the earlier ones made”; the other five re-check the expression-fragment rules from M1, so a regression there costs points here. A property is all-or-nothing: it is checked by several cases — some visible, some hidden — and you earn its 8 points only when all of them pass. When a property fails, Gradescope reports which property it was and states the rule it checks, so you know what behavior to fix. If the failing case is a visible one, you also see a short description of it; if it is a hidden one, you see only the property’s rule, not the specific input. Because attempts are unlimited, the workflow is: submit, read which properties failed, fix them, and resubmit.

The write-up: Description.md

You may use generative AI on this project, and a coding assistant can likely solve M2 on its own. That is fine — what I grade is not only that the code works, but that you understand the code you submitted. The Description.md is how I judge that. Write it yourself, in your own words, about the code you are actually turning in.

Put a Description.md at the root of the repository that answers all of the following.

Concept questions

A few sentences each, in your own words. These are about the code you wrote — point at your own implementation where a question asks you to, rather than repeating the textbook's answers.

  1. What does env.lookup(x) return, and how does your Expr::Var arm turn each of its two outcomes into a result of eval_expr? For the stuck outcome, name the RuntimeError variant you build, which fields it carries, and which node's span it blames.
  2. Explain how your block arm threads the environment through its items. When you evaluate a Stmt::Let, in which environment do you evaluate its right-hand side, and what do you pass to the items that follow? Point to the lines where you call env.extend.
  3. env.extend returns a new Env and leaves the one it was called on untouched. Using that fact, explain why a name bound by a let inside a block is not in scope outside the block — refer to what happens to the block's environment when your arm returns.
  4. In { let x = 1; let x = x + 1; x } the second let shadows the first rather than changing it. Explain, in terms of what extend does, why this produces 2 and not a mutation of the original binding — and why M2's let could not build a counter whose value changes over time.
  5. When a block contains a stuck item — say { z; 1 } with z unbound — the block is stuck and the tail 1 is never reached. Walk through how the ? operator in your arm produces that: what it does when a sub-evaluation returns Err(Control::Raise(..)), and which node's span the reported error carries.

How you implemented it

  • Walk through your Expr::Block arm: how do you destructure it into its items and optional tail, iterate the items while carrying the growing environment, dispatch on Stmt::Let versus Stmt::Expr, and produce the block's value (including Value::Unit when there is no tail)? Naming the provided tools you used (self.eval_expr, env.lookup, env.extend, RuntimeError, .into()/?) is encouraged. Note that the Option<Ty> annotation on a let is ignored at this milestone.
  • Point out anything that was tricky, a bug you fixed, or a design choice you made — and if you used an assistant, say what you had it do and how you checked its work.
Understanding what you submit

The Description.md is worth up to 10 points, graded by hand. But it can also be scored negative: if your description does not actually match the code you submitted — it describes an approach your code does not take, gets the behavior wrong, or reads as though you cannot explain your own submission — you can lose roughly 20 points, and up to 40, as judged by the TA or instructor, who may also ask you to explain your submission in person. Passing every test does not by itself secure full credit.

You are welcome to use a coding assistant to write the code. You are responsible for understanding it. Code you cannot explain will not earn full credit. This expectation grows across the semester, so keep building the habit while the milestones are still small.

Submitting

First write your Description.md at the root of the repository. Then, from inside the project folder, check the code and package the entire project into a .zip: 

cd bridger-interpreter                       # the project root

cargo m2                                     # all Milestone-2 tests pass (M1 too)?
cargo fmt                                     # format your code
cargo clippy --all-targets -- -D warnings    # lint — fix any warnings

zip -r ../m2-submission.zip . -x '.git/*' 'target/*'

That writes m2-submission.zip in the folder just above the project. The -x flags leave out the .git/ history and the target/ build directory, which you do not need to submit. Submit the whole project, not just eval.rs.

Then upload m2-submission.zip to the Milestone M2 assignment on Gradescope (linked from Canvas). Some tests are visible, so you will get results back shortly and can resubmit before the deadline; other tests are hidden, so passing every visible test does not guarantee full credit.

No zip command? The simplest route on any system is the GUI: select the project folder in Finder (macOS) or File Explorer (Windows) and choose Compress / Send to → Compressed (zipped) folder. Just make sure the files sit at the top of the archive (with src/ and Cargo.toml at its root), not nested inside an extra folder. If you would rather have the command line: macOS and most Linux systems already include zip (on Debian/Ubuntu, install it with sudo apt install zip); on Windows, install a zip tool such as 7-Zip, or use the built-in PowerShell command Compress-Archive.
