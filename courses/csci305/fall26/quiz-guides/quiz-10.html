Quiz 10 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lecture 28 and its two textbook chapters: sum and product types, and pattern matching. Exhaustiveness checking is not on this quiz. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 15 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions, each asking one thing. Most give you a small Bridger program — say what it prints or why it is rejected, and why. Others ask you to count a type's values or to work out what a pattern binds.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-Match, T-Con) if it helps, but you are never required to.

Sum and product types Lecture 28

Reading: Sum and Product Types  |  Slides: Lecture 28

Be able to:

  • Say what goes wrong with data encoded as tagged tuples: why a misspelled tag still runs, and why no single tuple type describes a tree of every depth.
  • Count a type's values: a product multiplies its components' counts, a sum adds its alternatives' counts, and a constructor's arguments form a product.
  • Explain why a sum is a disjoint union: the tag keeps the alternatives apart even when they hold the same type. Compare Result<Bool, Bool> with the set union of Bool and Bool, and Option<Option<T>> with TypeScript's T | null | null.
  • Read a type declaration as a sum of products. Write one for a small set of shapes, including a recursive or generic one.
  • Build a recursive type level by level, say at what level a given value first appears, and say why a type such as type Loop = Again(Loop); is accepted yet has no values.
  • Apply E-Con: a constructor evaluates its arguments left to right and builds a value tagged with its name, running no other code. Say when two constructor values are equal under ==.
  • Apply T-Con: say why a constructor use is rejected (unknown name, wrong number of arguments, wrong argument type) and why one name cannot belong to two types.
  • Say what determines a generic constructor's type arguments, why let n = None; is rejected, and why map([1, 2], Some) needs a lambda in Bridger.
  • Recognize the design space: untagged unions in C and TypeScript; null references compared with Option; nominal sums compared with OCaml's polymorphic variants; constructors as functions in ML and Haskell; Pascal's optional tag; sums written as class hierarchies.

Pattern matching Lecture 28

Reading: Pattern Matching  |  Slides: Lecture 28

Be able to:

  • Compute match(p, v) by hand for each form of pattern: wildcard, variable, literal, constructor, tuple, list, cons, and or-pattern. Tell the empty binding ∅ apart from the failure ⊥, and say why one failing subpattern fails the whole pattern.
  • Trace E-Match: the scrutinee is evaluated once, arms are tried from top to bottom, and the first arm whose pattern fits and whose guard holds runs. Say why a general arm can sit behind special ones, and what happens to a special arm placed behind a general one.
  • Say where a pattern's bindings are in scope, the guard and body of that arm, and how they shadow outer names.
  • Explain why an identifier in a pattern always binds, what that does to an arm named after an existing variable, and how to write the comparison with a guard.
  • Say why a pattern may bind each name only once (linearity), what that gives the matching relation and the typing rule, and how to test two components for equality instead.
  • Say what an or-pattern requires of its two sides, and why.
  • Give the types a pattern binds using p : τ ⊣ Γp, and say why T-Match requires every arm's body to have one type.
  • Use guards: when a guard runs, what a false guard does, and why a guard must be pure, including why it cannot call a function parameter.
  • Read the list patterns: [], [x], [x, ...t], and h :: t. Expand the bracket forms into conses, and write a recursive list function with one arm per way of building a list.
  • Expand e? on an Option and on a Result as a match with a return, trace where a failure leaves the function, and say what the enclosing function's result type must be.
  • Say why a top-down simplify can leave an addition of zero behind, and how simplifying the operands first changes that.
  • Recognize the design space: matching compared with unification; repeated variables in Prolog and Erlang; Python's capturing case limit:; compiling arms into a tree of tag tests; views and active patterns; match as an expression compared with a statement.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first. Once your interpreter handles match, run the programs to check yourself. The counting and level questions you check by reasoning.

  1. Counting values. How many values does each type have: Flip, (Coin, Option<Coin>), Result<(), Coin>, and Option<Option<Coin>>?

    type Coin = Heads | Tails;
type Flip = Done | Again(Coin, Bool);

  2. Levels. At what level does Succ(Succ(Zero)) first appear? Bridger accepts Fork. How many values does it have, and why?

    type Nat = Zero | Succ(Nat);
type Fork = Both(Fork, Fork);

  3. Rejected constructors. Each line, on its own, keeps a program from starting. Why?

    type Slot = Empty | Pos(Int, Int);

Pos(1)
Place(1, 2)
Pos(1, "2")
map([1, 2], Ok)
let n = None;

  4. The matching relation. Give each result: a binding, ∅, or ⊥.

    match(Mul(x, Num(1)), Mul(Num(1), Num(1)))
match(Mul(x, Num(1)), Add(Num(2), Num(1)))
match(None, None)
match(h :: t, [7])
match([a, ...t], [])
match([_], [1])

  5. Arm order and guards. What does main print, and which arm runs each time? What changes if the arm (_, 0) moves to the top?

    fn label(p: (Int, Int)) -> String = match p {
    (0, _) => "left zero",
    (x, y) if x == y => "equal",
    (_, 0) => "right zero",
    _ => "other",
};

fn main() {
    println(label((0, 0)));
    println(label((5, 5)));
    println(label((5, 0)));
    println(label((5, 6)));
}

  6. Scope. What does main print, and why?

    fn main() {
    let y = 1;
    let v = match (y + 1, y) {
        (y, 1) if y > 5 => y * 10,
        (y, _) => y + 100,
    };
    println(v);
    println(y);
}

  7. Typing patterns. What type does each of a, b, and c have, and where does the checker get it?

    fn f(p: (Option<Int>, [String])) -> String = match p {
    (Some(a), b :: c) => b ++ to_string(a + len(c)),
    _ => "none",
};

  8. Or-patterns. Why does Bridger accept the first function and reject the second?

    type Tok = Plus(Int) | Minus(Int) | End;

fn f(t: Tok) -> Int = match t {
    Plus(n) | Minus(n) => n,
    End => 0,
};

fn g(t: Tok) -> Int = match t {
    Plus(n) | End => 1,
    Minus(n) => n,
};

  9. Guards. Why does Bridger reject this guard? What would the program's behaviour depend on if it were allowed?

    ref seen = 0;
fn bump(x: Int) -> Bool { seen := deref seen + 1; x > 0 }

fn f(o: Option<Int>) -> Int = match o {
    Some(x) if bump(x) => x,
    _ => 0,
};

  10. List patterns. What does main print? Which arm handles a list of exactly one element, and why does the first arm not fit it?

    fn pairs(xs: [Int]) -> [Int] = match xs {
    [a, b, ...t] => (a + b) :: pairs(t),
    [x] => [x * 100],
    [] => [],
};

fn main() {
    println(pairs([1, 2, 3, 4]));
    println(pairs([1, 2, 3, 4, 5]));
}

  11. Propagating failure. What does main print, and why? Write the first line of the body as a match. Why would changing the result type to Result<Int, String> make this ? a type error?

    fn second(xs: [Int]) -> Option<Int> {
    let t = tail(xs)?;
    println(len(t));
    head(t)
}

fn main() {
    println(second([1, 2]));
    println(second([1]));
    println(second([]));
}

  12. Top-down simplification. Using the lecture's simplify, what is the result, and which identity did it miss?

    simplify(Mul(Add(Num(0), Num(1)), Num(9)))
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: declare a small type and list its values; draw a tree and walk a pattern over it, writing down the binding; reorder the arms of a match and predict what changes; and expand each ? in a short function by hand. If your interpreter handles match, run your programs and check yourself.
