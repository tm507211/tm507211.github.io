Quiz 4 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 10–12 and their textbook chapters: environment representations and lookup, expressions and statements, and mutation and references. One question also looks back at a design decision in your Milestone 1 evaluator. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect

Environment representations and lookup Lecture 10

Reading: Environment representations and lookup  |  Slides: Lecture 10

Be able to:

  • Describe the environment as an immutable chain of scopes, innermost first, with one binding per let, and say why leaving a block just drops the innermost link (nothing was overwritten, so nothing has to be put back — the environment is read-only).
  • Explain that a lookup is a walk outward: start at the innermost scope, take the first binding found (which is why shadowing resolves inward), and running off the end is UnboundVariable.
  • State the cost: a lookup costs its walk (the number of scopes visited), while extend (a link at the front) and leaving a block (drop the head) are each constant-time however deep the chain is — the representation puts its whole cost on the lookup.
  • Trace a lookup by hand: in { let x = 1; { let y = 2; { let z = 3; x + z } } }, say how many scopes the lookups of z and x each walk.
  • Contrast the chain with a flat map from all names in scope to values: one probe per lookup, but it must save what each binding shadows on entering a block and restore it on leaving — and say when each representation comes out ahead (frequent lookups favor the map; frequent scope changes favor the chain).
  • Give the de Bruijn index of an occurrence — the number of scopes to skip to its binder — and explain why it is computable before the program runs (lexical scope fixes the target from the text, so the count is the same on every run). Know that lexical addressing generalizes it to a ⟨scope, binding⟩ pair once a scope holds several bindings.
  • Say why Bridger keeps names rather than resolving to indices: an error reports a name (UnboundVariable, and the type errors to come), and a resolution pass buys a speed a tree-walker does not need.
  • Explain why the parent link is shared (Rc) rather than owned: a value can outlive the block that built it — a function will later carry off the scope it was defined in — so single ownership is not enough (the details are Part V's; the representation is chosen now so it can).

Expressions, statements, and blocks Lecture 11

Reading: Expressions, statements, and blocks  |  Slides: Lecture 11

Be able to:

  • Define an effect — a change a construct makes that a later step can observe, over and above the value it computes — and name Bridger's one built-in effect (mutation).
  • Describe the statement/expression line and where languages draw it: Fortran and Algol 60 kept statements in a category apart, carrying no value; Algol 68 lowered the line with units and a void type; Bridger (with ML, Ruby, Rust) draws it low.
  • Say what “drawn low” means in Bridger: if, match, while, for, and a block are all expressions with a value, and the effect-only forms (:=, a while) produce unit, ().
  • Explain why unit is the right value for an effect-only form (it reports only that the work was done) and why giving those forms a value at all lets the one expression grammar absorb them with no special case.
  • Say what remains a statement: a block item — a let or ref binding, or an expression closed with ; (its value discarded). The trailing expression with no ; is the block's value; the ; is the whole of what turns an expression into a statement.
  • Explain why let x = let y = 0; does not parse: a binding's work is to extend the environment over the rest of the block, so it is a block item, not an expression, and has no value to hand back as a right-hand side.
  • State the payoff of the low line: one eval_expr returning a Value with no eval_stmt beside it, and (later) one typing judgment — the effectful forms are handled by the same arms as 2 + 2 and return ().
  • Recognize the design space: C and Java keep the boundary, so they carry two conditionals (the if statement and the operator c ? a : b) and let a = b be an expression (hence if (x = 0) compiles); ML, Ruby, and Rust draw it low as Bridger does.

Mutation and references Lecture 12

Reading: Mutation and references  |  Slides: Lecture 12

Be able to:

  • Say why the environment alone cannot express a value that changes over time: it maps a name to a value once, and a second let makes a new binding rather than altering the first.
  • Describe the reference cell: a box whose contents a program can overwrite, with the name holding the cell's location rather than its contents. Know the tradition it comes from — ML keeps the binding immutable and adds a first-class cell, against the variable-as-cell model of Fortran, C, and Java where the name is the cell.
  • Read the store-threaded judgment ρ ⊢ ⟨e, σ⟩ ⇩ ⟨v, σ′⟩ and explain why the store goes in and out (evaluation can change a cell) while the environment ρ only goes in (no expression revises an existing binding).
  • Explain that threading the store also fixes left-to-right order: a two-operand form evaluates the first against the incoming store and the second against the store the first handed out.
  • State what each of the three forms does: ref e allocates a fresh cell and returns its location; deref e reads the cell (σ(ℓ)); e1 := e2 evaluates the cell first, then the value, writes, and returns (). A deref or := on a non-location is a runtime type error — the store's stuck case.
  • Trace aliasing: after let a = ref 0; let b = a; a := 1;, deref b is 1, because a and b hold the same location and so name one cell — a write through one is seen through the other.
  • Recognize ref x = e as sugar for let x = ref e (bind a name to a fresh cell), so the evaluator sees only the let and the ref it already has.
  • Compare the design space: variable-as-cell (C, Java, Python — every name mutable, aliasing implicit), ML's first-class cell (mutation visible as ref/deref/:=, the model Bridger follows), and Rust (mut on the binding, aliasing restricted by the borrow checker).

Looking back at Milestone 1 Reflection

Reading: Milestone M1  and its design problems.

Be able to:

  • Explain why eval_expr reports a stuck expression on the error channel (Err(Control::Raise(…))) rather than returning a special error Value or panicking: stuck is the absence of a value, so there is no value to return — reporting makes the absence observable and lets it propagate with ?, while the success path stays a plain Value.
  • Explain short-circuiting: false and (1 / 0) evaluates to false because the and arm settles the result from the left operand and never evaluates the right; an arm that evaluated both first would run 1 / 0 and get stuck.
  • Connect the two: your M1 evaluator returned a single Value (or an error) because evaluation is deterministic — e ⇩ v is a partial function, one value or none — and the rules are syntax-directed, with the two-rule forms (and, or) having mutually exclusive premises.
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: take a nested block and, by hand, draw its scope chain and count the scopes each lookup walks, then write the de Bruijn index of each occurrence; take a small program using ref, deref, and := and trace the store cell by cell, watching for two names that alias one cell; and for each design choice (chain vs. flat map, statement vs. expression, variable-as-cell vs. first-class cell) say in a sentence what each side makes easy and what it gives up.
