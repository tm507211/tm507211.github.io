Midterm Study Guide

CSCI 305: Concepts of Programming Languages

The midterm covers Lectures 1–19 and their textbook chapters, from syntax and the abstract syntax tree through programming functionally. This guide is organized by concept, not by chapter. It lists what you should be able to do, not the questions you will be asked. Almost every question gives you a small piece of Bridger code and asks what it evaluates to or prints, and why. Answers are short: a few sentences, in your own words, earns full credit.

What to expect
When
In class, on the date shown in the schedule.
Length
The full class period, 50 minutes.
Rules
Closed book, handwritten.
Format
About ten short conceptual questions, each about the size of a quiz question. Most give you a block of Bridger code to trace by hand. Some ask you to draw something: an abstract syntax tree, an environment, or a derivation tree. When a question needs an evaluation rule, the rule is printed on the exam. You will not write any code, in Bridger or in Rust.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-Let, E-App) if it helps, but you are never required to.

Reading Bridger code All lectures

Reading: Appendix B (grammar)  |  Appendix C (prelude)

Be able to:

  • Trace a short program by hand and say exactly what it prints, line by line, including what it prints before it gets stuck.
  • Read a block as an expression: its value is its last expression, and a block ending in ; is ().
  • Read the operators by precedence: * / % before + -, before comparisons, before and, before or; / on integers discards the remainder.
  • Read fn declarations, lambdas (|x: Int| e), function types (fn(Int) -> Int), and calls of a function held in a cell, (deref f)(x).
  • Know what the prelude's map, filter, fold, and range do, and in what order they call the function you give them.

Syntax, semantics, and the abstract syntax tree Lectures 2–3

Reading: Syntax and semantics  and The abstract syntax tree  |  Slides: Lecture 2, Lecture 3

Be able to:

  • Say whether an error is a syntax error or a semantic one.
  • Draw the abstract syntax tree for an expression, using precedence and associativity to decide its shape, and say why the evaluator never needs either rule.
  • Explain why the concrete syntax (x + y, (+ x y), x y +) can vary while the tree stays the same.

Evaluation rules and stuck expressions Lectures 4–7

Reading: Values and runtime errors, Tree-walking evaluation, Error handling, Program semantics  |  Slides: Lectures 4, 5, 6, 7

Be able to:

  • Read a big-step rule premise by premise, and say which premise fails when an expression is stuck.
  • Build a derivation tree for a small expression from rules you are given, one rule per node of the AST.
  • Explain stuck as the absence of a derivation, and say how the interpreter makes that absence visible (the error side of Result).
  • Explain short-circuit and/or: why the right operand may never be evaluated, and so may never get the chance to be stuck.
  • Tell equality (structural, for any two values) apart from ordering (integers only).
  • Compare ways to report an expected failure: exceptions, error values (Result), and aborting the program.

Environments and lexical scope Lectures 8–10

Reading: Environments and let, Lexical scope, Environment representations and lookup  |  Slides: Lectures 8, 9, 10

Be able to:

  • Say which binding each use of a name reads: the nearest enclosing let whose scope (the rest of its block) contains it.
  • Explain why a let's right-hand side sees the enclosing binding of its own name.
  • Explain shadowing: a new binding hides an old one until its block ends, and nothing is overwritten.
  • Draw the environment at a point in a program as a chain of bindings, innermost first, and count the bindings a lookup reads before it finds its name.
  • Explain why lexical scope lets that count be worked out before the program runs.

Imperative programming Lectures 11–13

Reading: Expressions, statements, and blocks  and Conditionals and loops  |  Slides: Lectures 11, 12, 13

Be able to:

  • Explain why Bridger treats if, loops, and assignment as expressions, and why the effect-only ones evaluate to ().
  • Trace a while or for loop over cells and give the final contents of each cell.
  • Explain why a loop that never stops has no derivation.
  • Follow a return out through if, loops, and blocks to the call that catches it, and say what the call then evaluates to.
  • Say which function a return inside a lambda leaves.

Mutable and immutable references Lectures 11–12

Reading: Mutation and references

Be able to:

  • Explain why a let binding never changes, and where change lives instead: a cell made by ref, read by deref, written by :=.
  • Separate the environment (name → location) from the store (location → value), and say which of the two each of let, ref, deref, and := touches.
  • Tell an alias apart from a copy: let b = a shares a cell; ref deref a makes a new one.
  • Predict what a program prints when two names reach one cell.

Functions and closures Lectures 14–16

Reading: First-class functions, Evaluating function calls, Closures  |  Slides: Lectures 14, 15, 16

Be able to:

  • Explain what makes functions first-class: passed, returned, and stored like any other value.
  • Give the order in which a call evaluates its parts (the function, then the arguments left to right, then the body) and use it to predict printed output.
  • Explain what a closure captures, and why its body runs in that captured environment rather than the caller's.
  • Explain how a closure can outlive the call that created it, and how two closures can share one cell.
  • Compare call by value with call by name and call by need.

Static and dynamic scoping Lecture 17

Reading: Static vs. dynamic scope  |  Slides: Lecture 17

Be able to:

  • Trace one program under both rules: static scope looks a free name up where the function was written; dynamic scope looks it up among the calls still in progress, most recent first.
  • Explain why a function returned from another loses its free names under dynamic scope.
  • Explain why dynamic scope makes a function's meaning depend on who calls it, and why Bridger is statically scoped.

Recursion Lecture 18

Reading: Recursion and higher-order functions  |  Slides: Lecture 18

Be able to:

  • Trace a recursive function and count the calls active at its deepest point.
  • Explain why a top-level fn can call itself but a lambda bound by let cannot, and how a cell can tie the knot instead.
  • Explain why each call takes a stack frame, what happens when a recursion runs too deep, and why writing it in tail form does not help in Bridger (no tail-call elimination).

Higher-order functions and functional programming Lectures 18–19

Reading: Recursion and higher-order functions  and Programming functionally  |  Slides: Lecture 18, Lecture 19

Be able to:

  • Evaluate a pipeline of map, filter, and fold by hand.
  • Read functions that take or return functions: composition, partial application, and currying.
  • Say whether a function is pure, and what referential transparency buys: a call can be replaced by its value.
  • Explain why rewriting a pipeline (for example, fusing two maps into one) is safe for pure functions but can change what a program does when a stage has a side effect.
  • Rewrite a loop over cells as a fold in your head, and say what state each version keeps.

Sample questions Practice

These are the same kind and size of question as the midterm, on different programs. No answers are given: work each one by hand first, then, if you have the interpreter built, run the program to check yourself. Unless a question says otherwise, there is no type checker.

  1. Abstract syntax tree. Draw the abstract syntax tree of this expression. What value does it evaluate to?

    8 / 2 / 2 + 3 * 2 < 10

  2. Stuck expressions. For each expression, give the value it evaluates to or write stuck and why it is stuck.

    expressionvalue, or stuck and why
    true or (1 / 0 == 0)
    (1, 2) == (1, 2)
    -true
    "a" < "b"
    [1, 2] == [2, 1]
    7 % 0

  3. Derivation trees. Using the rules below, draw the derivation tree for (9 / 3 > 2) and (1 < 0) and give its value. Label each step with its rule.

    E-Lit       n ⇓ n

E-Div       e1 ⇓ v1    e2 ⇓ v2    v1, v2 ∈ ℤ    v2 ≠ 0
            ───────────────────────────────────────────
                         e1 / e2 ⇓ v1 ÷ v2

E-Ord       e1 ⇓ v1    e2 ⇓ v2    v1, v2 ∈ ℤ
            ───────────────────────────────────    (⊗ is <, <=, >, >=)
                   e1 ⊗ e2 ⇓ (v1 ⊗ v2)

E-And-True  e1 ⇓ true    e2 ⇓ v    v ∈ 𝔹
            ─────────────────────────────
                    e1 and e2 ⇓ v

  4. Reading scopes. What does main print? For each m and n on the right of an =, say which binding it reads.

    let n = 2;
fn main() {
    let m = n + 1;
    let n = m * n;
    {
        let m = n - m;
        let n = m + 10;
        println(n);
    };
    println(n + m);
}

  5. Environments. Draw the environment in which x + y is evaluated, innermost binding first. How many bindings must be read to look up x and y, and what does the block evaluate to?

    { let x = 10;
  { let y = x + 1;
    { let x = y * 2;
      { let y = x - y; x + y } } } }

  6. Aliasing cells. What does main print and why? Draw the store after the two assignments.

    fn main() {
    let p = ref 5;
    let q = ref deref p;
    let r = p;
    p := deref q * 2;
    q := deref r + 1;
    println(deref p);
    println(deref q);
    println(deref r);
}

  7. Returning early. What does main print? Can the final 0 in first_square_over ever be its result? Why or why not?

    fn first_square_over(limit: Int) -> Int {
    let i = ref 1;
    while true {
        if deref i * deref i > limit { return deref i; }
        i := deref i + 1;
    }
    0
}
fn main() {
    println(first_square_over(20));
    println(first_square_over(0) * 100);
}

  8. Static and dynamic scoping. What does this program print in Bridger? What would it print under dynamic scoping? Explain why the two outputs differ.

    let scale = 10;
fn bump(x: Int) -> Int = x + scale;
fn twice(f: fn(Int) -> Int, x: Int) -> Int = f(f(x));
fn main() {
    let scale = 1;
    println(twice(bump, 0));
}

  9. Recursion through a cell. This program prints 120. A version that wrote let f = |n: Int| ... f(n - 1) ... would get stuck. Why does this one work? Why must the call be written (deref f)(n - 1) and not deref f(n - 1)?

    fn main() {
    ref f: fn(Int) -> Int = |n: Int| 0;
    f := (|n: Int| if n == 0 { 1 } else { n * (deref f)(n - 1) });
    println((deref f)(5));
}

  10. Tail calls. The first line prints 5050; the second gets stuck. Why, even though the recursive call is the last thing sum_to does? What would a language with tail-call elimination do instead?

    fn sum_to(n: Int, acc: Int) -> Int =
    if n == 0 { acc } else { sum_to(n - 1, acc + n) };
fn main() {
    println(sum_to(100, 0));
    println(sum_to(1000000, 0));
}

  11. Higher-order functions. What does main print? For each line, say which functions are passed as arguments and which are returned as results.

    fn compose(f: fn(Int) -> Int, g: fn(Int) -> Int) -> fn(Int) -> Int =
    |x: Int| f(g(x));
fn add(k: Int) -> fn(Int) -> Int = |x: Int| x + k;
fn main() {
    let h = compose(add(1), |x: Int| x * 3);
    println(map([1, 2, 3], h));
    println(fold(map([1, 2, 3], add(10)), 0, |acc: Int, x: Int| acc + x));
    println(filter(range(1, 7), |x: Int| x % 2 == 0));
}

  12. Purity. What does main print? Is tick a pure function? Could a programmer replace the second map with let b = a; without changing what the program prints? Why or why not?

    let calls = ref 0;
fn tick(x: Int) -> Int { calls := deref calls + 1; x + deref calls }
fn main() {
    let a = map([10, 20], tick);
    let b = map([10, 20], tick);
    println(a);
    println(b);
    println(a == b);
}
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. The six quizzes are the next best thing: redo them without looking at your answers. Beyond that, write small programs and predict their output before you run them: shadow a name inside a block; make two names for one cell and a copy of it; put a return inside a loop; return a closure from a function and call it from a scope that binds the same names; write a recursive function both at the top level and as a let-bound lambda; and run a map whose function prints. If you have the interpreter built, run your programs and check yourself.
