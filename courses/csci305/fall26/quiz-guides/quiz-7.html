Quiz 7 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 20–21 and their textbook chapters: why types, type checking and unification, and function types and polymorphism. Lecture 21 is covered through Generic values; let-bound lambdas, let-generalization, and the rest of that lecture are not on this quiz. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 15 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions, each about a small block of Bridger code. Most ask whether Bridger's type checker rejects the program and why; one also asks what the program prints with no type checker. One gives a short list of generic declarations to sort into accepted and rejected. You will not write any code, in Bridger or in Rust.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (T-If, Chk-Lam, T-Inst) if it helps, but you are never required to.

Why types? Lecture 20, first half

Reading: Why types? From runtime errors to static checking  |  Slides: Lecture 20

Be able to:

  • Explain how a type error behaves with no checker: it is found only when the bad expression runs, after earlier output has already been printed, and an annotation that is never checked may not fail at all (double("ab") prints abab).
  • Say what a static pass changes: the checker runs between parsing and evaluation, so a rejected program prints nothing.
  • Read the typing judgment ⊢ e : τ beside e ⇓ v: a type says what kind of value an expression will produce, without computing it. Compare T-Arith with E-Add, and the one T-If rule with the two E-If rules.
  • Build a small typing derivation, and say which premise fails for an expression that has no type (1 + false).
  • Explain why a checker is conservative: T-If types both branches without knowing which runs, so a program can run without going wrong and still be rejected. An exact checker would decide the halting problem.
  • Sort errors into those the checker rules out (1 + true, 5(3), a wrong number of arguments, an unbound name) and those it cannot (division by zero, deep recursion, failed input).
  • Retell the history in outline: types first told the machine how to store a value (FORTRAN, Algol, typeless B, C); Hoare argued the same information catches the programmer's mistakes; Milner's “well-typed expressions do not go wrong.”

A type checker Lecture 20, second half

Reading: A type checker  |  Slides: Lecture 20

Be able to:

  • Compare the typing context Γ (name ↦ type, before the program runs) with the environment ρ (name ↦ value, while it runs). Say why lexical scope lets the checker build Γ from the program text, and how a let that shadows a name at a different type is handled.
  • Read T-Lam and T-App, and give the function type of a small lambda. Say what T-Lam leaves unsaid: where the parameter's type comes from.
  • Distinguish the two modes of a bidirectional checker: synthesize (e ⇒ τ, work the type out) and check (e ⇐ τ, the type is given). Explain how Chk-Lam takes a lambda's parameter types from the type it is checked against, e.g. a function parameter's declared type.
  • Predict where an error is reported in a lambda passed to a function, and what a checker that synthesized the lambda's type first would report instead.
  • Trace inference variables through a declaration: give an unannotated parameter a fresh variable α, collect what the body requires of it, and solve it.
  • Unify two types by hand: the same constructor unifies part by part, an unsolved variable is solved, anything else is a mismatch. Give the solutions, or say why it fails.
  • Explain why let xs = []; followed only by len(xs) needs an annotation: every variable must be solved by the end of its declaration.
  • Explain the occurs check: derive the equation that self-application or a list containing itself produces (α = fn(α) → β, α = [α]), and why no finite type satisfies it.
  • Describe the shape of check_expr in Milestone M5: expected: Some(τ) checks, None synthesizes, and an arm that needs two types to agree calls unify, not ==.

Function types and polymorphism Lecture 21, through “Generic values”

Reading: Function types and polymorphism  |  Slides: Lecture 21

Be able to:

  • Explain why a checker with only monomorphic types rejects id used at Int and at String, and compose written at Int applied to a String stage, though both programs run.
  • Distinguish Strachey's two kinds of polymorphism: ad hoc (different code at each type, like + or Bridger's ++) and parametric (one definition, the same at every type).
  • Contrast type parameters written by the programmer (Reynolds, CLU) with types inferred at each use (Milner, Damas–Milner), and say which parts of each Bridger takes.
  • Explain how the top-level context Γ0 is built from the signatures alone, so bodies can be checked in any order and mutually recursive functions need nothing extra. Say why a global let g = |x| x; is rejected even if a later function calls g(1).
  • Read a type scheme such as ∀T. fn(T) → T, and write the signature of a generic function, e.g. compose<A, B, C>, saying which type parameters are shared.
  • Say what a generic body may do with a T (return it, pass it on, store it in a list, tuple, or cell) and what it may not (arithmetic, equality, printing). Explain why two different type parameters cannot be treated as equal.
  • Read T-Fn and T-Inst. Explain why the checker gives each use of a generic function fresh inference variables, and trace a generic call such as compose(|n| n + 1, |s: String| len(s)) to its solutions.
  • Explain that instantiation happens where the generic function's name is written: map(xs, id) instantiates id, and let f = id; binds f to one instance, so f cannot be used at two types.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first, then, if you have the interpreter built, run the program to check yourself — at Milestone M4 for “no type checker”, and at M5 for the checker.

  1. Checking before running. What is the output of this program on an interpreter without type checking? When type checked, does the type checker report any errors? If so, which error and why?

    fn safe_div(a: Int, b: Int) -> Int =
    if b == 0 { "undefined" } else { a / b };
fn main() {
    println(safe_div(10, 2));
    println(safe_div(9, 3));
    println(safe_div(1, 0));
}

  2. Checking a lambda. Why is this program rejected by Bridger's type checker? Where is the error reported?

    fn keep(f: fn(Int) -> Bool, xs: [Int]) -> [Bool] = map(xs, f);
fn main() {
    println(keep(|n| n > 2, [1, 5]));
    println(keep(|n| not n, [1, 5]));
}

  3. Typing nest. Why is this program rejected by the type checker? Would it run without one?

    fn main() {
    let nest = |x| [x, [x]];
    println(2);
}

  4. Instantiation. This program is rejected. Which line is the type error reported on and why? Which change to that line would make the program type-check?

    1  fn first<A, B>(p: (A, B)) -> A = p.0;
2  fn main() {
3      println(first((1, "a")));
4      println(first(("b", 2)));
5      let f = first;
6      println(f((3, "c")));
7      println(f(("d", 4)));
8  }

  5. Inside a generic body. Write if each declaration is accepted or rejected by the type checker. If rejected also briefly describe why.

    declarationaccepted, or rejected and why
    fn twice<T>(f: fn(T) -> T, x: T) -> T = f(f(x));
    fn neg<T>(x: T) -> Bool = not x;
    fn wrap<T>(x: T) -> [[T]] = [[x]];
    fn less<T>(a: T, b: T) -> Bool = a < b;
    fn flip<A, B>(p: (A, B)) -> (A, B) = (p.1, p.0);
    fn is_zero<T>(a: Int, b: T) -> Bool = a == 0;
    fn echo<T>(x: T) -> T { println(x); x }
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: write an if whose untaken branch has the wrong type and run it with and without the checker; pass a lambda whose body misuses its parameter to a function that declares the parameter's type, and predict where the error lands; give a lambda's parameter a fresh α and solve it by hand; unify a few pairs of types, including one that fails the occurs check; and write a generic function, call it at two types, then bind it with let and try again. If you have the interpreter built, run your programs and check yourself.
