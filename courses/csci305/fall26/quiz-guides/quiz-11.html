Quiz 11 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 29 and 30 and their textbook chapters: exhaustiveness checking, and structs with methods. Type checking of structs and method calls is not on this quiz. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 15 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions, each asking one thing. Most give you a small Bridger program — say whether a match covers every value and what it misses, why a program is rejected, or what it prints.
Answers
Explanations in your own words — no memorized dates or trivia. You will not be asked to trace the usefulness algorithm (U, S, D) step by step; reasoning about which values each arm covers is enough.

Exhaustiveness checking Lecture 29

Reading: Exhaustiveness Checking  |  Slides: Lecture 29

Be able to:

  • Say what it means for a list of arms to be exhaustive for a type, and what happens to a program with a gap: with the checker, and on the untyped path at run time.
  • Decide whether a match is exhaustive by reasoning about which values each arm covers. If it is not, give a value no arm matches, or describe all of them as a pattern.
  • Find a gap that only appears in a combination of components, as in zip_with, where each column looks covered on its own.
  • Give a type's signature, its set of head constructors, and say which types have a finite one (Bool, tuples, lists, Option, declared types, structs) and which do not (Int, String, functions, a type parameter). Say why only a wildcard or variable can complete the arms of a type without one.
  • Explain why a finite set of patterns can be checked against a type with infinitely many values, such as [Int].
  • Say why a guarded arm does not count toward coverage, and why a match whose guards together cover every value is still rejected. Fix one by changing a single arm.
  • State the idea behind the check: arms are exhaustive when a wildcard added after them could never match anything they miss. Say what an unreachable arm is, and that Bridger accepts one without comment.
  • Say what a catch-all arm hides when a constructor is added to a type later.
  • Recognize the design space: rejecting a gap (Rust, Swift, Elm, Bridger) compared with warning about it (OCaml, GHC, Scala); languages without the check (Python, TypeScript's never idiom); open types (#[non_exhaustive], Swift's @unknown default, Java's sealed hierarchies); printing a missing value.

Structs with methods Lecture 30

Reading: Structs with Methods  |  Slides: Lecture 30

Be able to:

  • Say what goes wrong when two different things share a tuple type such as (Int, Int), and how naming the type and each field prevents it.
  • Compare a tuple, a one-constructor type, and a struct as ways to write a product: which have a name, which name their components, and how each is read back.
  • Count a struct's values as a product of its fields' counts.
  • Apply E-Struct: a literal evaluates its fields in the order written, and the value holds them in the order the declaration lists them. Say when two struct values are equal under ==, and what a literal that omits, repeats, or invents a field does.
  • Apply E-Field, and tell field access (p.x) apart from tuple projection (t.0).
  • Read an impl block: a method with self is called on a value, an associated function without self is called on the type's name, and the type name evaluates to a value standing for the type.
  • Say what a method body can see: self, its parameters, and the top-level names, but not the caller's locals.
  • Explain why a method that "changes" a struct returns a new one, and how a ref field lets two copies of a struct share state.
  • Recognize the design space: Hoare's record classes and Simula's classes; fields and methods declared together (Java, C++) compared with separate impl blocks (Rust, Go); an implicit this compared with an explicit self; uniform call syntax in D and Nim; functional update in OCaml and Rust; nominal compared with structural record types.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first. Once your interpreter handles match and structs, run the programs to check yourself.

  1. Nested patterns. Is this match exhaustive? If it is not, give a value that no arm matches.

    fn g(p: (Bool, Option<Bool>)) -> Int = match p {
    (true, None) => 0,
    (_, Some(false)) => 1,
    (false, _) => 2,
};

  2. Lists. Is this match exhaustive? If it is not, describe every list that no arm matches, and write one arm that closes the gap.

    fn sum3(xs: [Int]) -> Int = match xs {
    [] => 0,
    [x] => x,
    [x, y] => x + y,
};

  3. Guards. Every Option<Bool> fits one of these arms when the program runs, yet the checker rejects the match. Which value does the checker consider missing, and why?

    fn describe(o: Option<Bool>) -> String = match o {
    Some(b) if b => "yes",
    Some(false) => "no",
    None => "none",
};

  4. What a wildcard hides. Neg(Arith) was just added to Arith. The checker rejects one of these functions and accepts the other. Which, and what does depth(Neg(Add(Num(1), Num(2)))) return?

    type Arith = Num(Int) | Add(Arith, Arith) | Mul(Arith, Arith) | Neg(Arith);

fn show(e: Arith) -> String = match e {
    Num(n) => to_string(n),
    Add(l, r) => "(" ++ show(l) ++ " + " ++ show(r) ++ ")",
    Mul(l, r) => "(" ++ show(l) ++ " * " ++ show(r) ++ ")",
};

fn depth(e: Arith) -> Int = match e {
    Add(l, r) => 1 + max(depth(l), depth(r)),
    Mul(l, r) => 1 + max(depth(l), depth(r)),
    _ => 0,
};

  5. Struct literals. What does main print?

    struct Pair { left: Int, right: Int }

fn note(n: Int) -> Int { println(n); n }

fn main() {
    let p = Pair { right: note(2), left: note(1) };
    println(p);
    println(p == Pair { left: 1, right: 2 });
}

  6. Methods and shared state. What does main print?

    struct Account { owner: String, balance: ref<Int> }

impl Account {
    fn open(owner: String) -> Account =
        Account { owner: owner, balance: ref(0) };
    fn deposit(self, n: Int) { self.balance := deref self.balance + n; }
    fn rename(self, owner: String) -> Account =
        Account { owner: owner, balance: self.balance };
}

fn main() {
    let a = Account.open("ann");
    let b = a.rename("bo");
    a.deposit(5);
    b.deposit(10);
    println(a.owner);
    println(b.owner);
    println(deref a.balance);
}
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: take a match over a small type, list every value of the type, and name the arm that catches each one; delete an arm and find the value that falls through; add a constructor to a type and see which functions the checker flags. For structs, predict what a program prints before running it, paying attention to field order and to which values share a ref.
