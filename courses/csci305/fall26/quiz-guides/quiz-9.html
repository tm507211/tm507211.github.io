Quiz 9 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 25–27 and their textbook chapters: evaluating relations by rounds, rule bodies with their safety and purity checks, and querying relations from ordinary code. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 20 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions, each asking one thing. Most give you a small Bridger program — say what it prints or why it is rejected, and why. Others ask you to trace evaluation round by round, or to decide which functions are impure.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-For-Query, P-Call) if it helps, but you are never required to.

Evaluating relations Lecture 25

Reading: Evaluating Relations  |  Slides: Lecture 25

Be able to:

  • Say what the immediate-consequence operator TP computes from a set of facts: the recorded facts plus every head that one rule step derives. Read “closed” (firing the rules adds nothing) and “fixed point” in terms of it, and say what makes it monotone.
  • Run the rounds by hand: start from the recorded and program facts, apply the rules, and list the facts each round adds. Stop at the first round that adds nothing.
  • Relate a fact's round to its derivation: a fact enters in round i when its shortest derivation needs i rule steps.
  • Explain why the rounds stop, even on a cycle: rule terms are variables and literals, so every value in a derived fact was already in the program or Δ. That leaves finitely many possible facts, and each round before the last adds at least one.
  • Explain why the facts the rounds stop at are exactly M(P, Δ).
  • Say which rule instances semi-naive evaluation fires, those with a premise that was new in the previous round, and why it cannot miss a fact.
  • Say why an engine can continue from its closure after an add, and why it cannot after a clear.
  • Recognize the design space: Prolog's search from the query, which keeps only its current path and can run forever on a cycle, compared with rounds, which keep every fact derived and compute all of them whatever the query asks.

Rule bodies and safety Lecture 26

Reading: Rule Bodies and Safety  |  Slides: Lecture 26

Be able to:

  • Sort a rule's conjuncts into generators (relation atoms, which bind variables by matching facts) and filters (any other expression, which tests values it already has and binds nothing).
  • Fire a rule by hand: each generator grows or shrinks the set of substitutions, each filter only keeps or drops them, and what remains gives the derived facts.
  • State the safety condition, that a generator of the same rule binds every head variable and every variable a filter reads, and use it to say why a rule is rejected. A filter may also name a top-level definition, but a rule never sees a query's locals.
  • Explain what would go wrong without it: == binding a variable lets a rule produce values no fact contains, so the rounds might never stop, and a head variable with no source leaves a fact that is not ground.
  • Explain why a filter must be pure, using each case: hidden state (two correct engines could disagree), effects (the evaluation strategy would become visible in the output), and queries (asking for a fact's absence breaks monotonicity, so the rounds can stop at the wrong answer).
  • Apply the purity judgment: literals, variables, operators over pure operands, and calls to functions in Φ. Name forms that have no purity rule, such as deref, add, solutions, and queries.
  • Compute the set I of impure functions as a least fixpoint on the call graph: start empty, add a function whose body has an effect or calls a function already in I, and stop when nothing changes. Say why a cycle with no effect stays out of I.
  • Explain why purity is not enough: a filter must also finish, so no function it reaches may recurse. Say why these are two separate checks on the same call graph.
  • Say when the order of a body's filters matters: only when a filter can get stuck, such as a division by zero that an earlier filter would have guarded.
  • Recognize the design space: stratified negation, layer numbers, and why stays and leaves have none; systems that let == bind computed values; aggregates inside a rule language.

Querying relations Lecture 27

Reading: Querying Relations from the Host Language  |  Slides: Lecture 27

Be able to:

  • Use each place a query can appear: where a Bool is expected (is there a solution?), solutions q (a list of hole values), and for q { … } (once per solution, with the holes bound in the body).
  • Say what a solution is: an assignment to the distinct named holes, with each distinct assignment counted once. An anonymous hole ? requires a value to exist and does not record it, and a hole named twice is one variable.
  • Predict the result of projecting: why dropping a name from a query can shrink the list, and why that changes a total computed from it. To sum a column across rows, keep a key among the named holes.
  • Give a query's type from its form: no named holes gives [()], one gives a list of that column's type, two or more give a list of tuples, and a bare query is a Bool whatever its holes. Say why type errors in a query are caught before main.
  • Explain how a value reaches a query: an argument is evaluated where the query is asked, then acts as a constant, and it is the only thing a query takes from its surroundings.
  • Trace hole scope: a hole introduces a new name in a for body, which can shadow a local of the same name. Say why a bare query binds nothing, so using its hole afterward is an unbound variable error.
  • Trace a walk that changes its own relation: a for reads its solutions once, from the facts present when it starts, while a query inside the body reads the current facts. A list from solutions is an ordinary value and holds still in the same way.
  • Work across the boundary: use ordinary code for what a rule cannot do, namely computing new values, testing for absence, and aggregating (len, fold). Say why rules always stop while a host while over the same facts might not.
  • Recognize the design space: the Halloween problem and why a single SQL UPDATE separates the rows it finds from its scan; loops elsewhere that change what they walk (Python's dict raises an error, its list keeps walking); SQL's bags compared with Bridger's sets. From the reading: queries embedded in a language compared with queries sent as strings, including SQL injection and queries built at run time.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first, then, if you have the interpreter built through M6, run the program to check yourself. The rounds and the purity questions you check by reasoning.

  1. Rounds. Which route facts does each round of evaluation add, and how do you know when to stop?

    relation road  : (String, String);   relation route : (String, String);
rule route(x, y) :- road(x, y);
rule route(x, z) :- route(x, y) and road(y, z);

fn main() {
    add road("a", "b");  add road("b", "a");  add road("b", "c");
    println(solutions route(?x, ?y));
}

  2. Semi-naive evaluation. Round 2 of this program adds path("a", "c") and path("b", "d"). Which instances of the second rule does semi-naive evaluation fire in round 3, and why is it safe to skip the others?

    relation edge : (String, String);   relation path : (String, String);
rule path(x, y) :- edge(x, y);
rule path(x, z) :- path(x, y) and edge(y, z);

fn main() {
    add edge("a", "b");  add edge("b", "c");  add edge("c", "d");
    println(solutions path(?x, ?y));
}

  3. Safety. Why does Bridger reject this rule, and what could it mean if it were allowed?

    relation person : (String);   relation knows : (String, String);
rule knows(x, y) :- person(x);

fn main() {
    add person("ann");
    println(solutions knows(?x, ?y));
}

  4. Purity. Which functions are impure, and why?

    fn log(x: Int) -> Int { println(x); x }
fn twice(x: Int) -> Int = log(x) + log(x);
fn square(x: Int) -> Int = x * x;
fn ping(x: Int) -> Bool = pong(x);
fn pong(x: Int) -> Bool = ping(x);

fn main() { println(square(3)); }

  5. Filters must finish. ping and pong have no effects. Why does Bridger still reject this rule?

    relation num : (Int);   relation r : (Int);
fn ping(x: Int) -> Bool = pong(x);
fn pong(x: Int) -> Bool = ping(x);
rule r(x) :- num(x) and ping(x);

fn main() { println(solutions r(?x)); }

  6. Hidden state. Reading a ref changes nothing, yet Bridger rejects this filter. What could go wrong if it were allowed?

    relation score : (String, Int);   relation passed : (String);
ref cutoff = 60;
rule passed(s) :- score(s, n) and n >= deref cutoff;

fn main() {
    add score("ann", 70);
    println(solutions passed(?s));
    cutoff := 80;
    println(solutions passed(?s));
}

  7. A fixed walk. What does main print, and why?

    relation guest : (String);

fn main() {
    add guest("ann");  add guest("bob");
    for guest(?g) {
        add guest(g ++ "+1");
        println(g);
        println(len(solutions guest(?x)));
    }
    let found = solutions guest(?x);
    add guest("cy");
    println(len(found));
    println(len(solutions guest(?x)));
}

  8. Projection. What does main print, and why?

    relation score : (String, String, Int);

fn main() {
    add score("ann", "q1", 8);  add score("ann", "q2", 9);
    add score("bob", "q1", 8);  add score("bob", "q2", 7);
    println(len(solutions score(?who, ?quiz, ?n)));
    println(len(solutions score(?, ?quiz, ?n)));
    println(len(solutions score(?who, ?, ?)));
    println(solutions score(?, ?, ?));
}

  9. Hole scope. What does main print, and why?

    relation team : (String, String);

fn main() {
    add team("ann", "red");  add team("bob", "blue");  add team("cy", "red");
    let t = "red";
    for team(?t, t) { println(t); }
    println(t);
}

  10. Across the boundary. The first println runs and prints a result, but the program then never finishes. Why does the rule's evaluation stop when the while does not?

    relation needs  : (String, String);   // needs(a, b): a needs b first
relation before : (String, String);
relation done   : (String);
rule before(b, a) :- needs(a, b);
rule before(b, a) :- needs(a, c) and before(b, c);

fn ready(s: String) -> Bool =
    not done(s) and filter(solutions needs(s, ?b), |b| not done(b)) == [];

fn main() {
    add needs("bake", "mix");  add needs("mix", "bake");
    println(before(?s, ?s));
    let steps = ["mix", "bake"];
    while len(solutions done(?d)) < len(steps) {
        for s in filter(steps, ready) { add done(s); }
    }
}
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: write a small relation with a cycle and list its facts round by round; change a filter until Bridger rejects it and read the error it gives; draw the call graph of a few functions and compute I by hand; ask one query with its holes named, then anonymous, and predict each list; and write a for whose body adds to the relation it walks. If you have the interpreter built, run your programs and check yourself.
