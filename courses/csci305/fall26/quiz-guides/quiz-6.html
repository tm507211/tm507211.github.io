Quiz 6 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 15–17 and their textbook chapters: evaluating function calls, closures, and static vs. dynamic scope. Recursion (Lecture 18) is not on this quiz. One question also looks back at a design decision in your Milestone 3 evaluator. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 15 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions. Most give you a small block of Bridger code to trace by hand — say what it evaluates to or what it prints, and why. One asks you to compare static and dynamic scope on the same program. One question looks back at your Milestone 3 evaluator — no Rust to write, just explain a decision in words.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-App, E-Ref) if it helps, but you are never required to.

Evaluating function calls Lecture 15

Reading: Evaluating function calls  |  Slides: Lecture 15

Be able to:

  • Read E-App premise by premise: evaluate the operator to a closure; evaluate the arguments left to right, threading the store; run the body in the closure's captured environment extended with the parameters.
  • Trace a call whose arguments change a cell, and say what it evaluates to under Bridger's left-to-right order — and what a right-to-left order would give instead.
  • Say when each stuck call is detected: a non-function operator before any argument runs (NotAFunction); a wrong number of arguments only after they have all run (ArityMismatch). Predict what a stuck call prints before it stops.
  • Explain how a return is caught by the call (unwrap), so the expression around the call carries on normally.
  • Compare approaches to evaluation order: fixed left to right (Bridger, Java), unspecified (Scheme), and C, where f(i++, i++) is undefined.

Closures Lecture 16

Reading: Closures  |  Slides: Lecture 16

Be able to:

  • Explain why make_adder and make_counter need a binding to last longer than the call that created it, and why a stack of activation records, which pops a call's bindings when it returns, cannot provide that.
  • Distinguish a binding's scope (a region of program text) from its extent (a span of time during one run), and say why a closure separates them.
  • Follow make_adder(5) then add5(10) through E-App and E-Lam: the binding k ↦ 5 lives inside the returned closure, and no rule ever discards an environment.
  • Explain state in a captured cell: the binding n ↦ ℓ never changes; the store's entry for ℓ does. Say why two calls of make_counter give independent counters (E-Ref picks a fresh location each time), and when two closures share one cell (both captured from the same call, or one closure value copied by let).
  • Predict what closures built inside a loop return: a for variable is a fresh binding to a value on each turn; a cell is one location, read when the closure is called. Fix a loop so each closure keeps the value a cell held on its own turn (let v = deref j;).
  • Explain why the provided Rc<Scope> chain keeps a captured scope alive exactly as long as something can still reach it, and why Rust rejects a closure that borrows a local and outlives the function (E0373).
  • Recognize the design space: capturing variables (Scheme, JavaScript, Python) vs. values (C++ [=], Rust move); Java's effectively-final rule and Bridger's immutable bindings; loop variables made fresh per turn (ES2015 let, C# 5 foreach, Go 1.22); environments on a stack (Algol, GNU C nested functions) vs. in the heap.

Static vs. dynamic scope Lecture 17

Reading: Static vs. dynamic scope  |  Slides: Lecture 17

Be able to:

  • State the one premise in which E-App and E-App-Dyn differ: the body runs in the closure's captured environment, or in the caller's environment, extended with the parameters. Say why a function value under dynamic scope needs no environment at all.
  • Trace a short program under both rules: under dynamic scope a free name finds the most recent binding of that name made by any call still in progress.
  • Explain what breaks under dynamic scope: a body's meaning depends on its callers; renaming a parameter can change what another function computes; a returned function loses its free names (make_adder has no dynamically scoped version).
  • Retell the Lisp history in outline: McCarthy's a-list eval looked up free variables where a function was applied; Slagle's program exposed it; Russell's FUNARG device carried the environment along — a closure under another name.
  • Explain why Bridger stays statically scoped: a checker that checks each body once, against the names where it is written, cannot give a dynamically scoped free name a single type.
  • Recognize where dynamic binding is kept on purpose: Emacs Lisp's default, Common Lisp special variables, Scheme's parameterize, Perl's local, shell function locals, and the way exception handlers are found.

Looking back at Milestone 3 Reflection

Reading: Milestone M3  and Conditionals and loops.

Be able to:

  • Explain why your Return arm builds Err(Control::Return(v)) rather than an ordinary Ok(v): every ? between the return and its boundary passes it straight out, abandoning the rest of a block and the remaining turns of a loop. Say what a program would compute if it were an ordinary value instead.
  • Say what catches a return at M3 (nothing you wrote; it reaches the top) and what will at M4 (the Call arm, which turns it into the call's ordinary value while still passing errors through).
  • Explain aliasing through one store: let b = a copies a location, so b := 9 is seen by deref a — the same reason two closures from one call share a cell.
  • Say why while and for evaluate to () and discard their body's value, and why your for arm extends the environment afresh for each element.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first, then, if you have the interpreter built, run the program to check yourself. In every program, trace prints its label and returns its number: 

fn trace(label: String, v: Int) -> Int { println(label); v }

  1. Order of evaluation. When main is evaluated, what is printed before evaluation gets stuck? Explain why, in terms of the order in which a call evaluates its parts.

    let c = ref 10;
fn bump() -> Int { c := deref c * 2; deref c }
fn pick(f: fn(Int, Int) -> Int) -> fn(Int, Int) -> Int { println("pick"); f }
fn main() {
    println(pick(|a: Int, b: Int| b - a)(trace("one", bump()), trace("two", bump())));
    let g = |a: Int| a;
    println(g(trace("three", bump()), trace("four", bump())));
}

  2. Capturing mutable state. (a) What does the program print? (b) Why does c see the change a made, while b does not?

    fn make_counter(start: Int) -> fn(Int) -> Int {
    ref n = start;
    |k: Int| { n := deref n + k; deref n }
}
fn main() {
    let a = make_counter(5);  let b = make_counter(5);  let c = a;
    println(a(1) + c(2));
    println(b(3));
}

  3. Closures and state. What list does this produce, and why? Say which part of each closure's result was fixed when the closure was made and which part was read when it was called.

    ref fs: [fn(Int) -> Int] = [];   ref k = 1;
for i in [10, 20] {
    let snap = deref k;
    fs := (|x: Int| x + i * snap + deref k) :: deref fs;
    k := deref k + 1;
}
map(deref fs, |g: fn(Int) -> Int| g(0))

  4. Static vs dynamic scope. Each call is made in main, after let x = 5;. Give its value (or stuck) under static scope and under dynamic scope (a body runs in its caller's environment).

    let x = 2;
fn show() -> Int = x * 10;
fn wrap(x: Int) -> Int = show() + x;
fn make() -> fn() -> Int { let x = 7; || show() + x }
    static (Bridger)dynamic
    show()
    wrap(1)
    make()()

  5. Looking back at M3. Explain how your M3 evaluator evaluates this block, and what it produces. What would it produce if the if line were deleted?

    { let i = ref 0;  let s = ref 0;
  while deref i < 10 {
      i := deref i + 1;
      if deref s > 5 { return deref i; }
      s := deref s + deref i;
  };
  deref s }
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: write a function whose two arguments both change one cell and work out its value; make two counters and a copy of one, and say which share a count; build a list of closures inside a for loop and inside a while loop over a cell, and predict what each returns; take a program in which a caller binds the same name as a function's free variable and trace it under both scope rules; and put a return inside a loop inside a block and say where it stops. If you have the interpreter built, run your programs and check yourself.
