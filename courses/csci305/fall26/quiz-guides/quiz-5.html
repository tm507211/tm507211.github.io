Quiz 5 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 13–15 and their textbook chapters: conditionals and loops, first-class functions, and evaluating function calls. One question also looks back at a design decision in your Milestone 2 evaluator. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 15 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions. Most give you a small block of Bridger code to trace by hand — say what it evaluates to or what it prints, and why. One asks you to compare evaluation strategies (for example, what a call prints under call by value vs. call by name). One question looks back at your Milestone 2 evaluator — no Rust to write, just explain a decision in words.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-While-True, E-App) if it helps, but you are never required to.

Conditionals and loops Lecture 13

Reading: Conditionals and loops  |  Slides: Lecture 13

Be able to:

  • Explain that if is an expression valued by the branch it takes: the condition is evaluated first, its store is threaded into the chosen branch, and the other branch is never evaluated — so only the taken branch's effects happen.
  • Say why an if with no else must have a ()-valued branch: the form still needs a value when the condition is false, and () is the only one the language can supply without a branch (it reads as if e1 then e2 else ()).
  • Read the two while rules: E-While-False stops and yields (); E-While-True runs the body, discards its value, and then derives the same loop again against the store the body left.
  • Explain what that self-reference means: a terminating loop is a finite stack of E-While-True closed by one E-While-False; a loop that never stops has no finite derivation, and so no value. Say why a while needs the store to do anything (without a cell to change, its condition can never change).
  • Trace a loop over cells by hand, including a one-armed if in the body, and say what the cells hold afterward and what the loop itself evaluates to (()).
  • Describe for x in xs: it walks the list's cons cells, binds x fresh on each turn, yields (), always stops (the list is finite), and accumulates a result only through a cell that outlives the loop — not by assigning to x.
  • Explain return e: it produces a returning outcome that travels outward, skipping the rest of the block and the remaining turns of any loop, until a function boundary catches it.
  • Recognize the design space: if-as-expression vs. C's if statement plus the ?: operator; C's do/while and three-part for, Python's and Rust's iterator for; Bridger's lack of break/continue; and the functional answer that makes none of jump, loop, or branch a primitive (repetition by recursion, selection as an expression).

First-class functions Lecture 14

Reading: First-class functions  |  Slides: Lecture 14

Be able to:

  • Explain the problem a subroutine solves, and the return problem it raises: a routine reached by a jump has to get back to a place that differs for every caller. Describe how the Wheeler jump solved it (the routine writes its own return jump into its exit order) and why that allows only one active call per routine — no recursion.
  • Distinguish the historical function (a call inside an expression, yielding one value) from the procedure/subroutine (a call that stands as a statement), and say why neither word promised “no effects” — Pascal and Fortran 77 made that promise a rule; C and Bridger have one kind of routine, with void/() marking a procedure.
  • State Strachey's test for a first-class value — is there anything a program can do with a number that it cannot do with a function? — and say what Algol 60 allowed a procedure (called, passed as an argument) and did not (bound to a variable, returned, stored).
  • Show Bridger's functions passing that test: bound by let, passed, returned, stored in a list or a cell. Know the two things a Bridger function cannot do (compare with ==, be printed) and why.
  • Explain that a top-level fn and a lambda |x: Int| … make the same kind of value, and that a procedure is just a function whose result is ().
  • Explain why evaluating a lambda runs nothing (E-Lam has no premises): let never = |x: Int| x / 0; is fine until never is called.
  • Say what a closure is — parameters, body, and the environment in force where the lambda was evaluated — and why it must record that environment: a function body is the first code that runs somewhere other than where it was written, and lexical scope says its free names mean what they meant where it was written.
  • Explain why “pass down only” (Algol, Pascal) and “pointers with no nested functions” (C) are cheaper designs than full closures: a function passed down is used while its defining environment still exists; one returned up or stored needs that environment to outlive the call that made it.

Evaluating function calls Lecture 15

Reading: Evaluating function calls  |  Slides: Lecture 15

Be able to:

  • Name the decisions a call makes: what is evaluated first, when an argument is evaluated, which environment the body runs in, and what happens when the body leaves early.
  • Read E-App premise by premise: evaluate the operator to a closure; evaluate the arguments left to right, threading the store (so a call whose arguments print prints them in order); run the body in the closure's captured environment extended with the parameters.
  • Explain that the caller's environment is used only for the operator and the arguments — never for the body. Trace a program in which the caller and the function's definition site bind the same name differently, and say which value the body sees.
  • Explain why each call builds a fresh frame on top of the captured environment rather than writing into it: two calls, or the levels of a recursion, would otherwise overwrite one another's parameters.
  • Explain how a return is caught by the call (unwrap: a returned value and an ordinary one both become the call's value), so the expression around the call carries on normally — and that a return inside a lambda leaves only that lambda, however deep inside another function's work it runs.
  • Say when each stuck call is detected: a non-function operator before any argument runs (NotAFunction); a wrong number of arguments only after they have all run (ArityMismatch).
  • Describe Algol 60's two parameter kinds: call by value (evaluate once into a local) and call by name (the argument's text replaces the parameter throughout the body, and runs each time the body reaches it). Know what Jensen's device does with that, and what a thunk is.
  • Compare call by value, call by name, and call by need: how many times an argument runs if the body uses it zero, one, or two times, and what a function that ignores a stuck or printing argument does under each.
  • Explain why a language with effects in ordinary expressions (Bridger) keeps call by value, and how a || lambda writes a by-name argument by hand.
  • Compare approaches to evaluation order: fixed left to right (Bridger, Java), unspecified (Scheme), and C, where two arguments that modify the same variable make the program undefined — and what each choice gives the compiler or the programmer.

Looking back at Milestone 2 Reflection

Reading: Milestone M2  and Environments and let.

Be able to:

  • Explain why your Block arm evaluates a let's right-hand side before extending the scope: let binds its name over the rest of the block, not over its own right-hand side, so let x = x + 1 reads the enclosing x. Trace nested blocks that shadow a name.
  • Explain why leaving a block needs no undo: Env::extend returns a new child scope and leaves the original untouched, so the outer block still holds its own environment.
  • Connect that property to closures: because an existing environment is never changed, a closure's captured environment keeps meaning what it meant where the function was written, and every call can extend it into a fresh frame without disturbing it.
  • Say why a block whose last item ends in ; (or is a let) has the value (), and why an unbound name is stuck (UnboundVariable) rather than given a default value.
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: write a small while over two cells and trace the store turn by turn; put a return inside a loop inside a function, and another inside a lambda handed to fold, and say where each one stops; write a function whose body mentions a global that the caller shadows, and say which value the body reads; and take a function that uses a parameter zero, one, and two times and say how often its argument runs under call by value, by name, and by need. If you have the interpreter built, run your programs and check yourself.
