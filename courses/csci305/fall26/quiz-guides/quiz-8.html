Quiz 8 Study Guide

CSCI 305: Concepts of Programming Languages

This guide lists what you should be able to do, not the questions you will be asked. It ranges a little wider than the quiz itself, and covers Lectures 23–24 and their textbook chapters: declarative programming with relations and rules, and unification. Evaluating relations (Lecture 25: rounds, fixpoints, semi-naive evaluation) is not on this quiz. Answers are short: a sentence or two, in your own words, earns full credit.

What to expect
When
At the start of class, on the date shown in the schedule.
Length
About 20 minutes.
Rules
Closed book, handwritten.
Format
A handful of short conceptual questions. Some give you a small Bridger program with relations and rules — say what it prints, and why. One asks you to draw a derivation tree from rules written as inference rules. Others ask you to match atoms against facts by hand, or to compare how Bridger and Prolog answer the same query.
Answers
Explanations in your own words — no memorized dates or trivia. You may name a rule (E-AddFact, E-Clear) if it helps, but you are never required to.

Declarative programming Lecture 23

Reading: Declarative programming  |  Slides: Lecture 23

Be able to:

  • Read a rule as logic: its head holds whenever its body does, and each variable stands for every value. Read a variable that appears only in the body as “for some” value, and two rules for one relation as an “or”.
  • Write a rule as an inference rule (body above the bar, head below), and draw the derivation tree for a fact: rule instances at each step, recorded facts at the leaves. Say which values each step gives the rule's variables.
  • Explain the meaning of a program, M(P, Δ): the least set of facts that contains the recorded facts and is closed under the rules. Say why a closed set can be too big, and why the set of derivable facts is exactly the least one.
  • Say what does and does not change M(P, Δ): changing a rule or a fact can; the order of rules, of a body's atoms, or of adds cannot.
  • Answer a query by hand: a solution is a value for each hole that makes the query a member of M(P, Δ). Use each place a query can appear: solutions q (a list, of tuples when there are several named holes), a query in Bool position (is there a solution?), and for q { … } (once per solution, holes bound as variables).
  • Predict a query's output: a set, so each solution appears once; listed in canonical (sorted) order; an anonymous hole ? is matched but not reported.
  • Trace add and clear: add evaluates ordinary expressions and records a fact (adding one already present changes nothing); clear R removes the facts add recorded for R, but not the program's own facts from body-less rules. Derived facts follow whatever is recorded now.
  • Distinguish stored and derived relations (EDB and IDB), and say why the relation database Δ is kept apart from the store: facts accumulate between clears, and a query reads Δ without changing it.
  • Explain why a rule's terms are only variables and literals (rule nat(n + 1) :- nat(n); does not parse), why that keeps M(P, Δ) finite, and how a program computes new values instead (ordinary code that loops and calls add).
  • Recognize the design space: Prolog's compound terms (a general-purpose language, with possibly infinite meanings); Prolog's search from the query, which depends on rule and atom order and can recurse forever when a body starts with an atom of the relation being defined; SQL's recursive queries (WITH RECURSIVE), which define a relation by recursion inside a database.

Unification Lecture 24

Reading: Unification  |  Slides: Lecture 24

Be able to:

  • Write a substitution θ and apply it to an atom (Aθ). Say when an atom is ground.
  • Match an atom against a fact under a substitution, position by position: a constant must equal the fact's value; a variable already bound must have the fact's value; an unbound variable is bound to it. Give the extended substitution, or say which position fails.
  • Explain why one position can test under one substitution and bind under another, and why a variable written twice in one atom (parent(x, x)) is bound at its first position and tested at its second.
  • Match a rule body by carrying a set of substitutions through its atoms: start from the empty substitution; each atom drops the substitutions it matches no fact under, and extends the others once per matching fact. Apply what remains to the head to get the derived facts.
  • Explain how a variable shared between atoms comes to mean “the same value” (the first atom binds it, later ones test it), and why this is a join.
  • Say why reordering a body's atoms changes the work done but never the result.
  • Treat a query the same way: holes are variables, other arguments are evaluated and become constants, a repeated hole is one variable, and an anonymous hole shares with nothing.
  • Contrast Bridger's matching with the type checker's unification from Part VI: one-sided (facts are ground), no compound terms, no occurs check needed.
  • Recognize the design space: Prolog's two-sided unification over compound terms (append run “backwards” to split a list); the occurs check and why most Prologs skip it by default; choosing which atom to match first, and indexing a relation by column.

Sample questions Practice

These are the same kind and size of question as the quiz, on different programs. No answers are given: work each one by hand first, then, if you have the interpreter built through M6, run the program to check yourself.

  1. Recording facts. What does main print? Explain each line in terms of the facts the program means at that point.

    relation owns : (String, String);   relation pet_owner : (String);
rule owns("ann", "cat");
rule pet_owner(p) :- owns(p, "cat");
rule pet_owner(p) :- owns(p, "dog");

fn main() {
    add owns("bob", "dog");  add owns("ann", "dog");  add owns("cy", "fish");
    println(solutions owns(?, ?pet));
    println(solutions pet_owner(?p));
    clear owns;
    add owns("cy", "dog");
    for pet_owner(?p) { println(p ++ " has a pet"); }
    println(owns("ann", ?));
}

  2. Derivations. A program records edge("a", "b"), edge("b", "c"), edge("c", "d"), and edge("a", "c"). Its two rules for path, written as inference rules, are:

       edge(x, y)                   edge(x, y)    path(y, z)
  ------------  (Path-Edge)     ------------------------  (Path-Step)
   path(x, y)                          path(x, z)

    The fact path(a, d) has two different derivation trees. Draw both, and label each step with its rule and the values of its variables.

  3. Matching. Match each atom against its fact under θ. Give the extended θ′, or fails and why.

    atomθfactθ′, or fails and why
    edge(x, "c"){}edge("a", "c")
    edge(x, y){x ↦ b}edge("a", "c")
    path(y, y){}path("c", "c")
    edge("a", z){x ↦ a}edge("a", "b")
    path(x, z){z ↦ d}path("b", "c")

  4. Joins. What does main print? Explain by listing the substitutions that remain after matching each atom of colleague's body, in order. Is everyone in the output someone you would call a colleague?

    relation works_in  : (String, String);   // works_in(e, d): e works in department d
relation colleague : (String, String);
rule colleague(a, b) :- works_in(a, d) and works_in(b, d);

fn main() {
    add works_in("ann", "sales");  add works_in("bob", "sales");
    add works_in("cy", "legal");
    println(solutions colleague(?a, ?b));
}

  5. Search order. What does main print? Prolog searches backwards from a query, trying a relation's rules in order and a body's atoms left to right, each as a new query. What happens if reach("a", "b") is answered that way, even though it has a solution? What change to the rules would let the search answer it, and why does that change not matter to Bridger?

    relation edge : (String, String);   relation reach : (String, String);
rule reach(x, z) :- reach(x, y) and edge(y, z);
rule reach(x, y) :- edge(x, y);

fn main() {
    add edge("a", "b");  add edge("b", "c");
    println(reach("a", "b"));
    println(solutions reach(?from, "c"));
}

  6. Rules that build values. Bridger rejects this program at the +. What would nat mean if the rule were allowed, and why does that conflict with how Bridger answers a query? Rewrite main so that nat holds 0 through 10.

    relation nat : (Int);
rule nat(0);
rule nat(n + 1) :- nat(n);
fn main() { println(solutions nat(?n)); }
How to practice
The single best rehearsal is the Concept Checks at the end of each textbook chapter — they are the same kind of short, conceptual question, with worked answers you can check yourself against. Work them with the answers hidden first. Beyond that: write a few facts about your own family, friends, or courses, and a recursive rule over them; draw the derivation tree for one derived fact; fire one rule by hand, writing out the table of substitutions after each body atom; ask the same query with the holes in different places; and clear a relation that also has program facts and predict what remains. If you have the interpreter built, run your programs and check yourself.
