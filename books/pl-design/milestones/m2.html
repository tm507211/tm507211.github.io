A Practical Introduction to Programming Language Design

Milestone M2

Environments and Binding

Part III gave a name a value. The environment is the map from names in scope to the values they denote, let extends it over the rest of a block, lexical scope fixes which binding each name reads from the program text, and the scope chain is what an environment is made of at run time. This milestone puts a variable and a block into the evaluator, so that the env parameter carried unused since Milestone M1 finally does work.

Setting up

The toolchain, the clone, and the codebase are the ones from Milestone M1; the setup there is done once. The loop you repeat each milestone is the same, with the milestone number advanced:

cargo m2                                    # run the Milestone-2 tests
cargo fmt                                   # format your code
cargo clippy --all-targets -- -D warnings   # lint

cargo m2 is cargo test --features m2, and the milestones are cumulative: it runs the M2 tests and every M1 test, so the expression fragment keeps passing as you grow the evaluator.

Finding the holes

The same search lists what this milestone asks for:

grep -rn 'todo_m2!' src

turns up two arms of eval_expr:

// src/interp/eval.rs — the two M2 arms of eval_expr
Expr::Var(..)   => todo_m2!("E-Var"),
Expr::Block(..) => todo_m2!("E-Block / E-Let / E-Seq"),

A variable is read against the environment, and a block threads an environment that each let extends. Every other Expr variant is a hole tagged for a later milestone, so the crate still compiles with these two unwritten.

The specification you must satisfy

Each form this milestone adds, the rule that gives it meaning, and when it is stuck:

ExpressionRuleStuck when
xE-Varx is not bound in the environment — the new error UnboundVariable
{ let x = e; rest }E-Letonly if a subexpression is stuck
{ e; rest }E-Seqonly if a subexpression is stuck
{ … e }E-Blockonly if the tail is stuck
{ }, { …; }E-Empty—

The full rules are in the Environments and let chapter; this table is the checklist your evaluator is measured against, not a second statement of them. Reading a variable is the whole of E-Var. A block is one arm covering the other four rules: it walks its items top to bottom, and its value is the trailing expression, or unit when there is none.

Two contracts carry over from M1 and hold here. On success an arm returns Ok(v); a stuck subexpression returns Err(Control::Raise(…)) and the ? operator sends it straight out, so a stuck item aborts the block at that item's span rather than running the rest. And the environment is read-only: a let adds a binding by producing a new scope, and it never rewrites an existing one — rebinding a name shadows it.

Implementing the arms

Destructure each arm's .. into the fields you need. The two M2 variants and what they carry:

VariantFieldsCovers
Expr::Var(Name, Span)E-Var — one name, and the span to blame if it is unbound
Expr::Block(Vec<Stmt>, Option<Box<Expr>>, Span)the items, the optional tail expression

A block's items are Stmt values, of which there are two:

StatementFieldsIs
Stmt::Let(Name, Option<Ty>, Expr, Span)let x = e; — bind x to e over the rest
Stmt::Expr(Expr)a bare expression, evaluated for effect and discarded

The Option<Ty> on Stmt::Let is a type annotation the programmer may write (let x: Int = …). It is unused until the type checker of Part VI reads it; evaluation ignores it.

The environment reaches the arms through the method's env parameter, and an Env offers the two operations the environments chapter described:

  • Look a name up with env.lookup(x), which returns Some(v) for a bound name and None for one that is not in scope. A None is the stuck case: return RuntimeError::UnboundVariable { name, span }, carrying the name and the variable's span. As in M1, a From<RuntimeError> for Control is provided, so ? and .into() lift it into the Control::Raise the signature returns.
  • Extend the environment with env.extend(name, value), which returns a new Env with one more binding and leaves the one it was called on untouched. A block threads this through its items: a Stmt::Let evaluates its right-hand side in the current environment and then extends it for the items that follow; a Stmt::Expr evaluates in the current environment and carries the same one forward. The trailing expression is evaluated in the environment the items built, and its value is the block's — or Value::Unit when there is no trailing expression.

Because extend produces a child scope rather than editing the parent, the environment a block builds is local to it: when the arm returns, that environment is dropped and the caller's is unchanged, which is why a name bound inside a block is not in scope outside it. The environments chapter worked the shape of both arms; the rest of M2 is filling them in.

Worked examples

A block, and the value it evaluates to:

{ let x = 2; x + 3 }               ⇓ 5
{ let x = 1; let y = x + 1; y }    ⇓ 2      (a later let sees the earlier one)
{ let x = 1; let x = x + 1; x }    ⇓ 2      (the second binding shadows the first)
{ 1; 2; 3 }                        ⇓ 3      (the first two are discarded)
{ let x = 5; }                     ⇓ ()     (a trailing ; leaves no tail)
{ }                                ⇓ ()

And expressions with no value, which halt the run:

y                        ⇓ stuck   (UnboundVariable: y is not in scope)
{ { let x = 1; x }; x }  ⇓ stuck   (x's scope ended at the inner })
{ z; 1 }                 ⇓ stuck   (the unbound z aborts the block before the tail)

How to know it works

cargo m2 runs the provided M2 tests together with M1's; all pass means the fragment is likely correct. Each test builds an Expr and evaluates it — a value test checks the Value, and a stuck test checks the error's variant, its name, and the span it blames. The M1 builders are joined by var, let_, and block (and env_with, which sets up an environment by hand), so a check reads close to the rule it exercises:

// { let x = 2; x + 3 }  ⇓  5
let b = block(
    vec![let_("x", int(2, 1), 0)],
    Some(binary(Add, var("x", 2), int(3, 3), 4)),
    5,
);
assert_eq!(value_of(&b), Value::Int(5));

// y  is stuck: an unbound variable, blamed at its span
let bad = var("y", 3);
assert!(matches!(stuck(&bad),
    RuntimeError::UnboundVariable { ref name, span }
    if name == "y" && span.start == 3));

Fill an arm, run cargo m2, and repeat until all M2 tests pass.

Design problems

Trace { let x = 1; { let y = 2; { let z = 3; x + z } } }: its value, the environment x + z is read in, and how many scopes the lookups of x and z walk. Which chapter's rule fixes the value, and which chapter's representation fixes the walk?

It evaluates to 4. At x + z the scope chain is {z:3} → {y:2} → {x:1} → root, built by three extends as evaluation entered the three nested blocks. Looking up z finds it in the innermost scope — one scope visited; looking up x misses at z's scope, misses at y's, and hits at the third — three scopes. The value is fixed by E-Let and E-Var: each let extends the environment over the rest of its block, and E-Var reads the threaded environment, so x is 1 and z is 3. The walk is a property of the representation from the representations chapter: a lookup follows parent links outward and stops at the first match, so its cost is the number of scopes between the use and its binding.

You want a counter that starts at 0 and whose value goes up each time you read it. Can M2's let build one? Distinguish shadowing from the mechanism you would actually need, and say which part introduces it.

M2's let cannot. A let binds a name to a value once and never changes that binding: the environment is read-only, so let n = n + 1 does not make n count — it produces a new binding that shadows the old one over the rest of the block, and the old value is untouched, not incremented. Shadowing changes which value a name reads from a point in the text onward; it does not make one value change over time. A counter needs a binding whose contents change while the name stays put — a mutable cell — which is a different mechanism, held in the store rather than the environment, and it arrives in Part IV.

Nothing an M2 program does can tell lexical scope from dynamic scope. Explain why, using what a block is the only way to do at M2, and name the feature that would make the two observable.

Under lexical scope a free name resolves in the environment where the code is written; under dynamic scope, in the environment where it runs. At M2 the only way to enter a new environment is to enter a block, and the code that runs in a block's environment is exactly the code written inside that block — so "where it is written" and "where it runs" name the same place, and the two disciplines pick the same binding for every occurrence. They diverge only once a region of code can be carried away from where it was written and run elsewhere, which is what a function does: its body mentions free names, and a call runs that body somewhere other than where it was defined. Functions arrive in Part V, and that is where the choice becomes observable.

Write one Bridger block that evaluates to 30 using three lets, each defined in terms of the one before it. Then move a single use so the block instead raises UnboundVariable, and say why.

One block that works, each binding built from the previous:

{ let a = 5; let b = a + a; let c = b + a; a + b + c }   // 5 + 10 + 15 = 30

Every use sits after the let that binds it and inside the same block, so each name is in scope where it is read. Now push one binding into a nested block, so its scope ends at that block's brace:

{ let a = 5; { let b = a + a; }; let c = b + a; a + b + c }

b is bound only inside the inner block; its scope is the rest of that block and no further (E-Let extends over the block's remainder). The inner block ends, b leaves scope, and let c = b + a reads a b that is no longer bound — env.lookup returns None and the block is stuck with UnboundVariable. The value never had a chance to shadow anything outward: a block produces a value, not an environment, so a binding made inside it does not leave it.
