A Practical Introduction to Programming Language Design

Appendix D: Bridger Language Reference

This appendix covers Bridger’s formal definitions: the rules that dictate what a program means. The concrete syntax (how one writes a Bridger program as a string of characters) can be found in Appendix B, and Bridger’s prelude (the set of built-in functions and capabilities) is in Appendix C. Throughout the book, each chapter develops the semantics of Bridger one feature at a time. This appendix develops the full formal semantics all at once in its complete form. To learn how to read an inference rule, and the symbols the rules use, see the Notation reference in Appendix G.

Abstract syntax

The rules range over the abstract syntax (the output of Bridger’s parser, after the surface details of the concrete syntax are resolved). In the AST chapter we detail that tree, including the exact Rust enum this book asks you to interpret through its milestones. Below is the grammar, over programs, expressions e, blocks, definitions d, patterns p, and query atoms q:

e::= ∣ ∣ ∣ ∣ ∣ ∣ ∣ ∣ ∣ ∣ blk::= arm::= prog::= d::= ∣ ∣ ∣ ∣ ∣ ∣ ∣ p::= ∣ q::= a::= ​n∣b∣s∣()x∣self−e∣e⊕e∣e⊗enot e∣eande∣eore∣e++eif e then e else e∣match e {arm+}(e,…,e)∣[e,…,e]∣e.i∣e.fC(e,…,e)∣S{f:e,…}e(e,…,e)∣e.m(e,…,e)∣λx,…,x.eref e∣deref e∣e:=ewhile e e∣for x in e e∣for q e∣return e{blk}∣add q∣clear R∣solutions(q)∣q(let x=e)blk∣eblk∣e∣εp [if e]⇒ed∗fn f(x,…,x)=elet x=etype T=C(τ,…)’|’⋯’|’C(τ,…)struct S{f:τ,…}trait Tr{(fn m(self,x:τ,…)→τ)∗}impl [Tr for] τ{(fn m(self,x,…)=e)∗}relation R:(τ,…)rule q [:- body]_∣lit∣x∣C(p,…)∣(p,…,p)[p,…]∣[p,…,…x]∣p::p∣S{f:p,…}∣p’|’pR(a,…,a)e∣?x∣?​​literalsvariable, receivernegation, arithmetic, comparisonboolean, concatenationconditionalstuple, list, projection, fieldconstructor, struct literalapplication, method, lambdareferencesloops, returnblock, relationsblock interiormatch armprogram (definitions, order-free)functionglobaldata typestructtraitimplrelationrulewildcard, literal, variable, constructor, tuplelist, cons, struct, orquery atomquery argument​

Here ⊕∈{+,−,∗,/,%} ranges over the arithmetic operators and ⊗∈{==,!=,<,≤,>,≥} over the comparisons. A projection index i is a literal integer; f is a field name, m a method name, C a constructor, S a struct name, Tr a trait, R a relation. The quoted '|' inside a data type or an or-pattern is Bridger’s own token, set apart from the metagrammar’s ∣ as in Appendix B. The ref x = e binding desugars to let x = ref e, and fn foo(x: Int) = e; to fn foo(x: Int) { e }.

Definitions appear only at the top level; a block holds let bindings and expressions, so a local function is a let-bound lambda, and execution begins at a required main. A type, struct, trait, impl, or fn may take type parameters ⟨Tˉ⟩ with trait bounds; the grammar leaves these implicit and the typing rules make them explicit.

Values

Evaluation produces a value. The values are the literals, the compound forms built from them, a location (the identity of an allocated cell), and a closure (a function paired with the environment it captured):

v::= ∣ ∣ ∣ ​n∣b∣s∣()(v,…,v)∣[]∣v::vC(v,…,v)∣S{f=v,…}ℓ∣⟨λx,…,x.e, ρ⟩​​integer, boolean, string, unittuple, empty list, consconstructor value, struct valuelocation, closure​

where n ranges over integers (Z), b over the booleans true and false (B), and s over strings. A list is the empty list [] or a cons vh​::vt​; the literal [v1​,…,vn​] is shorthand for v1​::⋯::vn​::[]. A nullary constructor value is written C for C().

Evaluation is carried out against three pieces of state. The environment ρ maps each variable in scope to its value; the store σ maps each allocated location to the value it holds; and (from the relations section) the relation database Δ holds the facts that queries read.

ρ:Var⇀vσ:Loc⇀vΔ⊆{R(v,…,v)}

The grammar above is complete — every value a Bridger program produces is one of these. Its forms enter the language across the book (locations with mutable references, closures with functions, the compound forms with tuples and lists); the reference gathers them here so the rules below have their operands defined.

The evaluation judgment

The central judgment is

ρ⊢⟨e,σ,Δ⟩⇓⟨r,σ′,Δ′⟩r::=Val v∣Ret v

read in environment ρ, evaluating expression e against store σ and relation database Δ produces outcome r, updated store σ′, and updated database Δ′. The outcome is Val v for an expression that finishes normally with value v, and Ret w for one that returns early (return w) without executing the remaining body of the enclosing function. Once Ret w hits the enclosing function boundary, it turns from a returned value into a regular Val w.

Two conventions keep the rules readable:

  • A bare value (v) in result position means Val v. A conclusion or premise written ⟨v,σ′⟩ abbreviates ⟨Val v,σ′⟩. The Ret outcome is always written out. So every value-case rule reads as an ordinary big-step rule, and only return, application, and the loops mention Ret at all.
  • Ret short-circuits. When a premise written ⟨vi​,σi​⟩ is discharged by a subexpression that instead yields ⟨Ret w,σi​⟩, the rule does not fire; the enclosing expression evaluates to ⟨Ret w,σi​⟩, and the subexpressions to its right are not evaluated. This one convention threads Ret outward through every rule without doubling any of them.

Worked expansion. To see what the conventions abbreviate, consider the rule for addition:

ρ⊢⟨e1​+e2​,σ,Δ⟩⇓⟨v1​+v2​,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩v1​,v2​∈Z​(E-Add)

The above rule is actually three separate rules. The case where bot operands evaluate to values:

ρ⊢⟨e1​+e2​,σ,Δ⟩⇓⟨Val (v1​+v2​),σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨Val v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨Val v2​,σ2​,Δ2​⟩v1​,v2​∈Z​(value)

and two more cases where the left or right operand return a value Ret w:

ρ⊢⟨e1​+e2​,σ,Δ⟩⇓⟨Ret w,σ1​,Δ1​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨Ret w,σ1​,Δ1​⟩​(Ret in e1​)

ρ⊢⟨e1​+e2​,σ,Δ⟩⇓⟨Ret w,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨Val v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨Ret w,σ2​,Δ2​⟩​(Ret in e2​)

Every rule uses these conventions to implicitly thread returned values while only needing to explicitly describe the semantics for the case where all operands evaluate to values. The application is explicitly stated as it unlike other rules explicitly turns a returned value within the function to a value (the value computed/returned by the function).

The environment ρ is read-only; the store σ and the database Δ are threaded — each rule passes them out of one subexpression and into the next, so a change one subexpression makes is visible to those evaluated after it. Threading is needed because a subexpression can be effectful: a call may allocate or write a reference, add and clear change the database, and either can sit as an operand of +, so x + f() may alter σ or Δ between evaluating x and combining the results.

Every rule below threads both the store and Δ in evaluation order, so each records how its subexpressions are sequenced; the rules that leave a piece of state untouched thread it unchanged rather than drop it. Slices appear in the chapters, not here — each an honest projection of the judgment above. Nothing writes the store until mutable references in Part IV, so those chapters use the store-free ρ⊢e⇓v; nothing writes Δ until the relations material, so earlier chapters drop it.

The typing judgment

The static semantics is the judgment

Γ⊢e:τ

read in typing context Γ, expression e has type τ, where Γ records the type of each variable in scope together with the enclosing function’s return type. The typing rules below give the static semantics declaratively; the bidirectional checking and local inference that decide it are built with the type checker in Part VI. The judgment is stated here first so the evaluation rules can name the types they assume.

Runtime errors: stuck evaluation

Some expressions have no value. Adding a boolean to an integer, applying a non-function, or reading a field a value does not have fits no rule, so no derivation of ρ⊢⟨e,σ,Δ⟩⇓⟨r,σ′,Δ′⟩ exists. Evaluation is then stuck: the interpreter halts and reports the offending expression rather than producing an outcome. These are Bridger’s runtime type errors, and in the untyped evaluator they are how a nonsensical program fails.

Stuckness is the absence of an outcome rather than a special one. It stands apart from the recoverable failures modeled by Option and Result, which are ordinary values handled with match and live entirely inside the evaluation relation — evaluating Err("…") is a successful derivation that yields a value. Error handling develops that distinction; the type checker later rules out the type-shaped stuck cases for the programs it accepts, leaving division by zero (and, until exhaustiveness lands, a non-exhaustive match) as the errors that survive typing.

The stuck cases, gathered from the rules below, are: an unbound variable; arithmetic, negation, or ordering on a non-integer; a non-boolean condition to if, while, and, or, or not; division or modulo by zero; a projection or field access on a value that lacks it; applying a non-function, or calling one with the wrong arity; a match no arm covers; iterating a non-list; dereferencing or assigning through a non-location; and equality on a function or relation.

Evaluation rules

Throughout, the store and database are threaded left to right. Where a rule’s premises evaluate several subexpressions, they are written in evaluation order, and both pass σ→σ1​→σ2​→⋯ and Δ→Δ1​→Δ2​→⋯ from each to the next.

Literals and variables

A literal evaluates to itself and leaves the store untouched (n, b, s, and () all take this form):

ρ⊢⟨n,σ,Δ⟩⇓⟨n,σ,Δ⟩​(E-Lit)

A variable evaluates to the value the environment binds to it; self, inside a method, is the variable bound to the receiver:

ρ⊢⟨x,σ,Δ⟩⇓⟨v,σ,Δ⟩ρ(x)=v​(E-Var)

When ρ has no binding for x the premise cannot be met, no rule applies, and evaluation is stuck on the unbound variable.

Arithmetic

Addition evaluates its left operand, then its right against the store the left produced, then combines the results — threading store and database, σ→σ1​→σ2​ and Δ→Δ1​→Δ2​, in evaluation order:

ρ⊢⟨e1​+e2​,σ,Δ⟩⇓⟨v1​+v2​,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩v1​,v2​∈Z​(E-Add)

Subtraction and multiplication take the same shape, with ⊕∈{+, −, ∗} computed on integers:

ρ⊢⟨e1​⊕e2​,σ,Δ⟩⇓⟨v1​⊕v2​,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩v1​,v2​∈Z​(E-Arith)

Division and modulo add a premise that the divisor is nonzero; when v2​=0 no rule applies and evaluation is stuck:

ρ⊢⟨e1​ / e2​,σ,Δ⟩⇓⟨v1​÷v2​,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩v1​,v2​∈Zv2​=0​(E-Div)

Modulo (%) is identical with the remainder in place of the quotient. Negation evaluates its operand and negates an integer:

ρ⊢⟨−e,σ,Δ⟩⇓⟨−v,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨v,σ′,Δ′⟩v∈Z​(E-Neg)

Comparison and equality

A comparison evaluates both operands and returns a boolean. Writing ⊗ for one of the six operators and ⊗^​ for the corresponding relation on values:

ρ⊢⟨e1​⊗e2​,σ,Δ⟩⇓⟨(v1​⊗^​v2​),σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩​(E-Cmp)

The ordering operators <, <=, >, >= require integer operands. Equality == and inequality != are structural: they compare integers, booleans, strings, unit, tuples, lists, constructor values, and struct values componentwise, so (1,[2])==(1,[2]) is true. Equality on a function (closure) or a relation has no value and is stuck. Comparisons do not chain: the grammar makes them non-associative, so a < b < c is not a program.

Boolean connectives

and and or short-circuit: the right operand is evaluated only when the left does not already settle the result. For and, a false left operand settles it, and the right is not evaluated:

ρ⊢⟨e1​ande2​,σ,Δ⟩⇓⟨false,σ1​,Δ1​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨false,σ1​,Δ1​⟩​(E-And-False)

ρ⊢⟨e1​ande2​,σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨true,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩v∈B​(E-And-True)

or is symmetric: a true left operand settles it as true without evaluating the right, and a false left operand yields the value of the right.

ρ⊢⟨e1​ore2​,σ,Δ⟩⇓⟨true,σ1​,Δ1​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨true,σ1​,Δ1​⟩​(E-Or-True)

ρ⊢⟨e1​ore2​,σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨false,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩v∈B​(E-Or-False)

Negation evaluates its operand, which must be a boolean, and flips it:

ρ⊢⟨not e,σ,Δ⟩⇓⟨¬b,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨b,σ′,Δ′⟩b∈B​(E-Not)

A non-boolean operand to any of the three fits no rule and is stuck.

Concatenation, tuples, and lists

++ concatenates two strings or two lists, threading the store left to right. On lists it appends; on strings it joins:

ρ⊢⟨e1​++e2​,σ,Δ⟩⇓⟨v1​++v2​,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v2​,σ2​,Δ2​⟩v1​,v2​∈Z∗ or v1​,v2​ lists​(E-Concat)

where v1​++v2​ on lists is v2​ when v1​=[] and vh​::(vt​++v2​) when v1​=vh​::vt​. A tuple and a list evaluate their elements left to right and collect the results:

ρ⊢⟨(e1​,…,en​),σ0​,Δ0​⟩⇓⟨(v1​,…,vn​),σn​,Δn​⟩ρ⊢⟨ei​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤n)​(E-Tuple)

ρ⊢⟨[e1​,…,en​],σ0​,Δ0​⟩⇓⟨v1​::⋯::vn​::[],σn​,Δn​⟩ρ⊢⟨ei​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤n)​(E-List)

Tuple projection e.i and struct field access e.f evaluate the compound and select a component; a projection out of range, or a field the value lacks, is stuck:

ρ⊢⟨e.i,σ,Δ⟩⇓⟨vi​,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨(v0​,…,vn−1​),σ′,Δ′⟩0≤i<n​(E-Proj)

ρ⊢⟨e.f,σ,Δ⟩⇓⟨v,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨S{…,f=v,…},σ′,Δ′⟩​(E-Field)

Conditionals

if evaluates its condition, which must be a boolean, and then evaluates the chosen branch against the store the condition produced. The other branch is not evaluated.

ρ⊢⟨if e1​ then e2​ else e3​,σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨true,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩​(E-If-True)

ρ⊢⟨if e1​ then e2​ else e3​,σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨false,σ1​,Δ1​⟩ρ⊢⟨e3​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩​(E-If-False)

Both branches must have the same type, which is a typing rule rather than an evaluation one. The else -less form is admitted only when the then-branch has type (); it behaves as if e1 then e2 else (), taking the value () when the condition is false.

Bindings and blocks

A block evaluates its elements top to bottom in an environment that grows as its bindings are met, and its value is the final expression (or () when the last element is followed by ;). A let evaluates its right-hand side and extends the environment over the rest of the block:

ρ⊢⟨{let x=e1​; rest},σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ[x↦v1​]⊢⟨{rest},σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩​(E-Let)

An element evaluated for its effect discards its value and threads its store into the rest of the block; the final expression is the block’s value:

ρ⊢⟨{e1​; rest},σ,Δ⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨v1​,σ1​,Δ1​⟩ρ⊢⟨{rest},σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩​(E-Seq)

ρ⊢⟨{e},σ,Δ⟩⇓⟨v,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨v,σ′,Δ′⟩​(E-Block)ρ⊢⟨{},σ,Δ⟩⇓⟨(),σ,Δ⟩​(E-Empty)

A let ’s own value is (); naming that value (let x = (let-free effect)) binds x to () and is caught by the checker if x is later used as anything else.

A program is a set of definitions whose order does not matter: every top-level name is visible in every definition, so any function, global, or method may refer to any other wherever it is written. Top-level names are distinct — declaring one twice is rejected. Evaluation binds them all in one program environment ρ0​ — each fn to a closure over ρ0​, each global let x = e to the value of its right-hand side — and runs main under it. The fn bindings make ρ0​ recursive, each closure capturing the very environment that holds it:

ρ0​⊇[f↦⟨λx.ef​, ρ0​⟩ ​ (fn f(x)=ef​)∈prog]

The type, struct, trait, impl, relation, and rule definitions register in the contexts they introduce (structs, relations) and bind no runtime value.

References and the store

ref e allocates a fresh location holding the value of e; the location is the value. deref e reads the location’s contents; e1 := e2 writes and yields (). Allocation picks a location outside the current store’s domain:

ρ⊢⟨ref e,σ,Δ⟩⇓⟨ℓ,σ1​[ℓ↦v],Δ1​⟩ρ⊢⟨e,σ,Δ⟩⇓⟨v,σ1​,Δ1​⟩ℓ∈/dom(σ1​)​(E-Ref)

ρ⊢⟨deref e,σ,Δ⟩⇓⟨σ′(ℓ),σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨ℓ,σ′,Δ′⟩ℓ∈dom(σ′)​(E-Deref)

Assignment evaluates the cell first, then the value, then updates the store (spec’s order: the cell, then the right-hand side, then the write):

ρ⊢⟨e1​:=e2​,σ,Δ⟩⇓⟨(),σ2​[ℓ↦v],Δ2​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨ℓ,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩ℓ∈dom(σ2​)​(E-Assign)

Two names may hold the same location, so a write through one is visible through the other — the aliasing the store model makes possible. Dereferencing or assigning through a value that is not a location is stuck.

Loops

while evaluates its condition; on false it stops with (), and on true it runs the body (whose value is discarded and is ()), then repeats against the resulting store:

ρ⊢⟨while e1​ e2​,σ,Δ⟩⇓⟨(),σ1​,Δ1​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨false,σ1​,Δ1​⟩​(E-While-False)

ρ⊢⟨while e1​ e2​,σ,Δ⟩⇓⟨(),σ3​,Δ3​⟩ρ⊢⟨e1​,σ,Δ⟩⇓⟨true,σ1​,Δ1​⟩ρ⊢⟨e2​,σ1​,Δ1​⟩⇓⟨v,σ2​,Δ2​⟩ρ⊢⟨while e1​ e2​,σ2​,Δ2​⟩⇓⟨(),σ3​,Δ3​⟩​​(E-While-True)

By the Ret convention, a return inside the body abandons the loop: the body premise yields ⟨Ret w,σ2​,Δ2​⟩, so the whole while does, and the remaining iterations do not run.

for x in e evaluates the iterable to a list, then walks it, binding x to each element. Once the iterable is a value, two rules drive the walk (a list value stands in the in position as an intermediate configuration):

ρ⊢⟨for x in e eb​,σ,Δ⟩⇓⟨(),σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨vlist​,σ1​,Δ1​⟩ρ⊢⟨for x in vlist​ eb​,σ1​,Δ1​⟩⇓⟨(),σ′,Δ′⟩​(E-For)

ρ⊢⟨for x in [] eb​,σ,Δ⟩⇓⟨(),σ,Δ⟩​(E-For-Nil)

ρ⊢⟨for x in (vh​::vt​) eb​,σ,Δ⟩⇓⟨(),σ2​,Δ2​⟩ρ[x↦vh​]⊢⟨eb​,σ,Δ⟩⇓⟨v,σ1​,Δ1​⟩ρ⊢⟨for x in vt​ eb​,σ1​,Δ1​⟩⇓⟨(),σ2​,Δ2​⟩​(E-For-Cons)

A return in the body propagates out by the same convention, abandoning the rest of the iteration. Iterating a non-list is stuck. The relational form for q e_b walks the solutions of a query instead of a list; its rule is with the relations.

return

return e evaluates e and wraps the value as a Ret outcome, which the conventions above carry outward until a function boundary catches it:

ρ⊢⟨return e,σ,Δ⟩⇓⟨Ret v,σ′,Δ′⟩ρ⊢⟨e,σ,Δ⟩⇓⟨v,σ′,Δ′⟩​(E-Return)

That return is legal only inside a function body is checked rather than evaluated: a Ret that reaches the top level with no function boundary to catch it is a static error, ruled out before evaluation.

Functions and application

A lambda evaluates, with no effect, to a closure that captures the current environment — the source of Bridger’s lexical scope, since the body will later run under the environment of the lambda’s definition rather than its call:

ρ⊢⟨λx.e,σ,Δ⟩⇓⟨⟨λx.e, ρ⟩,σ,Δ⟩​(E-Lam)

A named fn is reached through E-Var: hoisting bound it to its closure in the program environment, so f evaluates to that closure and is applied by the same rule as a lambda. Application evaluates the operator to a closure, then the arguments left to right, then the body under the captured environment extended with the parameters; a return in the body is caught here and becomes the call’s value:

ρ⊢⟨e0​(e1​,…,en​),σ0​,Δ0​⟩⇓⟨Val (unwrap r),σ′,Δ′⟩ρ⊢⟨e0​,σ0​,Δ0​⟩⇓⟨⟨λx.eb​, ρ′⟩,σ0′​,Δ0′​⟩ρ⊢⟨ei​,σi−1′​,Δi−1′​⟩⇓⟨vi​,σi′​,Δi′​⟩(1≤i≤n)ρ′[x↦v]⊢⟨eb​,σn′​,Δn′​⟩⇓⟨r,σ′,Δ′⟩​​(E-App)

where unwrap (Val v)=unwrap (Ret v)=v: whether the body finished normally or hit return, the application yields that value as a Val, so the Ret never escapes the function it belongs to. Applying a value that is not a closure, or supplying the wrong number of arguments, is stuck.

A constructor application C(e_1, …, e_n) builds a tagged value rather than calling code — the constructor C comes from a type definition, and evaluation collects its arguments:

ρ⊢⟨C(e1​,…,en​),σ0​,Δ0​⟩⇓⟨C(v1​,…,vn​),σn​,Δn​⟩ρ⊢⟨ei​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤n)​(E-Con)

Constructors and pattern matching

match evaluates its scrutinee, then tries the arms top to bottom, taking the first whose pattern matches and whose guard holds. Pattern matching is the auxiliary relation

match(p,v)=θ  or  ⊥

giving a binding θ (a finite map from the pattern’s variables to values) when v fits p, and ⊥ when it does not. Its clauses:

match(_,v)match(x,v)match(lit,v)match(p1​∣p2​,v)match(C(p1​,…,pn​),C(v1​,…,vn​))match((p1​,…,pn​),(v1​,…,vn​))match(p1​::p2​,vh​::vt​)match(S{fi​:pi​},S{…,fi​=vi​,…})​=∅={x↦v}=∅ if v=lit, else ⊥=match(p1​,v) if match(p1​,v)=⊥, else match(p2​,v)=⨄i​match(pi​,vi​)=⨄i​match(pi​,vi​)=match(p1​,vh​)⊎match(p2​,vt​)=⨄i​match(pi​,vi​)​

A constructor pattern matches only its own constructor (a different one gives ⊥); a list pattern [p1​,…,pk​] matches a list of exactly k elements, and [p1​,…,pk​,…x] a list of at least k, binding x to the remaining tail as a list. A struct pattern names a subset of the fields and constrains only those; fields it omits may be anything. An or-pattern p1​∣p2​ requires both sides to bind the same variables, a static check. Patterns are linear — a variable appears at most once — so the unions ⨄ never collide. Any structural mismatch yields ⊥.

The match rule takes the first arm j whose pattern matches and whose guard (if present) evaluates to true; guards read state but change none, so a failed guard leaves the store as the scrutinee left it:

ρ⊢⟨match e0​ {p1​[if g1​]⇒e1​, …},σ,Δ⟩⇓⟨v′,σ2​,Δ2​⟩ρ⊢⟨e0​,σ,Δ⟩⇓⟨v,σ1​,Δ1​⟩match(pj​,v)=θj​ρ∪θj​⊢⟨gj​,σ1​,Δ1​⟩⇓⟨true,σ1​,Δ1​⟩match(pk​,v)=⊥ or its guard is false(k<j)ρ∪θj​⊢⟨ej​,σ1​,Δ1​⟩⇓⟨v′,σ2​,Δ2​⟩​​(E-Match)

An arm with no guard is the case gj​=true. When no arm matches, no rule applies and evaluation is stuck on the non-exhaustive match — the residual runtime error that survives typing until exhaustiveness checking lands.

Structs, fields, and methods

A struct literal evaluates its fields in source order and builds a struct value; field access reads one back:

ρ⊢⟨S{f1​:e1​,…,fn​:en​},σ0​,Δ0​⟩⇓⟨S{f1​=v1​,…,fn​=vn​},σn​,Δn​⟩ρ⊢⟨ei​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤n)​(E-Struct)

A method call e0.m(e1, …, en) evaluates the receiver and the arguments, then runs the method whose impl matches the receiver’s runtime head type. Let head(v0​) be that type — a struct name, a constructor’s type, or a built-in — and lookup(head(v0​),m) the method the matching impl provides. The body runs with self bound to the receiver, catching return as an application does:

ρ⊢⟨e0​.m(e1​,…,en​),σ0​,Δ0​⟩⇓⟨Val (unwrap r),σ′,Δ′⟩ρ⊢⟨e0​,σ0​,Δ0​⟩⇓⟨v0​,σ0′​,Δ0′​⟩ρ⊢⟨ei​,σi−1′​,Δi−1′​⟩⇓⟨vi​,σi′​,Δi′​⟩(1≤i≤n)lookup(head(v0​),m)=⟨λself,x.eb​, ρ′⟩ρ′[self↦v0​,x↦v]⊢⟨eb​,σn′​,Δn′​⟩⇓⟨r,σ′,Δ′⟩​​(E-Method)

Resolution is by the receiver’s runtime type, and coherence — at most one impl of a given trait per head type (spec §19-c) — makes that method the same one a static, declared-type dispatch would choose, so the two dispatch strategies agree on the code that runs and differ only in when it is selected. A call to a method no impl provides is stuck.

Relations

The Datalog fragment reads and extends a global relation database Δ, a set of ground facts R(v1​,…,vn​). Every rule threads Δ; the rules here are the ones that change it, where the rest pass it along untouched. The chapters before the relations material present the Δ -free slice.

A program’s rule definitions form a fixed rule set P. Together with the current facts Δ, they denote a set of derivable facts: the least set M(P,Δ) that contains Δ and is closed under every rule, where a rule H :- B1​ and … and Bm​ derives Hθ whenever a substitution θ makes each generator atom Bi​θ a member and each pure filter Bi​θ evaluate to true. M(P,Δ) is the least fixpoint of that immediate-consequence operator; it exists and is unique because the operator is monotone (all recursion is positive — negation is confined to pure filters), and it is finite because the fragment is range-restricted and terminating (spec §12.5). Every query reads M(P,Δ).

add evaluates a relation atom’s arguments to values and inserts the ground fact; clear drops a relation’s facts. Both change Δ and yield ():

ρ⊢⟨add R(e1​,…,en​),σ0​,Δ0​⟩⇓⟨(),σn​,Δn​∪{R(v1​,…,vn​)}⟩ρ⊢⟨ei​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤n)​(E-AddFact)

ρ⊢⟨clear R,σ,Δ⟩⇓⟨(),σ,Δ∖{R(v)∣v}⟩​(E-Clear)

add is monotone by design — facts accumulate and are never retracted individually — which is what lets a query denote a least fixpoint; clear resets a relation wholesale between uses. A query atom q carries holes ?x; a solution is a substitution θ for its holes with qθ∈M(P,Δ). solutions(q) returns the list of solutions — the tuples of hole values — in a fixed canonical order, so the result is a deterministic value; a hole-free query in boolean position is true exactly when its fact is derivable:

ρ⊢⟨solutions(q),σ,Δ⟩⇓⟨[θˉ1​,…,θˉk​],σ,Δ⟩{θ1​,…,θk​}=sols(q,M(P,Δ)) in canonical order​(E-Solutions)

ρ⊢⟨q,σ,Δ⟩⇓⟨true,σ,Δ⟩q groundq∈M(P,Δ)​(E-Query-True)ρ⊢⟨q,σ,Δ⟩⇓⟨false,σ,Δ⟩q groundq∈/M(P,Δ)​(E-Query-False)

The relational for q e_b walks the solutions of q in that same canonical order, binding the hole variables of each solution and running the body once per solution, threading the store and Δ through:

ρ⊢⟨for q eb​,σ0​,Δ0​⟩⇓⟨(),σk​,Δk​⟩sols(q,M(P,Δ0​))=[θ1​,…,θk​] in canonical orderρ∪θi​⊢⟨eb​,σi−1​,Δi−1​⟩⇓⟨vi​,σi​,Δi​⟩(1≤i≤k)​​(E-For-Query)

A return in the body abandons the remaining solutions by the Ret convention. The body neither reads a partially built relation nor writes one it is iterating — for iterates a fixed M(P,Δ0​) — so the iteration order is the only thing the canonical ordering pins down, and it pins it down precisely for reproducibility.

Typing rules

The rules below are declarative: they say which programs are well-typed. The bidirectional checking and local monotype inference that decide well-typedness — filling in the types a let or a lambda parameter omits — are built with the type checker in Part VI; they compute what these rules specify. The typing context Γ binds variables to types and carries one extra slot, the enclosing function’s return type τret​, which return consults; at the top level, outside any function, that slot is empty.

The types are those of the grammar:

τ::=Int∣Bool∣String∣()∣(τ,…,τ)∣[τ]∣fn(τ,…)→τ∣ref⟨τ⟩∣Self∣N⟨τ,…⟩

where N names a declared type or struct (a bare N when it takes no arguments), and a type variable T is such a name bound by an enclosing <T>.

Literals, variables, and operators

Γ⊢n:Int​(T-Int)Γ⊢b:Bool​(T-Bool)Γ⊢s:String​(T-Str)Γ⊢():()​(T-Unit)

Γ⊢x:τx:τ∈Γ​(T-Var)Γ⊢self:Selfin a method on τ​(T-Self)

Arithmetic and negation are on Int; the ordering comparisons take Int operands and yield Bool; and, or, not are on Bool. Writing ⊕∈{+,−,∗,/,%} and ≶∈{<,≤,>,≥}:

Γ⊢e1​⊕e2​:IntΓ⊢e1​:IntΓ⊢e2​:Int​(T-Arith)Γ⊢−e:IntΓ⊢e:Int​(T-Neg)

== and != share T-Eq; a type admits equality when it is built from Int, Bool, String, (), tuples, lists, constructor, and struct types — every type but a function or a relation. Boolean connectives:

Γ⊢e1​ande2​:BoolΓ⊢e1​:BoolΓ⊢e2​:Bool​(T-And)Γ⊢e1​ore2​:BoolΓ⊢e1​:BoolΓ⊢e2​:Bool​(T-Or)Γ⊢not e:BoolΓ⊢e:Bool​(T-Not)

Compound data

Tuples and lists; a list literal’s elements share one type, and the empty list takes any element type (the inference pass fixes it from context):

Γ⊢(e1​,…,en​):(τ1​,…,τn​)Γ⊢ei​:τi​(1≤i≤n)​(T-Tuple)Γ⊢[e1​,…,en​]:[τ]Γ⊢ei​:τ(1≤i≤n)​(T-List)

Γ⊢e.i:τi​Γ⊢e:(τ0​,…,τn−1​)0≤i<n​(T-Proj)Γ⊢e.f:τf​Γ⊢e:S(f:τf​)∈S​(T-Field)

A struct literal supplies every field; a type definition gives each constructor the arrow above.

Control flow

if needs a boolean condition and branches of one type; the else -less form is that type at (). match types each arm’s body against the scrutinee’s type through the pattern, and all arms agree:

Γ⊢if e1​ then e2​ else e3​:τΓ⊢e1​:BoolΓ⊢e2​:τΓ⊢e3​:τ​(T-If)

Γ⊢match e0​ {pj​[if gj​]⇒ej​}:τΓ⊢e0​:τ0​pj​:τ0​⊣Γj​Γ,Γj​⊢gj​:BoolΓ,Γj​⊢ej​:τ(1≤j≤k){p1​,…,pk​} exhaust τ0​​​(T-Match)

The judgment p:τ⊣Γp​ reads *pattern p matches a value of type τ and binds the variables in Γp​ *: a wildcard and a literal bind nothing (_:τ⊣∅, lit:τ⊣∅ at the literal’s type), a variable binds itself (x:τ⊣{x:τ}), and a constructor, tuple, list, cons, or struct pattern types its parts against the corresponding component types and unions their bindings; an or-pattern types both sides against τ and both must bind the same variables at the same types. Exhaustiveness is checked here (spec’s non-exhaustive match is the residual runtime error until it is).

Loops are () -typed; return checks at any type, provided its operand matches the enclosing function’s return type:

Γ⊢while e1​ e2​:()Γ⊢e1​:BoolΓ⊢e2​:()​(T-While)Γ⊢for x in e1​ e2​:()Γ⊢e1​:[τ]Γ,x:τ⊢e2​:()​(T-For)

Γ⊢return e:τΓ⊢e:τret​(Γ)​(T-Return)

T-Return gives return e an arbitrary type τ, so it slots into any context (as in let x = if c then 1 else return 0), while its operand is pinned to τret​. No bottom type and no subtyping are needed; an empty τret​ slot — a return at the top level — is the static error.

References, bindings, and blocks

Γ⊢ref e:ref⟨τ⟩Γ⊢e:τ​(T-Ref)Γ⊢deref e:τΓ⊢e:ref⟨τ⟩​(T-Deref)Γ⊢e1​:=e2​:()Γ⊢e1​:ref⟨τ⟩Γ⊢e2​:τ​(T-Assign)

A let extends the context over the rest of the block; a non-binding element may have any type and is discarded; the block’s type is its final expression’s (or () when it ends in ;):

Γ⊢{let x=e1​; rest}:τΓ⊢e1​:τ1​Γ,x:τ1​⊢{rest}:τ​(T-Let)Γ⊢{e1​; rest}:τΓ⊢e1​:τ1​Γ⊢{rest}:τ​(T-Seq)

A let may carry an annotation let x : \ty_1 = e_1, which pins τ1​; without one the checker synthesizes it. A program’s fn definitions enter Γ with their declared signatures — alongside its globals and type declarations — before any body is checked, so a definition may refer to any other regardless of order, itself included:

Γ⊢(fn f(x:τ)→τr​=ef​)∗ okΓ′=Γ,(f:fn(τ)→τr​)∗Γ′,x:τ, τret​=τr​⊢ef​:τr​ for each f​(T-Fn)

Each function body is checked against its declared return type, and both return e and the fall-through value are checked against it. Declaration signatures stay mandatory even where local inference is available (spec §19-d).

Functions, methods, and generics

A lambda types its body under its parameters, its result type serving as τret​ for a return inside it; application checks each argument against the corresponding parameter type:

Γ⊢λx1​…xn​.e:fn(τ1​,…,τn​)→τΓ,x1​:τ1​,…,xn​:τn​, τret​=τ⊢e:τ​(T-Lam)

Γ⊢e0​(e1​,…,en​):τΓ⊢e0​:fn(τ1​,…,τn​)→τΓ⊢ei​:τi​(1≤i≤n)​(T-App)

A method call resolves m against the receiver’s type and checks the arguments against the method’s parameter types, with Self standing for that type in the signature:

Γ⊢e0​.m(e1​,…,en​):τΓ⊢e0​:τ0​m:(self,τ1​,…,τn​)→τ in the impl for τ0​Γ⊢ei​:τi​​(T-Method)

Generics are declaration-level. A fn f<T: C>(…) -> … has, at its definition, a scheme quantified over T with the single trait bound C. At a call site the checker instantiates T with a concrete type σ by first-order matching, and requires an impl C for \sigma to exist; the call is then typed by T-App on the instantiated signature. There is no let-generalization — a let never acquires a ∀ (spec §4, §19-e) — so the only schemes are the ones written on declarations. The matching and bound-checking are the mechanical heart of Part VI; stated here, a generic call is well-typed exactly when some instantiation of its type parameters makes the arguments check and satisfies every bound.

Relations

A relation R : (τ₁, …, τₙ) declares R; add checks its arguments against that signature and has type (), as does clear. A hole-free query in boolean position is Bool; solutions(q) collects the tuples filling the holes, at the hole positions’ declared types:

Γ⊢add R(e1​,…,en​):()R:(τ1​,…,τn​)Γ⊢ei​:τi​​(T-Add)Γ⊢clear R:()R declared​(T-Clear)

Γ⊢for q eb​:()q holes ?xj​ at types τj​Γ,xj​:τj​⊢eb​:()​(T-For-Query)

Relation and rule declarations are checked by this same system: a rule’s head and generator atoms check against relation signatures, and its filter conjuncts against Bool, so the Datalog fragment reuses the core type checker (spec §12.1) rather than a second one.

Purity and effects

A Datalog rule’s filters must be pure — free of effects and a deterministic function of the variables the generators bind — so that a query denotes a least fixpoint that the evaluation schedule cannot perturb (spec §12.2, §19-d). The judgment

Φ⊢e pure

reads given the set Φ of functions known pure, expression e is pure. The effect-free forms are pure when their subexpressions are, so purity is a congruence over most of the grammar:

Φ⊢n pure​(P-Lit)Φ⊢x pure​(P-Var)Φ⊢e1​⊕e2​ pureΦ⊢e1​ pureΦ⊢e2​ pure​(P-Op)

The same congruence covers negation, the comparisons, and/or/not, ++, tuples, lists, projection, field access, constructor application, struct literals, if, and match (arms and guards): each is pure when all of its subexpressions are. A call is pure when it targets a named function already known pure and its arguments are pure:

Φ⊢f(e1​,…,en​) puref∈ΦΦ⊢ei​ pure(1≤i≤n)​(P-Call)

A method call is pure on the same condition, taking every impl ’s version of the method to be pure. A call whose operator is not a named function — a parameter or a computed closure — has no P-Call instance and so is impure; this is what excludes function-typed parameters from filters (spec §19-d), since their behavior cannot be analyzed. The remaining forms are never pure, each because it reads or writes state that makes its result depend on more than its inputs:

ref ederef ee1​:=e2​while …for …return eadd qclear Rsolutions(q)q​

ref/deref/:= touch the store; add/clear and every query read or write the relation database Δ; the loops and return exist for control and effect. None has a purity rule, so any expression containing one is impure.

Which functions are pure is the least solution for the impure set. Let I be the smallest set of function names such that f∈I whenever f ’s body contains one of the never-pure forms directly, or calls a function in I, or calls through a parameter. Then Φ is every function name not in I. Because I is a least fixpoint over the call graph, it is exactly the functions that can reach an effect, and a rejected filter is reported with the witness path — the chain of calls from the filter to the effect it reaches (spec §19-d).

The rule this serves: in a rule H :- B₁ and … and Bₘ, every conjunct Bi​ that is a filter (an expression rather than a generator atom) must satisfy Φ⊢Bi​ pure. Enforcing it keeps rules monotone and their meaning independent of evaluation order, which is what makes the least-fixpoint semantics of the relations section well defined.

Determinism and evaluation order

For every ρ, e, σ, and Δ there is at most one triple (r,σ′,Δ′) with ρ⊢⟨e,σ,Δ⟩⇓⟨r,σ′,Δ′⟩: evaluation is a partial function, partial exactly where an expression is stuck. The order is fixed. Each rule with several premises evaluates them left to right and threads the store (and Δ) between them, so a program’s effects — writes, add s, print s — occur in one determined order. Allocation chooses some fresh location, so a store is determined up to the renaming of locations, which no expression can observe. This determinism is what lets the reference interpreter serve as an oracle and lets step counts reproduce.

Cost semantics

The challenge measures a program by a step count: the size of its big-step evaluation derivation — one unit per rule applied, so the count is the number of nodes in the tree for ρ⊢⟨e,σ,Δ⟩⇓⟨r,σ′,Δ′⟩, not a new construct. Being big-step, the tree already reflects the work done: an unevaluated and/or operand or an untaken branch adds nothing, each loop iteration is its own subtree, and a short-circuiting return drops its right-hand siblings.

Two computations otherwise ride along as side conditions, which the bare tree would charge nothing; the count adds them back. Each step of the matching relation match(p,v) counts as a node, and computing the relation database M(P,Δ) costs one unit per fixed-point iteration of its immediate-consequence operator. Environment and store lookups stay atomic — one unit within the rule that performs them. The model is fixed with Part X, where each construct’s contribution is set.
